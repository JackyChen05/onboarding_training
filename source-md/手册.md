# 前言：这本手册想帮你解决什么问题

如果你是刚入职嵌入式产品测试岗的应届生，这本手册是为你写的。它假设你没有任何测试工作经验，也不要求你事先懂射频、懂协议栈、懂音视频编解码。它唯一假设的是：你用过路由器、看过网络电视、跟智能音箱说过话。


## 一、为什么需要这样一本手册

测试这个岗位有一个很不友好的特点：入门门槛看起来很低，但天花板极高。

低在什么地方？你入职第一周就能开始干活——按着测试用例一条一条执行，看结果对不对，把不对的记下来。这件事一个星期就能学会。

高在什么地方？三年之后，有的人还在执行别人写好的用例，有的人已经能在一个陌生的产品面前，判断出“哪里最可能出问题、该怎么把问题逼出来、结果说明了什么”。这两种人的差距，不是熟练度的差距，是判断力的差距。

判断力这个东西，不会在执行用例的过程中自动长出来。它需要有人告诉你：为什么是这样、为什么不是那样、这个方法能回答什么问题、又答不了什么问题。

这本手册想做的，就是把这些“为什么”讲清楚。


| 【提示】这本手册不做什么它不是操作手册。你不会在这里找到“某某仪器的第三个菜单在哪里”这类内容——那些应该查设备说明书和部门 SOP。它不是标准原文。RFC 2544、TR-398、GB/T 25000.10 这些标准，手册会讲清它们在解决什么问题、边界在哪里，但不会替代原文。它也不是完整的知识地图。嵌入式测试涉及的知识面极广，六万字装不下。手册选的是入门阶段最该先建立的那部分认知。 |

## 二、这本手册的主线

市面上大多数测试教材的结构是“分门别类地讲方法”：这一章讲功能测试，那一章讲性能测试，再一章讲自动化。这种结构的问题是，读完之后你知道了很多方法，但不知道什么时候该用哪个。

这本手册用的是另一条主线，从一个更根本的问题出发：

测试这件事，为什么会存在？

把这个问题回答清楚，就能推出测试的目标是什么；目标清楚了，就能推出任何一项测试活动其实都在解四个子问题；四个子问题清楚了，你再去看具体的方法——性能怎么测、兼容怎么测、安全怎么测——就不再是在背方法，而是在看“这个方法是怎么解那四个子问题的”。

所以这本手册的九章是这样排的：


| 章 | 内容 | 解决什么 |
| --- | --- | --- |
| 第 1 章 | 认识测试这件事 | 测试为什么存在，它的目标函数是什么，四个不可约子问题 |
| 第 2 章 | 嵌入式产品的七个约束 | 为什么嵌入式测试不能照搬互联网那一套，难点集中在哪 |
| 第 3 章 | 三类产品与它们的失效空间 | 你将来要测的东西长什么样，它们各自最容易在哪里坏 |
| 第 4 章 | 测试基本流程与阶段策略 | 一项测试怎样从需求中长出来，不同研发阶段问的问题有何不同 |
| 第 5 章 | 质量模型与测试视角 | 质量包含哪些方面，同一个需求为什么要从多个角度测 |
| 第 6 章 | 性能测试 | 用一个专项把模型、方法、环境、工具和证据完整串一遍 |
| 第 7 章 | 兼容性、安全与自动化 | 补齐技术地图，理解产能如何被放大 |
| 第 8 章 | 测试思维 | 遇到没见过的问题时，靠什么想 |
| 第 9 章 | 测试的本质与价值 | 收束回目标函数，理解你最终要交付什么 |

第 1、2、8、9 章是“为什么”和“怎么想”，第 3 到 7 章是“是什么”和“怎么做”。两头是判断力，中间是技术。中间那部分你上网也能查到，两头查不到。

## 1.1 一个几乎所有人都答错的问题

先看第一个问题：无限的资源，能不能测到零缺陷？

大多数人的第一反应是“能”，或者“理论上能”。这个直觉背后的假设是：缺陷的数量是有限的，测试的工作量也是有限的，只要资源足够就能穷尽。

我们来算一笔账。一台家用路由器，做一次完整的无线性能测试，至少要考虑这些维度：


| 维度 | 典型取值数 |
| --- | --- |
| 帧长 | 5 种（64 / 128 / 512 / 1024 / 1518 字节） |
| 终端数量 | 10 档（1、2、4、8、16、24、32、48、64、96 台） |
| 距离与衰减 | 8 档 |
| 加密方式 | 4 种（开放 / WPA2 / WPA3 / WPA2-WPA3 过渡） |
| 信道与带宽 | 20 组以上 |
| 干扰场景 | 6 类（净空 / 邻居 AP / 蓝牙 / 微波炉 / Zigbee / 混合） |
| 业务组合 | 8 种（纯下载 / 视频 / 游戏 / 会议 / 混合……） |
| 固件版本 | 每个项目 3 到 10 个 |
| 国家码 | 30 个以上（各国法规不同） |

把这些乘起来，量级在千万以上。假设一个组合测 5 分钟，一年不吃不喝不睡也跑不完千分之一。

但这还不是最要命的地方。

上面这些组合，是你“想得到”的组合。真正咬人的缺陷，往往长在你根本没想到的地方。

比如：用户在配置保存的那一瞬间拔掉了电源；比如：设备连续运行 49 天之后某个 32 位计数器回绕了；比如：用户家里的电视是十年前的老机型，HDMI 的 EDID 信息不完整。这些组合不在任何维度表里，因为没人想到要把它们列进去。

所以答案是：不能。而且限制你的不只是资源，还有认知边界。


## 1.2 从三条公理推出测试的目标

既然不能穷尽，那测试的目标是什么？这个问题不能靠经验回答，要从更根本的地方推。


### 1.2.1 公理一：产品是一个承诺

一台路由器摆在货架上，标价三百块。用户买它的时候，买的不是那个塑料壳子和里面的电路板，买的是一个承诺：

在接下来的三到五年里，在我家这个有承重墙、有邻居 Wi-Fi、有微波炉、放着二十多台新旧设备的环境里，让我能正常上网。

这个承诺有四个要素：特定环境（家庭，不是实验室）、特定寿命（三到五年，不是出厂那一刻）、特定人群（普通用户，不是工程师）、特定行为（上网，以及一系列具体的功能）。

承诺的范围，就是测试的范围。这一点很重要，因为它直接推翻了一个常见的做法：只在实验室、只用新设备、只测出厂状态、只测半小时。那样测的是“出厂时能不能用”，而承诺的是“三年内在用户家里能不能用”——这是两件事。


### 1.2.2 公理二：实现必然偏离意图

第二条公理更根本：只要是人造物，实现就必然偏离设计意图。

这里要特别澄清一点，因为新人很容易理解错。偏差的存在，不是因为开发不认真。把测试和开发对立起来，是这个岗位最容易走的一条歪路，而且一旦走上去，你后面几年的工作都会很难受。

真正的原因是：设计者的模型永远不完整。具体来说，不完整体现在四个方面：

- 对芯片的理解不完整——芯片手册几百页，勘误表（Errata）还在不断更新。某个寄存器在特定时序下的行为，可能连原厂都没写清楚。
- 对协议的理解不完整——协议标准里大量使用“SHOULD”“MAY”这类词，留下了实现空间。你按一种理解实现，对端按另一种理解实现，两边都符合标准，但就是不通。
- 对用户的理解不完整——没有哪个开发能想到用户会把路由器塞进弱电箱、会在升级时拔电源、会用十年前的手机连 Wi-Fi 6。
- 对物理世界的理解不完整——高温下芯片会降频，湿度会影响触摸，电源纹波会耦合进射频通道。这些在代码里看不见。
四条加起来，结论是：偏差不是态度问题，是认知边界问题。所以它必然存在，也必须被系统地找出来。


| 【提示】这一条对你的实际影响当你提交一个缺陷时，正确的心态不是“我抓到你了”，而是“这里有一个我们集体都没想到的地方”。这不只是情商问题。抱着前一种心态，你会倾向于提交那些容易发现、容易证明的表面缺陷；抱着后一种心态，你才会去挖那些难的、需要跟开发一起才能定位的深层缺陷——而那些才是真正有价值的。 |
| --- |


### 1.2.3 公理三：代价随发现阶段指数增长

第三条公理关于成本。同一个缺陷，在不同阶段被发现，修复代价差别巨大：


| 发现阶段 | 修复动作 | 相对代价 |
| --- | --- | --- |
| 需求阶段 | 改一句需求描述 | 1 |
| 设计阶段 | 改设计方案 | 约 5 |
| 研发阶段 | 改几行代码 | 约 10 |
| 测试阶段 | 改代码 + 回归验证 | 约 30 |
| 量产阶段 | 停线 + 返工 + 重新验证 | 约 500 |
| 售后阶段 | 召回 + 返修 + 品牌损失 | 1000 以上 |

这张表里的具体数字在不同行业、不同产品上会有差异，但量级关系是稳定的：从研发期到售后期，差三到四个数量级。

嵌入式产品尤其如此，因为它有一个软件产品没有的特点：硬件出厂即定型。软件出了问题可以发个补丁，硬件出了问题——比如天线布局不对、散热余量不足、某个器件选型有隐患——只能召回或者认了。


## 1.3 测试的目标函数

三条公理放在一起，测试的目标就出来了：


| 【要点】测试的目标函数在有限的时间、成本和观测手段下，最大化“关于交付风险的信息获取量”。 |
| --- |

这句话看起来抽象，但每个词都是从前面推出来的，而且每个词都有实际后果。逐个拆开看：


### 1.3.1 "有限的"——约束是三重的

注意约束有三个，而不是一个。

时间和成本是显而易见的：项目排期就这么长，实验室设备就这么多，人就这么几个。

但第三个约束——观测手段——是嵌入式测试特有的，也是最容易被忽略的。你可能有足够的时间和人，但设备根本不给你看内部状态：没有日志，或者日志要抢串口才能拿到；没有性能计数器；解码器降级了但不上报。这时候即使缺陷就在你眼前发生，你也看不见。

这一点后面第 2 章会详细讲，它是嵌入式的七个约束之一。


### 1.3.2 "交付风险"——不是"缺陷"

目标函数里写的是“交付风险的信息”，不是“缺陷的数量”。这个区别很关键。

风险 = 发生概率 × 影响程度。一个必然发生但影响很小的问题（比如某个提示文案有错别字），和一个概率很低但影响致命的问题（比如升级中断会导致变砖），后者的风险远高于前者，即使它更难被发现。

所以测试资源应该按风险分配，而不是按“哪里容易找到缺陷”分配。这两者往往是相反的：容易找到缺陷的地方，通常是功能主路径，而那里的风险其实最低——因为开发自测过、产品经理体验过、其他人也都走过。


### 1.3.3 "信息获取量"——最反直觉的一句

这是整个目标函数里最重要、也最反直觉的部分：

一个必然通过的用例，信息量为零。

什么意思？信息量的定义是“不确定性的减少”。如果一条用例你在执行之前就百分之百确定它会通过，那么执行完之后，你对产品质量的认知没有任何改变。你花了工时，但没换回任何东西。

这条推论会推翻很多习惯做法：

- 用例数量不是产出。一千条必然通过的用例，信息量之和还是零。
- 覆盖率是安慰剂。组合空间是天文数字，任何覆盖率数字都只是分母造出来的错觉。真正该问的是“高风险区域的采样密度够不够”。
- 反复执行同一条稳定用例，边际信息量趋近于零。这也是为什么回归测试应该自动化——把零信息量的活交给机器，人去做有信息量的事。

| 【常见错误】那冒烟测试岂不是白做了？这是新人听完上面这段之后最常提的疑问，而且提得很好。冒烟测试确实几乎总是通过。但它回答的不是“产品有没有缺陷”，而是“这个版本值不值得投入后续测试”。它的信息量体现在极少数不通过的时候——那时候它替你省下了几十人天。所以冒烟测试的信息量是不均匀的：绝大多数时候接近零，极少数时候极大。从期望值上看，它是划算的。真正零信息量的，是那种明知不会失败、只为凑用例数而反复执行的用例。判断标准很简单：这条用例最近一年有没有失败过？如果从来没有，而且你也想不出它会怎么失败，那就该考虑把它降频或者自动化掉。 |
| --- |


## 1.4 四个不可约子问题

目标函数讲清楚了“要什么”，但没讲“怎么做”。

把任何一项测试活动——不管是功能测试、性能测试、安全测试还是自动化——剥到最底层，你会发现它都在解同样的四个问题。这四个问题不可再拆分，也不能互相替代，所以叫“不可约子问题”。


| 子问题 | 本质 | 失败的样子 |
| --- | --- | --- |
| ① 会怎么坏？ | 失效空间的构造 | 想不到的失效，必然测不到 |
| ② 怎么让它坏？ | 可控性——把系统驱到目标状态 | 缺陷存在，但激励不出来 |
| ③ 怎么知道它坏了？ | 可观测性 + 判定准则 | 现象发生了，却被判为“正常” |
| ④ 这一次说明了什么？ | 从样本外推到总体与寿命 | “测了一台一小时没问题” |

还有第五个，是元层面的问题：⑤ 我的测试有效吗？它的失败样子是“通过率 99%，市场炸了”。这一问会在第 7 章讲自动化时详细展开。


### 1.4.1 第一问：会怎么坏

这一问是构造失效空间——也就是列出“这个东西可能以哪些方式坏掉”。

为什么它最难？因为它没有输入，只有输出。前三问都有明确的对象：给你一个失效，你想办法激励它、观测它、外推它。但第一问要求你凭空想出还没发生的事。

好消息是：这不是天赋，是可以训练的。训练的方法有三条：

- 缺陷模式库——把历史上所有出过的缺陷抽象成“模式”，形成清单。你想不到的，别人可能已经踩过。这是最有效的一条，也是部门最重要的资产之一。
- 结构化激发清单——对系统的每一个接口，机械地问一遍：“断了会怎样？慢了会怎样？乱序了会怎样？满了会怎样？重复了会怎样？”这套问法能挖出大量没人想到的路径。
- FMEA / FTA——失效模式与影响分析、故障树分析。它们的价值不在于表格本身，而在于强迫你系统性地遍历，而不是凭印象。

### 1.4.2 第二问：怎么让它坏

知道会怎么坏，不等于能让它坏。这一问解决的是可控性：你能不能把系统驱动到那个失效状态。

举几个具体的例子：

- 你知道 NAT 会话表满了之后新连接会失败，但你构造不出十万条并发连接，这个缺陷就还在那里等用户去踩。
- 你知道升级过程中断电可能变砖，但你不知道该在哪个毫秒断电——手动拔插头一百次，可能一次都没落在最危险的那个窗口里。
- 你知道内存泄漏会导致设备几周后重启，但你的测试周期只有三天。
解决可控性的手段是把物理世界变成可编程的：可程控电源（精确控制断电时刻）、可编程衰减器（把“距离”变成一个数字）、损伤仪（注入指定的丢包率和抖动）、故障注入接口（直接让某个模块假装挂掉）。

这也是嵌入式自动化和互联网自动化最大的区别——第 7 章会展开讲。


### 1.4.3 第三问：怎么知道它坏了

这一问包含两个层面，而且两个层面都容易出问题。

第一个层面是可观测性：现象发生了，你能不能感知到。举个真实的例子——设备因为温度升高触发了降频保护，解码能力下降，画面开始零星掉帧。但设备既不上报也不记日志，掉帧又不明显到肉眼可辨。你在旁边盯一小时，什么也发现不了。

第二个层面是判定准则：现象你看见了，但你判它算通过还是不通过。这一层比第一层更容易出问题，也更被低估，所以下一节专门讲。


### 1.4.4 第四问：这一次说明了什么

这一问是外推：从你实际测的那一次，推到你没测的那些。

“我测了一台，跑了一小时，没问题。”——那你敢不敢批准发十万台，让它们各自跑三年？

从一台到十万台，中间隔着样本量和批次一致性；从一小时到三年，中间隔着时间加速模型和寿命评估。这两件事都不是靠“多测一会儿”能解决的，需要专门的方法：

- 概率型指标的样本量计算——要多少次才能对成功率有足够的置信度。
- 加速试验——用高温、高负载、高频操作把三年的老化压缩到几周。
- 批次抽检与过程能力分析——用少量样本推断整批的一致性。

## 1.5 判定准则：最被低估的环节

现在回到章首的第三个问题：给你一台机顶盒，测“播放视频不卡顿”，你怎么判断算通过？


### 1.5.1 三个模糊判据

大多数人的答案是“看着不卡”。我们来追问几轮：


| 追问 | 为什么这一问是致命的 |
| --- | --- |
| 你看多久？十分钟还是两小时？ | 很多卡顿是累积性的，十分钟看不出来 |
| 两小时里卡了三次，算通过吗？ | 没有门限，就没有判定 |
| 卡一次半秒和卡一次五秒，一样吗？ | 没有量纲，“卡”这个词包含了太多东西 |
| 你和同事看同一段视频，会得出同一个结论吗？ | 不会。而这意味着结论不可复现 |

最后一问是关键。如果两个人对同一现象得出不同结论，那么这两小时的工时产生的不是信息，是噪声。

类似的模糊判据在实际工作中比比皆是：

- “语音能不能唤醒”——试了几次？站多远？多吵？成功几次算达标？
- “Wi-Fi 快不快”——什么帧长？多远？几个终端？开没开加密？
- “音质好不好”——用什么设备听？多大音量？听什么内容？
- “界面流不流畅”——什么操作？后台有没有负载？多少帧算流畅？

### 1.5.2 合格判据的五要素

一条能用的判定准则，必须包含五项内容：


| 要素 | 回答什么 | 反例 → 正例 |
| --- | --- | --- |
| 观测量 | 测的是哪个具体的量 | “卡顿” → “解码丢帧数” |
| 测量方法 | 用什么方式测 | “肉眼看” → “采集卡录制后逐帧比对” |
| 判定门限 | 多少算通过 | “不卡” → “连续 2 小时内丢帧 ≤ 3 帧” |
| 样本量 | 概率型指标必填 | “试一下” → “50 次，成功率 ≥ 95%” |
| 环境条件 | 在什么条件下成立 | （省略） → “常温、有线千兆、码率 25Mbps” |

把这五项填完，前面那个模糊的“播放视频不卡顿”就变成了：

在常温、有线千兆接入、播放 25Mbps 4K 码流的条件下，用采集卡录制输出画面，连续 2 小时内的解码丢帧数不超过 3 帧，且无单次超过 200ms 的画面停顿。

这句话的好处是：任何人按它执行，都会得出同样的结论。这就是可复现。


### 1.5.3 概率型指标的特殊要求

五要素里的“样本量”只对概率型指标是必填项，但嵌入式测试里的概率型指标非常多，值得单独说。

什么是概率型指标？简单判断：同样的操作重复做，结果不总是一样的，那它就是概率型的。

- 语音唤醒率、误唤醒率
- Wi-Fi 关联成功率、漫游成功率
- 拨号成功率、配网成功率
- 掉线率、重缓冲率
- 开机成功率、升级成功率
对这类指标，“试了几次都行”不构成结论。原因是：成功率是一个估计量，不是一个确定值。你测 10 次成功 9 次，得到的 90% 只是一个点估计，它的真实值可能在 60% 到 98% 之间。


| 【案例】一个真实的判断错误某版本固件的语音唤醒测试：新版本测了 50 次成功 47 次（94%），旧版本测了 50 次成功 45 次（90%）。报告写“新版本唤醒率提升 4 个百分点”。这个结论站不住。在样本量只有 50 的情况下，94% 和 90% 的差异完全落在统计波动的范围内。换一批人、换一天再测，结果可能反过来。正确的做法有两种：要么加大样本量到足以分辨这个差异（通常需要数百次），要么在报告里明确写出“两版本差异未达到统计显著性”。这不是学术上的吹毛求疵。如果基于这个假的“提升”做了发布决策，或者放弃了本来该做的算法优化，代价是真金白银的。 |
| --- |

实际工作中的最低要求是：报告概率型指标时，必须同时给出样本量。写“唤醒率 94%”是不完整的，要写“唤醒率 94%（47/50）”。有了分母，读的人才能自己判断这个数字有多可信。

## 2.1 为什么不能照搬互联网那一套

第 1 章讲的目标函数和四个子问题，对所有软件测试都成立——测 App 是这样，测网站是这样，测嵌入式设备也是这样。

但具体到“怎么做”，嵌入式和互联网的差别非常大。原因不是技术栈不同，而是约束条件不同。

这一章讲七个约束。它们不是并列的知识点，而是一组会互相叠加、互相放大的限制条件。理解了它们，你才能明白为什么后面几章的方法会长成那个样子。


## 2.2 七个约束


### 2.2.1 约束一：物理性

系统绑定在物质上。它的行为不只取决于代码，还取决于电、热、电磁、时间对材料的作用。

一个 Web 服务出问题，你可以假设 CPU 就是 CPU、内存就是内存，它们的行为是确定的。嵌入式不能这么假设。


| 物理因素 | 会导致什么 | 为什么容易被漏掉 |
| --- | --- | --- |
| 电源纹波与跌落 | 模块间歇性复位、射频指标劣化 | 现象表现为“软件偶发异常” |
| 结温上升 | CPU 或射频降频，性能静默下降 | 降频通常不上报，实验室温度又低 |
| 射频多径与干扰 | 速率骤降、连接不稳 | 实验室是净空环境，现场不是 |
| 静电（ESD） | 端口失效、设备死机 | 需要专门设备才能复现 |
| 器件老化 | 一到两年后失效 | 验证周期内根本不会出现 |

物理性带来的最大麻烦是：物理问题经常伪装成软件问题。


| 【案例】一个典型的伪装现象：某机顶盒在用户家里偶发闪屏、雪花点，实验室复现不出来。研发查了三周解码器代码，没发现问题。真相：用户用的是三米长的廉价 HDMI 线。在 4K 60Hz、4:4:4 色度采样的高带宽模式下，链路裕量不足，出现误码。实验室用的是半米长的认证线，裕量充足。为什么难查：现象在应用层表现为“画面异常”，所有人的第一反应都是找解码器。而真正的原因在物理层，需要用眼图仪去看链路质量。教训：当一个现象查了很久查不到软件原因时，要主动往下走一层——先怀疑硬件、链路和物理条件，而不是继续在代码里找。 |
| --- |


### 2.2.2 约束二：不可逆性

硬件出厂即定型。而 OTA 升级本身，还自带“变砖”这个新的失效模式。

互联网服务的一大优势是可回滚：发现问题就回退版本，几分钟搞定，用户可能都没察觉。

嵌入式产品有三层不可逆：

- 硬件不可逆——天线布局、散热方案、器件选型，一旦量产就定死了。发现散热余量不足，只能改结构重开模具，或者用软件降频硬扛（代价是性能永久损失）。
- 已出货设备不可逆——十万台设备已经在用户家里了。你不能像服务器一样“重新部署”，只能寄希望于 OTA。
- OTA 自身有风险——升级过程中断电、回滚逻辑有缺陷、引导标志写入不是原子操作，任何一项出问题都会导致设备变砖：既起不来，也升不了级，只能返修。
第三点尤其值得警惕。它是一个典型的“引入新失效模式的解决方案”：OTA 本来是为了解决“已出货设备不可逆”的问题，但它自己带来了一个更严重的失效模式。


| 【常见错误】新人最容易低估的一件事很多人测 OTA 时，测的是“能不能升级成功”——升上去了，版本号对了，功能正常，通过。这只测了一半。OTA 真正的高风险场景是升级失败之后会怎样：断电点落在写引导标志的那一瞬间会怎样？下载到一半网络断了会怎样？新版本起不来能不能自动回滚到旧版本？回滚之后配置还在吗？变砖率必须是 0，没有“基本不变砖”这一说。一万台设备里砖一台，就是一台返修加一个愤怒的用户。 |
| --- |


### 2.2.3 约束三：时间是一等公民

设备要连续运行三到五年不重启。而常规测试的时间尺度是分钟到小时。

这是七个约束里最反直觉、也最容易被忽略的一条。

你的手机每天都在重启（或者至少每周），你的电脑每天关机。但路由器、光猫、机顶盒不是——它们插上电就一直在跑，用户不会主动重启，除非出了问题。

这意味着有一整类缺陷，只有时间才能把它们逼出来：


| 时间类缺陷 | 机理 | 典型暴露时间 |
| --- | --- | --- |
| 内存泄漏 | 某条路径每次执行泄漏少量内存，累积到 OOM | 数天到数周 |
| 句柄 / 实例泄漏 | 资源未释放，累积到上限后无法再创建 | 数小时到数天 |
| 内存碎片 | 碎片化后无法分配连续大块内存 | 数周（且需要“脏状态”才暴露） |
| 计数器回绕 | 32 位流量或时间计数器溢出 | 约 49 天（2³² 毫秒）或达到流量阈值 |
| 时钟漂移 | 音视频同步误差随播放时长累积 | 数小时 |
| 闪存磨损 | 高频写入耗尽擦写寿命 | 一到两年 |

这些缺陷有一个共同点：它们是时间的函数，不是操作的函数。你重复操作一千次也未必能触发，但让它安静地跑三周就会自己出现。


| 【常见错误】长稳测试最常见的错误做法错误做法：跑 72 小时，结束后看设备有没有重启。没重启 → 通过。为什么错：这只能发现已经爆掉的问题，发现不了正在积累的问题。设备可能在第 71 小时时内存已经占用 85%，再跑两天就 OOM 了——但你的测试在 72 小时准时结束，一切“正常”。正确做法：判据是趋势斜率，不是绝对阈值。整个长稳期间周期性采集内存、句柄、CPU、温度，画出趋势曲线。斜率应该接近零；只要是持续上升的，不管当前值多低，都是问题。还有一个补充动作：长稳结束后不要重启，直接在“脏状态”下执行升级、大内存操作、复杂功能。碎片类缺陷只有在这时候才会暴露。 |
| --- |


### 2.2.4 约束四：开放互操作

正确性是相对于“同样有 bug 的对端”定义的。

一个封闭系统的正确性容易定义：符合规格就是对的。但嵌入式产品几乎都工作在开放环境里，必须跟大量不受你控制的设备打交道：

- 光猫要和各厂商的 OLT 互通——而不同厂商对 OMCI 标准的实现有差异。
- 路由器要和上千种终端互通——不同品牌、不同系统版本、不同 Wi-Fi 芯片平台。
- 机顶盒要和各种电视、功放互通——EDID、HDCP、CEC、ARC 都可能出问题。
- 音箱要和各种智能家居设备互通——协议不同、实现质量参差不齐。
关键在于：对端本身也有 bug。你完全符合标准，对方也自认为符合标准，但两边就是不通。这时候“谁对谁错”不是判定出来的，是用证据谈判出来的。


| 【提示】互操作问题的处理套路遇到互操作问题时，你需要准备三样东西才能跟对方谈：抓包——完整的交互报文，能看出双方各自发了什么、期望什么。时序——精确的时间戳，很多互操作问题本质是超时或竞态。标准条款——引用具体的章节号，说明标准是怎么规定的。这三样凑齐，才能说清“我们的实现符合第 X.Y 节，对方在第 N 步的响应超出了标准规定的范围”。缺了任何一样，讨论都会变成互相甩锅。 |
| --- |


### 2.2.5 约束五：资源极度稀缺

MB 级的内存、性能有限的 CPU。缺陷高度聚集在资源边界。

一台家用路由器的内存可能只有 128MB 甚至 64MB，CPU 主频几百兆。这不是成本抠门，而是这类产品的售价、功耗和散热决定的。

资源稀缺的直接后果是：每一种资源都有一个明确的上限，而缺陷密度在上限附近比在中间高一个数量级。


| 资源类型 | 典型边界 | 超限后的常见表现 |
| --- | --- | --- |
| NAT 会话表 | 几千到几万条 | 网页打不开但下载正常（新建连接失败） |
| MAC / ARP 表项 | 几百到几千条 | 大量终端环境下偶发不通 |
| 组播组数 | 几十到几百组 | 频繁换台后黑屏 |
| 解码器实例 | 几个到十几个 | 反复切换片源后无法解码 |
| 并发无线终端 | 几十台 | 个别终端被“饿死”，完全没速率 |
| Mesh 节点数 | 几个到十几个 | 超限后拓扑震荡或新节点连不上 |
| 存储空间 | 几十 MB 到几 GB | 日志写满后服务异常 |

测试的启示是明确的：不要只测规格范围内的中间值，要重点测边界，而且要测超过边界之后的行为。

好的设计在超限时应该优雅降级——明确拒绝、给出提示、保护已有连接、压力撤除后自动恢复。坏的设计会崩溃、死机，或者进入一个再也出不来的异常状态。


### 2.2.6 约束六：可观测性天然差

黑盒、没有 APM、日志要抢串口。

互联网服务有完善的可观测性基础设施：日志采集、链路追踪、指标监控、性能剖析，出了问题一层层点进去就能定位。

嵌入式的处境完全不同：

- 设备通常是黑盒——量产固件关闭了调试接口，你看不到内部状态。
- 日志可能要抢串口才能拿到，而串口只有一个，多个人调试就要排队。
- 存储空间有限，日志会被轮转覆盖，等你发现问题时现场可能已经没了。
- 很多状态根本没有导出接口——降频了、丢帧了、重传了，设备自己知道，但不告诉你。
这条约束有一个非常重要的推论：


| 【要点】可测性设计（DFT）是测试工程师的上游职责如果设备不给你看内部状态，那不是“测试条件差”，而是产品设计缺陷——它没有被设计成可测试的。所以测试工程师必须在需求评审和设计评审阶段就提出可测性需求：· 关键状态要有导出接口（当前频率、温度、丢帧数、重传数、内存占用）· 日志要分级，且可以动态调整级别· 要有可注入的故障接口，方便构造异常场景· 要有稳定的时间戳和统计计数器这些需求必须在设计定型前提，事后再提就来不及了。这也是为什么第 4 章会强调“测试从读需求开始”。 |
| --- |


### 2.2.7 约束七：合规是二值闸门

认证不过 = 不能卖。没有“部分通过”这个选项。

嵌入式产品要过的认证非常多，而且性质和内部质量标准完全不同：


| 类别 | 典型项目 | 不过的后果 |
| --- | --- | --- |
| 法规强制 | CE、FCC、SRRC、3C、能效 | 该市场不能销售 |
| 无线频谱 | 各国频段、功率、DFS 规则 | 违规使用频谱，可能被处罚 |
| 授权认证 | HDMI、Dolby、DTS、Wi-Fi Alliance | 不能使用商标和技术，或功能受限 |
| 内容保护 | Widevine、PlayReady、ChinaDRM | 内容方不授权，高清内容不可播 |
| 生态认证 | GMS / CTS / GTS（Android 系产品） | 没有应用生态，产品基本作废 |
| 运营商入网 | 各运营商集采规范 | 进不了集采，失去主要出货渠道 |
| 无障碍 | EN 301 549 / EAA | 欧盟市场不能销售 |

二值的意思是：没有中间状态。内部质量指标可以说“达成了 90%，剩下的下个版本改”，认证不行——过就是过，不过就是不能卖，一天都不行。

而且认证还有两个特性让它成为项目排期的第一杀手：

- 周期长——实验室排队加上测试执行，常以月计。
- 有依赖关系——某些认证要先拿到另一个认证的证书才能送测。
所以认证不是“测试的一部分”，而是必须在项目立项时就锁定排期的关键路径。第 4 章讲阶段策略时会再回到这一点。


## 2.3 最凶的缺陷长在哪

七个约束讲完了。现在回答章首的第二个问题：为什么产品出厂前测了成千上万条用例，用户还是会遇到“重启一下就好了”的问题？

答案是：那类缺陷长在三个维度的交叉处，而常规功能测试三样都不碰。


### 2.3.1 三个维度


| 维度 | 来自哪条约束 | 具体内容 |
| --- | --- | --- |
| 资源边界 | 约束五（资源稀缺） | NAT 表项、并发连接数、组播组数、解码器实例、Mesh 节点数、内存与存储 |
| 时间累积 | 约束三（时间维度） | 内存泄漏、句柄泄漏、内存碎片、计数器回绕、时钟漂移、闪存磨损 |
| 异常路径 | 约束二（不可逆）等 | 掉电、断纤、拔线、服务超时、升级中断、看门狗盲区 |

单独一个维度的问题，通常不难发现。真正难的是两两交叉、甚至三者交叉的区域：

- 资源边界 × 时间累积：会话表本来够用，但因为老化策略有缺陷，表项缓慢累积，两周后满了。
- 时间累积 × 异常路径：长稳运行两周后内存碎片化，这时候执行升级，因为分配不到连续大块内存而失败。
- 资源边界 × 异常路径：并发连接跑到上限时突然断网，恢复后会话表没有正确清理，设备进入半死状态。
- 三者交叉：设备运行三周（时间）后，在高并发（资源边界）状态下遭遇断电（异常路径），重启后配置损坏。

### 2.3.2 常规功能测试为什么碰不到

把常规功能测试的执行条件写下来，问题就一目了然：


| 常规功能测试的做法 | 对应哪个维度 | 结果 |
| --- | --- | --- |
| 在设备空闲、刚重启的状态下执行 | 资源边界 | 离边界很远，触碰不到 |
| 单条用例执行时间从几秒到几分钟 | 时间累积 | 时间尺度差了几个数量级 |
| 按用例步骤走正常路径 | 异常路径 | 异常路径根本不在步骤里 |

三样全都不碰——所以那个交叉区对常规功能测试来说，几乎是完全的盲区。


| 【常见错误】一个必须澄清的误解看到这里，有些人会得出“功能测试没用”的结论。这个结论是错的，而且很危险。功能测试是地基。没有它，产品连基本可用都做不到，后面所有的性能、可靠性、兼容性测试都无从谈起——因为功能都跑不通，测什么？正确的理解是：功能测试是必要不充分条件。它保证了“正常路径能走通”，但保证不了“异常情况下不出事”。所以测试策略应该是：功能测试作为基线，另外专门设计针对三交叉区的测试——长稳测试打时间维度，容量压测打资源边界，故障注入打异常路径。这三类测试不会自然发生，必须显式地排进计划。 |
| --- |


## 2.4 七个约束的相互放大

最后要强调的是：这七个约束不是独立的，它们会互相放大。

举一个把五条约束串起来的例子：


| 【案例】五条约束叠加的一个真实场景现象：某型号光猫在部分小区出现“夏天下午集中掉线，晚上恢复”的问题。分析链条：夏天下午机房或弱电箱温度高（约束一：物理性）→ 光模块温度升高，发射功率漂移，接近规格下限 → 该小区 ODN 分光比高，光衰本来就接近预算边界（约束五：资源边界的一种）→ 两者叠加，接收端信噪比不足，误码率上升 → OLT 侧判定链路异常，触发掉线。为什么难发现：实验室在常温下测，光衰用标准值，两个因素都不在边界上（约束六：可观测性差——设备也不上报光模块温度）。而且问题只在特定季节、特定时段、特定小区出现（约束四：互操作——还和 OLT 的判定策略有关）。修复代价：如果是硬件光模块选型问题，已出货设备只能返修（约束二：不可逆）。这个案例的价值：它说明为什么嵌入式测试必须做应力组合测试——单独测温度没问题，单独测光衰没问题，两个叠加才出问题。 |
| --- |


## 2.5 本章小结


| 【要点】要点清单1. 七个约束：物理性、不可逆性、时间是一等公民、开放互操作、资源极度稀缺、可观测性天然差、合规是二值闸门。2. 物理问题经常伪装成软件问题。查了很久查不到软件原因时，要主动往下走一层。3. OTA 测试的重点不是“能不能升成功”，而是“升级失败之后会怎样”。变砖率必须是 0。4. 长稳测试的判据是趋势斜率，不是绝对阈值。长稳结束后不要重启，要在“脏状态”下再测一轮。5. 互操作问题的归属靠证据谈判：抓包 + 时序 + 标准条款，三样缺一不可。6. 缺陷密度在资源边界处比在中间高一个数量级。要测边界，更要测超过边界之后的行为。7. 可观测性差不是“测试条件差”，而是产品设计缺陷。可测性需求必须在设计定型前提出。8. 认证是二值闸门且周期以月计，必须在项目立项时锁定排期。9. 最凶的缺陷长在“资源边界 × 时间累积 × 异常路径”的交叉处，而常规功能测试三样都不碰。10. 功能测试是必要不充分条件。针对三交叉区的测试必须被显式地排进计划。 |

## 3.1 三类产品的共同结构

部门在做的三类产品——接入产品（路由器、光猫）、机顶盒、智能中屏音箱——形态差别很大，但它们的系统结构是同构的。理解这个共同结构，你以后换产品线就不会从零开始。


### 3.1.1 六层协同

任何一台嵌入式产品都是六层协同的结果：


| 层 | 内容 | 典型失效 |
| --- | --- | --- |
| 硬件与电源 | SoC、内存、闪存、电源、射频前端、接口 | 纹波、时序、器件老化 |
| 驱动与固件 | 各硬件模块的驱动、bootloader | 初始化失败、寄存器配置错 |
| 操作系统 | Linux / OpenWrt / RDK-B / Android / RTOS | 内存管理、调度、文件系统 |
| 协议与应用 | 网络协议栈、媒体流水线、语音引擎 | 协议实现偏差、状态机缺陷 |
| 网络与云服务 | 运营商网络、CDN、云端 API | 服务异常、变更影响存量设备 |
| 用户与真实环境 | 摆位、干扰、使用习惯、其他设备 | 实验室外推失败 |

注意最后一层。很多人的认知里，测试对象是前四层。但用户实际体验到的是六层叠加的结果，第五、六层出问题时用户投诉的仍然是我们的产品。


### 3.1.2 同一个任务闭环

三类产品都在执行同一个闭环：

输入 → 处理 → 传输 → 输出 → 反馈

差别只在于每一段具体是什么：


| 环节 | 路由器 / 光猫 | 机顶盒 | 中屏音箱 |
| --- | --- | --- | --- |
| 输入 | WAN 侧数据包 / 光信号 | 码流、遥控指令 | 声音、触摸 |
| 处理 | 转发、NAT、QoS | 解密、解复用、解码 | 唤醒、识别、语义理解 |
| 传输 | LAN / 无线 | 内部流水线 / HDMI | 端到云、云到端 |
| 输出 | 终端的网络访问 | 画面 + 声音 | 屏幕 + 语音 + 设备控制 |
| 反馈 | 管理页面、指示灯、云管理 | 界面状态、指示灯 | 语音应答、屏幕显示 |

测试对象是这条链路，不是链路上的某个功能点。这一点在定位问题时尤其重要——现象出现在输出端，原因可能在任何一环。


## 3.2 接入产品：路由器与光猫


### 3.2.1 它到底是什么

很多人把路由器理解成“发 Wi-Fi 的盒子”。这个理解不完整。它同时是三种设备：

- 转发设备——在 WAN 和 LAN、有线和无线之间转发数据包，这是它的本职。
- 协议控制设备——处理 PPPoE 拨号、DHCP、NAT、IPv6 前缀分发、组播、QoS，这些都是有状态的协议逻辑。
- 安全管理设备——它是家庭网络的边界，承担防火墙、访问控制、管理面认证的职责。
光猫（HGU）在结构上和路由器高度相似，差别只在 WAN 侧：路由器的 WAN 是以太网口，光猫的 WAN 是光模块 + PON MAC + OMCI。其余部分——转发、无线、管理——基本一致。

所以这两条产品线的测试方法可以大量复用。


### 3.2.2 系统组成


| 模块 | 作用 | 关注点 |
| --- | --- | --- |
| SoC + DDR + Flash | 计算、内存、存储 | 资源边界、内存泄漏、闪存磨损 |
| WAN PHY | 以太网上联 | 链路协商、大包转发 |
| 光模块 + PON MAC + OMCI | 光接入（光猫形态） | 光功率、注册、OLT 互通 |
| LAN PHY + Switch | 有线下联 | VLAN、环路、表项 |
| Wi-Fi 基带 + RF 前端 + 天线 | 无线收发 | 发射功率、灵敏度、覆盖、干扰 |
| 电源与外围 | 供电、USB、按键、LED | 掉电完整性、指示语义 |
| 系统软件 | Linux/SDK、协议栈 | 转发路径、硬件加速一致性 |
| 管理 | Web/App、TR-069、云管理 | 配置冲突、远管在线率 |


### 3.2.3 真实使用环境

现在回答章首第一个问题：实验室测出覆盖 120 平米，你家为什么有死角？

因为实验室和你家有四个根本差异：


| 差异 | 实验室 | 用户家里 |
| --- | --- | --- |
| 遮挡 | 开阔无遮挡 | 承重墙、金属门、镜子、鱼缸 |
| 距离 | 固定几个点位 | 用户在移动，还会去阳台和卫生间 |
| 信道占用 | 净空 | 邻居十几个 AP，加上自己家二十多台设备 |
| 摆位 | 桌面正中，天线展开 | 弱电箱里、电视柜后、贴着墙角 |

这四条决定了：实验室的数字和用户体验之间，隔着一层不可控因素。


| 【常见错误】那实验室数据还有意义吗有，而且不可替代。但要理解它的作用是什么。实验室数据的价值是可比性：同样的条件下，今天测和明天测一样，A 版本和 B 版本可比，我们和竞品可比。这是判断“改好了还是改坏了”的唯一依据。真实环境测试的价值是外推性：它告诉你用户实际会遇到什么。两者都要做，谁也替代不了谁。只做实验室测试，你会得到一堆漂亮但没用的数字；只做现场测试，你会发现问题却说不清原因，也判断不了改进是否有效。 |

### 3.2.4 典型失效空间

下面这些是接入产品最常见、也最值得先掌握的失效模式。它们都是真实的缺陷模式，不是编出来的：


| 失效模式 | 典型现象 | 为什么容易逃逸 |
| --- | --- | --- |
| 写 Flash 时掉电导致配置损坏 | 反复拉电后配置丢失或启动失败 | 拉电测试常在空闲态做，避开了写窗口 |
| 高温下 Wi-Fi 降功率 | 夏天变慢，实验室复现不出 | 性能测试在常温、空载机箱内进行 |
| PMTU 黑洞 | 能 ping 通但网页打不开 | 连通性测试用小包 ping，掩盖了问题 |
| NAT 会话表耗尽 | P2P 下载时网页打不开 | 测试并发连接数远低于规格上限 |
| IPv6 前缀续租失败 | 运行数天后 IPv6 静默失效 | IPv6 只测初次获址，不测生命周期 |
| 组播组老化超时 | 看电视几分钟一次短暂花屏 | IPTV 测试时长短，低频事件观测不到 |
| 硬件加速绕过 QoS | 限速配置不生效，流量统计不准 | 加速默认开启，从不做开关对比 |
| WPA2/3 过渡模式兼容 | 部分老终端连不上 Wi-Fi | 测试终端集中在新机型 |
| OTA 升级断电变砖 | 升级失败后无法开机 | 断电点选择粗糙，避开了最危险的窗口 |


| 【案例】重点案例：硬件加速的双路径不一致这是接入产品最典型、也最容易被误判为“软件 bug”的一类缺陷，值得单独讲。背景：为了达到高吞吐，路由器会用硬件加速引擎来转发数据包。它的工作方式是：一条连接的首包走软件路径（正常处理各种策略），软件在硬件里建一条表项，后续包由硬件直接转发，不再经过软件。问题在哪：如果硬件表项没有携带完整的策略信息，那么后续包就会绕过 QoS 限速、绕过流量统计、绕过 ALG、甚至绕过部分防火墙规则。用户看到的现象：限速设置了但不生效；流量统计对不上；某些应用的端口映射时灵时不灵。为什么逃逸：加速默认是开启的，测试时也开着，所以你看到的一直是“绕过策略”的那条路径。而现象又表现为功能不正常，大家会往功能模块去查。正确的测试方法：所有涉及策略的用例——QoS、流量统计、ALG、防火墙、端口映射——都必须开加速跑一遍、关加速跑一遍，对比两条路径的行为。不一致的地方要么是缺陷，要么必须有明确的设计说明。 |
| --- |


## 3.3 机顶盒


### 3.3.1 六层流水线

机顶盒的核心是一条媒体处理流水线：

传输 → 解密 → 解复用 → 解码 → 后处理 → 输出


| 环节 | 做什么 | 对应硬件 / 模块 |
| --- | --- | --- |
| 传输 | 把码流从网络或射频拿进来 | Tuner（广播）/ IP 输入 |
| 解密 | 解开内容保护 | DRM / CAS |
| 解复用 | 把音频、视频、数据分离出来 | Demux |
| 解码 | 把压缩码流还原成图像和声音 | 视频解码器、音频解码器 |
| 后处理 | 缩放、HDR 转换、降噪、帧率转换 | 图像处理引擎 |
| 输出 | 送到电视和音响 | HDMI、光纤、模拟音频 |

现在回答章首第二个问题：用户说“电视花屏”，你问哪三个问题？

关键在于每问一个问题，都要能排除掉一层：


| 问题 | 如果回答“是” | 如果回答“否” |
| --- | --- | --- |
| 所有频道都花吗？ | 问题在传输、输出或后处理这些公共环节 | 只有个别频道花 → 问题在内容源或该格式的解码 |
| 换一根 HDMI 线或换一台电视还花吗？ | 问题在盒子内部（解码及以上） | 不花了 → 问题在输出链路或电视兼容 |
| 断网之后播本地文件还花吗？ | 问题在解码或输出 | 不花了 → 问题在传输环节（丢包） |

这就是分层定位。它不是什么高深技巧，本质就是设计一组能切分层次的实验。


| 【提示】为什么"花屏"这个词很危险同一个“花屏”，可能来自完全不同的层：· 网络丢包 → 传输层。表现为块状马赛克，随网络状况波动。· 解码器 bug → 解码层。表现为特定片源必现，换片源就好。· HDMI 链路裕量不足 → 输出层。表现为闪烁、雪花点，和线材、分辨率相关。· 电源纹波 → 物理层。表现为随机、无规律，可能伴随其他模块异常。这四种现象在用户眼里几乎一样，但原因、定位方法和解决方案完全不同。所以接到“花屏”这个描述时，第一件事不是去查代码，而是做分层隔离实验。 |
| --- |


### 3.3.2 外部业务链路

机顶盒还有一条外部链路：

运营商平台 / CDN → 家庭网关 → 机顶盒 → 电视 / 功放

这条链路上的每一环都不完全受我们控制，但出了问题用户投诉的都是机顶盒。所以对机顶盒来说，互操作（约束四）的压力特别大——它要面对的对端包括：

- 电视机——数千款机型，通过 EDID 协商能力、通过 HDCP 做内容保护鉴权、通过 CEC 做联动。
- 功放 / 回音壁——通过 ARC / eARC 回传音频，涉及格式协商和延时补偿。
- 运营商平台——EPG 数据、鉴权、计费、消息推送。
- 内容方——DRM 授权，安全等级不够就不给高清内容。

### 3.3.3 典型失效空间


| 失效模式 | 典型现象 | 为什么容易逃逸 |
| --- | --- | --- |
| EDID 解析异常 | 接某品牌电视黑屏或只能输出 1080p | 实验室电视机型少且都是主流新款 |
| 经 AVR 中继时 HDCP 鉴权失败 | 直连电视正常，接功放后黑屏 | 只测直连，不测中继链路 |
| 高带宽模式链路裕量不足 | 4K HDR 下偶发闪屏、雪点 | 实验室用短的高质量线，用户用长的劣质线 |
| 音画同步漂移 | 刚开始正常，看一小时后对不上嘴 | 同步只在片头看几分钟 |
| 特定编码参数组合下花屏 | 某些片源必花，换片源就好 | 测试码流来自少数样片，维度覆盖不足 |
| 异常码流导致解码器崩溃 | 某个片源播完整机重启 | 测试码流都是正常生成的 |
| 解码器资源泄漏 | 看一晚上后换台黑屏，重启恢复 | 人工换台次数远不足以耗尽资源 |
| 高频换台组播泄漏 | 快速换台后黑屏 | 手工换台频率与次数不足 |
| DRM 安全等级降级 | 某些平台只能看标清 | 只验证“能播”，不验证实际安全等级 |


| 【案例】重点案例：音画同步的时间累积现象：用户反映“看电影时间长了，人物说话对不上嘴”。刚打开时正常。机理：音频和视频用了不同的时钟基准，或者缓冲补偿存在微小的系统性偏差。每一帧偏差可能只有零点几毫秒，肉眼完全不可辨——但它是单调累积的。播放一小时之后，累积误差可能达到几百毫秒，这时候就明显了。为什么逃逸：常规测试打开片源看几分钟，确认“音画同步正常”就过了。而这个缺陷需要连续播放数小时才会显现。正确的测试方法：用带同步标记的标准测试码流，连续播放 4 小时以上，定时测量偏差并画出曲线。判据不是“某一时刻的误差在门限内”，而是“全程无单调漂移趋势”——这又回到了第 2 章讲的趋势判据。延伸：这个案例是“时间累积”维度的典型代表。同类的还有内存泄漏、解码器实例泄漏、缓冲水位漂移。它们的共同特征是：判据必须是趋势，不能是快照。 |
| --- |


## 3.4 智能中屏音箱


### 3.4.1 一条端到端的交互链路

一次语音交互，背后是六个步骤：

采集 → 唤醒 → 识别 → 理解 → 执行 → 反馈


| 步骤 | 在哪里完成 | 失败时用户看到什么 |
| --- | --- | --- |
| 采集 | 端侧（麦克风阵列 + 前端算法） | 叫不醒 |
| 唤醒 | 端侧（本地唤醒模型） | 叫不醒 / 自己乱应答 |
| 识别 | 通常在云端 | 听错了 |
| 理解 | 通常在云端 | 听懂了字但做错了事 |
| 执行 | 云端 + 第三方技能 + 设备 | 没反应 / 执行了别的 |
| 反馈 | 端侧（屏幕 + 扬声器） | 反应慢 / 说的和显示的不一致 |

这六步分属不同的层，定位方法完全不同。用户只会说“不好用”，你需要先判断卡在哪一步：

- 听不见 → 声学、拾音、唤醒（端侧）
- 听不懂 → 识别、语义（云侧）
- 执行错 → 技能、设备控制
- 反馈慢 → 端云时延

### 3.4.2 声学的特殊性

现在回答章首第三个问题：音箱大声放音乐时，能听见你在三米外叫它吗？

先看物理条件：

- 它的麦克风离自己的喇叭只有几厘米。
- 它的麦克风离你有三米。
- 声音强度随距离衰减（自由场下大致按距离平方反比）。
结论是：它自己的音乐到达麦克风时，可能比你的声音大几十倍甚至上百倍。它必须在自己的巨大声音里，把你那点声音捞出来，还要认出这是唤醒词。

这个能力叫回声消除（AEC），配合“打断唤醒”（barge-in），是这个品类技术难度的顶点。


| 【常见错误】实验室最容易绕过的场景常规唤醒测试怎么做？把设备放在安静的房间里，站在几个距离上喊，统计成功率。这个测法系统性地绕开了最难的场景。因为它是在“设备不播放”的状态下测的。实验室测出 98% 的唤醒率，用户在家放着歌喊它，可能只有 60%。正确的做法：barge-in 必须作为独立指标，按播放音量分档测试，且最大音量档必须单独达标。这是这个品类最不能省的一项测试。 |
| --- |


### 3.4.3 这个品类的另一个特殊性：全是概率指标

第 1 章讲过概率型指标要给样本量。中屏音箱把这一点推到了极致：

这个品类没有一个核心指标是布尔值。

- 唤醒率、误唤醒率
- 识别准确率、意图正确率
- 端到端成功率
- 配网成功率、控制成功率
全是分布，不是“能”或“不能”。所以统计能力在这个品类不是加分项，是入场券——不给样本量和置信区间的结论，本质上是噪声。

还有一个特殊之处：两类错误的代价不对称。


| 错误类型 | 用户感受 | 真实性质 |
| --- | --- | --- |
| 漏唤醒（叫了没反应） | 有点烦，多叫一次 | 体验问题 |
| 误唤醒（没叫却应答） | 有点吓人 | 隐私事件——设备在未被呼叫时录音上云 |

这两者在同一条 ROC 曲线上此消彼长：把唤醒门限调松，唤醒率上去了，误唤醒也上去了。所以工作点的选择必须显式论证，不能只优化一边。

而且两者的测量方法完全不同：

- 唤醒率——主动触发，重复 N 次数成功次数。
- 误唤醒率——被动统计，需要长时暴露（播放影视、新闻、日常对话语料，累计上百小时），按“次 / 24 小时”计。

| 【常见错误】一个常见的测量错误“我们重复触发了 500 次，一次误唤醒都没有，误唤醒率是 0。”这句话在测量学上是错的。主动触发测的是唤醒率，测不出误唤醒率——因为误唤醒的定义就是“在没有人叫它的时候被触发”。要测误唤醒，必须让设备在没有人叫它的环境里长时间运行，播放电视剧、新闻、多人对话，统计它自己响了几次。这两件事测的根本不是同一个量。 |
| --- |


### 3.4.4 典型失效空间


| 失效模式 | 典型现象 | 为什么容易逃逸 |
| --- | --- | --- |
| 结构漏声压垮 AEC | 放音乐时几乎叫不醒 | EVT 阶段不测 AEC 相关的结构指标 |
| 麦阵通道一致性超差 | 从某个方向叫就是不理人 | 唤醒测试只在正前方一个点位做 |
| barge-in 失效 | 放歌时怎么喊都不理 | 唤醒测试在不播放状态下进行 |
| 误唤醒偏高 | 半夜自己说话，看电视时插嘴 | 用主动触发的方式“测”误唤醒 |
| 人群覆盖不足 | 小孩叫不醒，老人说方言不识别 | 语料由工程师本人录制 |
| 端点截断 | 话说一半就被打断 | 测试指令都是短促标准句 |
| 断网后几乎全废 | 路由器一重启就啥都干不了 | 测试环境网络永远良好 |
| 闹钟丢失 | 断电或升级后闹钟不响 | 闹钟只做“能设能响”的功能验证 |
| 静音开关可被绕过 | 关了麦还能被唤醒 | 静音只做 UI 层验证 |


## 3.5 三类产品对比

把三类产品放在一起对比，能更清楚地看到各自的难点在哪：


| 维度 | 接入产品 | 机顶盒 | 中屏音箱 |
| --- | --- | --- | --- |
| 输入是什么 | 数据包 / 光信号（确定） | 码流（确定） | 物理声场（不可完全复现） |
| 判定对象 | 通不通、快不快 | 好不好看、好不好听 | 懂没懂 |
| 判据类型 | 多为客观量 | 大量感官量，需转客观 | 几乎全是概率量 |
| 主要对端 | OLT、终端 | 电视、功放、内容方 | 智能家居、云服务 |
| 最难的一关 | 资源边界与时间累积 | 分层定位 | 回声消除与统计判定 |
| 特有的重资产 | 互通实验室 | 码流库、电视机型库 | 声学剖面、人群语料库 |

注意最后一行。测试资产是这三类产品各自的门槛：

- 没有多厂商 OLT，光猫的互通问题只能等到现网爆发。
- 没有维度化的码流库，机顶盒的解码边界就是测试盲区。
- 没有覆盖人群的语料库，音箱的唤醒率数据没有外推价值。
这些资产的建设周期以月计，不是临到测试才准备的东西。


## 3.6 本章小结


| 【要点】要点清单1. 三类产品同构：六层协同、同一个“输入→处理→传输→输出→反馈”闭环。测试对象是链路，不是功能点。2. 路由器同时是转发设备、协议控制设备和安全管理设备。光猫只在 WAN 侧不同，方法可大量复用。3. 实验室与用户家里差四条：遮挡、距离、信道占用、摆位。实验室数据的价值是可比性，现场测试的价值是外推性，两者不可替代。4. 硬件加速的双路径不一致是接入产品的高逃逸缺陷：所有策略类用例必须开/关加速各跑一遍。5. 机顶盒的核心是六层流水线。同一个“花屏”可能来自任意一层，分层定位是第一技能。6. 音画同步会随播放时长单调漂移。判据必须是趋势，不能是快照。7. 中屏音箱的输入是不可完全复现的物理声场；核心难点是回声消除与 barge-in，而实验室常规唤醒测试恰好绕开了它。8. 误唤醒是隐私事件不是体验问题，且必须用长时暴露统计，不能用主动触发来测。9. 三类产品各有重资产：互通实验室、码流库与机型库、声学剖面与语料库。它们定义了输入空间，缺口就是测试盲区。 |

## 4.1 测试流程的九个步骤

一项测试从产生到结束，要走完九步：

需求分析 → 风险识别 → 测试计划 → 测试设计 → 环境准备 → 测试执行 → 缺陷与回归 → 测试报告 → 残余风险评估

很多新人对这九步的第一印象是“一串文档动作”——每一步交一份文档，走完就算完事。这个理解会让你把大量时间花在格式上，而错过每一步真正要解决的问题。

正确的理解是：测试流程是一条证据链。每一步都在产出下一步需要的输入，最终汇成一个能支撑决策的结论。任何一步断掉，后面的结论就没有依据。


### 4.1.1 九步在回答四个子问题

把九步和第 1 章的四个不可约子问题对照，结构就清楚了：


| 流程步骤 | 回答哪个子问题 | 这一步的实质 |
| --- | --- | --- |
| 需求分析、风险识别 | ① 会怎么坏 | 构造失效空间，找出风险点 |
| 测试计划、测试设计、环境准备 | ② 怎么让它坏 | 设计能把系统驱到失效状态的手段 |
| 测试执行、缺陷与回归 | ③ 怎么知道它坏了 | 观测现象并按判据做出判定 |
| 测试报告、残余风险评估 | ④ 这一次说明了什么 | 从测到的推断没测的，给出结论 |

这张表有一个很实用的用途：当你不知道某一步该做到什么程度时，回头问它在回答哪个子问题。

比如“环境准备”要做到什么程度？它服务于第二问（可控性），所以标准是：这个环境能不能把系统驱动到我想验证的那个状态。如果不能，环境就没准备好，哪怕设备都上电了、网线都插好了。


## 4.2 第一步：需求分析

现在回答章首第一个问题：测试工作从哪一步开始？

答案是读需求，不是写用例。

这一点值得强调，因为新人的直觉几乎都是“拿到版本、拿到用例就可以开工了”。但用例写得再漂亮，如果需求理解错了，全部白做——而且是做完之后才发现。


### 4.2.1 从需求到可测试需求

产品需求文档里的一句话，通常离“可以设计测试”还有很远的距离。看章首第二个问题里的那句需求：

路由器断网后能够自动恢复。

这句话读起来很清楚，但你没法照着它设计测试。逐层追问一下：


| 追问 | 为什么这一问不能省 |
| --- | --- |
| “断网”断的是什么？ | 拔 WAN 网线、断光纤、上游服务器不响应、运营商侧抖动——这是四种完全不同的测试，激励方式、恢复机制、耗时都不一样 |
| 断多久？ | 断 1 秒和断 30 分钟，设备的行为可能完全不同（重拨退避、状态机超时） |
| “恢复”怎么算？ | 拨号成功算，还是能打开网页才算？这两者差很远——见过拨号成功但业务不通的情况 |
| 多久内恢复算合格？ | 没有时限就没有判据 |
| 做几次？ | 单次成功不代表可靠。这是概率型指标 |
| 失败率门限是多少？ | 100 次里失败 1 次算不算通过？ |
| 留什么证据？ | 三个月后有人质疑结论，你拿什么证明 |

把这些问题的答案填进去，这条需求才变成可执行的。填的过程有个固定结构，叫可测试需求六要素：


| 要素 | 回答什么 | 本例的答案 |
| --- | --- | --- |
| 对象 | 测哪个设备 / 模块 | 路由器 WAN 侧接入模块 |
| 条件 | 前置状态是什么 | 已完成 PPPoE 拨号并正常上网 10 分钟 |
| 刺激 | 做什么操作 | 拔掉 WAN 网线，保持 60 秒后插回 |
| 指标 | 观察哪个量 | 从插回网线到首个业务报文成功往返的时长 |
| 标准 | 多少算通过 | ≤ 60 秒；重复 100 次，成功率 100% |
| 证据 | 留什么材料 | 抓包文件、恢复时长记录表、失败次数统计 |


| 【提示】六要素不是填表格式，是思维清单有些团队把六要素做成模板让人填，结果就变成了应付格式。它真正的用法是：写完一条用例后，逐项自查有没有漏。漏得最多的两项是“条件”和“证据”。漏了“条件”，别人复现不出来；漏了“证据”，结论无法被质疑也无法被复用。 |
| --- |


### 4.2.2 需求里最危险的三类表述

读需求时，遇到下面三类表述要特别警惕，它们是歧义的高发地：


| 危险表述 | 为什么危险 | 该怎么问 |
| --- | --- | --- |
| “支持 XX” | 支持到什么程度？边界在哪？ | 支持多少个？多大？多快？超过了会怎样？ |
| “正常”“稳定”“流畅” | 纯主观词，无法判定 | 观测量是什么？门限是多少？测多久？ |
| “自动 XX” | 自动的触发条件和失败处理都没定义 | 什么条件下触发？失败了怎么办？会重试吗？ |


## 4.3 第二步：风险识别与优先级

需求拆清楚之后，问题往往不是“不知道该测什么”，而是“要测的太多，测不完”。这时候需要排序。


### 4.3.1 风险的两个维度

风险 = 发生概率 × 影响程度

注意这两个维度是相乘而不是相加。一个必然发生但影响轻微的问题（提示文案有错别字），风险可能低于一个概率很低但影响致命的问题（升级中断导致变砖）。

实际排序时通常用一个 3×3 或 5×5 的矩阵：


|  | 影响：低 | 影响：中 | 影响：高 |
| --- | --- | --- | --- |
| 概率：高 | 中 | 高 | 最高 |
| 概率：中 | 低 | 中 | 高 |
| 概率：低 | 低 | 低 | 中 |

但这个矩阵有一个陷阱：“概率”指的是在用户手里发生的概率，不是在实验室被发现的概率。这两者往往相反——越是实验室不容易发现的，越是在现场大量发生。


### 4.3.2 第三个维度：可检出性

所以更完整的做法是引入第三个维度——可检出性（这也是 FMEA 的标准做法）：

风险优先级 = 发生概率 × 影响程度 × 不可检出性

“不可检出性”衡量的是：如果这个问题真的存在，我们现有的测试手段能不能发现它。越难发现，风险越高，因为它更可能逃逸到市场。


| 【案例】三维评估如何改变结论问题 A：某个配置页面的下拉菜单在特定浏览器下显示错位。概率高（该浏览器占比不低）、影响低（不影响功能）、可检出性高（一眼就能看到）→ 综合优先级：中低。问题 B：设备连续运行超过 49 天后，流量统计计数器回绕导致数值异常。概率中（用户确实会连续跑几个月）、影响中（统计不准，可能影响计费）、可检出性极低（需要连续跑 49 天，或者用注入方式加速才能验证）→ 综合优先级：高。如果只用二维矩阵，B 会排在 A 后面。引入可检出性之后，B 排到了前面——这才是对的，因为 A 一定会在测试阶段被发现，B 大概率会逃逸到现场。 |
| --- |


### 4.3.3 风险识别的输入从哪来

风险不是凭空想的，它有明确的来源：

- 缺陷模式库——历史上出过的问题，最直接的输入。
- 变更点——这一版改了什么？改动的模块及其影响范围是风险最高的地方。
- 新特性——第一次实现的东西，没有历史数据支撑，默认高风险。
- 平台变更——换芯片、换 SDK 版本、换编译器，会引入大量隐性变化。
- 现场反馈——上一批产品在现网出了什么问题。
- 认知盲区——团队里没人熟悉的模块，风险要往上调。

## 4.4 研发阶段与测试重点

现在回答章首第三个问题：EVT 阶段跑三千条功能用例，合理吗？

不合理。要理解为什么，得先看清四个阶段各自在回答什么问题。


### 4.4.1 四个阶段


| 阶段 | 全称 | 核心问题 | 测试重点 |
| --- | --- | --- | --- |
| EVT | 工程验证
Engineering Verification Test | 设计和关键链路是否可行 | 找设计风险与技术边界 |
| DVT | 设计验证
Design Verification Test | 完整设计是否满足质量要求 | 验证全部质量属性与边界 |
| PVT | 生产验证
Production Verification Test | 工艺和量产一致性是否成立 | 批次散差、产线工装与校准 |
| MP | 量产
Mass Production | 变更和现场质量是否受控 | 过程监控、变更回归、现场反馈 |

每个阶段的样本形态、测试环境、出口准则都不同：


| 阶段 | 样本 | 典型数量 | 关键输出 |
| --- | --- | --- | --- |
| EVT | 手工样机、裸板 | 3–10 台 | 指标裕量报告、设计变更建议 |
| DVT | 完整外壳的设计样机 | 20–50 台 | 完整测试报告、缺陷清单 |
| PVT | 试产线按节拍生产的小批量 | 100–500 台 | 一致性报告、CPK 分析 |
| MP | 量产批次 + 现网灰度 | 全检 + 抽检 | 趋势看板、灰度评估 |


### 4.4.2 为什么 EVT 不该跑全量功能用例

EVT 阶段要回答的是“这个方案能不能成”。这时候：

- 硬件方案可能还要改——散热余量不够就要改结构，天线布局不对就要重新布板。
- 芯片选型可能还要换——解码能力不足、射频指标达不到，都可能推倒重来。
- 软件还在搭架子，很多功能根本没实现。
在这种状态下跑三千条功能用例，会有两个后果：大量用例根本跑不通（功能没做完），以及跑通的那些也可能白跑（方案一改全部作废）。

EVT 该做的是验证设计假设——那些一旦不成立就要改硬件的东西：

- 接入产品：射频传导与 OTA 指标裕量、密闭高温下的降频行为、光模块指标（光猫）。
- 机顶盒：最高规格码流的解码能力、HDMI 高带宽模式的链路裕量、DRM 安全等级是否可达。
- 中屏音箱：腔体共振与异音、结构漏声（决定 AEC 有没有工作余量）、麦阵通道一致性、设备自噪声。

| 【常见错误】EVT 阶段最贵的一类失误把“一旦不成立就要改硬件”的验证推迟到 DVT。典型例子：中屏音箱的结构漏声。如果 EVT 不测麦克风端的回声等级，等到 DVT 发现 barge-in 完全达不到指标时，结构早已冻结、模具早已开好。这时候只能靠算法硬扛，而算法通常扛不住——因为物理上信噪比就不够。另一个例子：DRM 安全等级。如果 EVT 不验证等级可达性，等到后期发现只能达到低等级、内容方不给高清授权，产品的核心卖点就没了，而这时候换方案已经来不及。判断标准很简单：问自己“如果这一项不达标，需要改什么？”答案里出现“硬件”“结构”“芯片”的，必须在 EVT 验证。 |
| --- |


### 4.4.3 反过来的失误：PVT 才发现设计缺陷

另一个方向的问题是：DVT 没做透，把设计缺陷带到了 PVT。

PVT 的任务是验证一致性和可制造性——同一个设计做出来的每一台是不是都一样。它默认设计本身已经没问题了。如果这时候还在发现设计缺陷，说明 DVT 失职，而代价是：试产批可能全部报废、量产计划推迟、模具可能要改。

PVT 有一类测试是它专属的，DVT 阶段做不了，也不该省：

- 批次一致性抽测——射频指标、光功率、功耗在不同批次间的散差有多大。
- 产线工装与校准流程验证——工装能不能筛出不良？误判率、漏判率是多少？
- 产线密钥或校准数据注入——这是研发阶段从未走过的路径，也是最典型的逃逸点之一。
- 量产固件复检——研发固件通常开着调试口、关着签名校验，量产配置完全不同，必须用量产固件重新做一遍安全检查。
- 包装跌落与运输振动——必须用量产包装和量产机，DVT 阶段的样机不代表最终形态。

## 4.5 出口准则与残余风险


### 4.5.1 什么是出口准则

每个阶段结束时要回答一个问题：能不能进入下一个阶段。回答这个问题的依据，就是出口准则。

一条好的出口准则和一条好的判定准则一样，必须是可核验的：


| 不好的出口准则 | 好的出口准则 |
| --- | --- |
| 测试基本完成 | 规格项覆盖率 100%，用例执行率 ≥ 98% |
| 质量稳定 | P0/P1 缺陷清零，P2 缺陷收敛趋势连续三周下降 |
| 性能达标 | 各帧长吞吐达标，时延 P99 ≤ 门限，长稳 14 天内存斜率 ≈ 0 |
| 兼容性没问题 | 目标终端清单内关联成功率 100%，未覆盖组合的残余风险已书面说明 |


### 4.5.2 残余风险：测试报告里最重要的一段

这是新人最容易忽略、但资深工程师最看重的一部分。

测试永远不可能穷尽（第 1 章的结论），所以一定有没测到的部分。测试报告的价值不只在于说清“我们测了什么、结果如何”，还在于说清“我们没测什么、那部分风险有多大、为什么可以接受”。


| 【要点】一份完整测试结论的三段式第一段：测了什么。用什么方法、在什么条件下、覆盖了哪些范围。第二段：结果如何。关键指标的数值与判定，缺陷分布，附证据。第三段：还剩什么风险。哪些组合没覆盖、为什么、这部分风险的评估、建议采取的缓解措施（比如灰度发布、现网监控重点、备用回滚方案）。只有第一、二段的报告是不完整的。它把“能不能发货”这个判断隐含地推给了读报告的人，而那个人手上没有你的信息。 |
| --- |

这也解释了为什么第 9 章会说：测试的结论不是“没问题”，而是“我们知道了什么，还有什么不知道”。


## 4.6 本章小结


| 【要点】要点清单1. 测试流程是一条证据链，不是一串文档动作。九个步骤分别在回答四个不可约子问题。2. 不知道某一步该做到什么程度时，回头问它在回答哪个子问题。3. 测试从读需求开始，不是从写用例开始。4. 可测试需求六要素：对象、条件、刺激、指标、标准、证据。漏得最多的是“条件”和“证据”。5. 需求里最危险的三类表述：“支持 XX”、“正常/稳定/流畅”、“自动 XX”。6. 风险 = 概率 × 影响 × 不可检出性。第三个维度会显著改变优先级排序。7. 四个阶段问的问题不同：EVT 验证设计假设，DVT 验证规格与应力，PVT 验证一致性与工艺，MP 维持过程稳定。8. 判断某项测试该不该在 EVT 做：问“如果不达标要改什么”，答案里有硬件、结构、芯片的，必须在 EVT。9. PVT 有专属测试：批次一致性、产线工装、密钥注入、量产固件复检、包装运输。10. 测试结论是三段式：测了什么、结果如何、还剩什么风险。缺第三段的报告是不完整的。 |

# 第 5 章　质量模型与测试视角


| 【先想一想】读正文之前，先自己答一遍问题 1：一个功能全部测试通过的产品，能发货吗？问题 2：还是“路由器断网后自动恢复”这条需求。除了“能不能恢复”，你还能想出几个完全不同的问题？ |

## 5.1 质量包含哪些方面

第 4 章解决了“一项测试怎么从需求中长出来”。但还有一个问题没回答：面对同一条需求，我该从哪些角度去测？

这个问题不能靠灵感回答，需要一个框架。国标 GB/T 25000.10—2016（等同于国际标准 ISO/IEC 25010）给出的产品质量模型，把质量拆成八个属性：


| 质量属性 | 回答什么问题 | 嵌入式产品的具体体现 |
| --- | --- | --- |
| 功能性 | 功能对不对、全不全 | 能上网、能播放、能唤醒 |
| 性能效率 | 够不够快、够不够省 | 吞吐、时延、并发数、功耗 |
| 兼容性 | 能不能和别的东西一起工作 | 终端兼容、OLT 互通、电视兼容 |
| 易用性 | 用户会不会用、看不看得懂 | 配网引导、指示灯语义、错误提示 |
| 可靠性 | 会不会坏、坏了能不能恢复 | 长稳、掉线率、异常恢复、防砖 |
| 安全性 | 会不会被攻破、数据安不安全 | 固件安全、管理面鉴权、隐私边界 |
| 可维护性 | 出了问题好不好查、好不好改 | 日志、状态导出、模块化程度 |
| 可移植性 | 换个环境还能不能用 | 跨芯片平台、跨系统版本、跨运营商 |

现在可以回答章首第一个问题了：不能。功能全部通过，只说明八个属性里的第一个达标。

剩下七个里，任何一个塌了都可能导致不能发货：

- 性能不达标——用户觉得慢，投诉率上升，运营商验收不通过。
- 兼容性不过——某品牌手机连不上，那个品牌的用户全部流失。
- 可靠性不行——用一周就要重启，退货率飙升。
- 安全性不过——认证过不了，直接不能卖。

### 5.1.1 为什么这四个属性是重点

八个属性并非同等重要。对嵌入式产品来说，性能效率、兼容性、可靠性、安全性这四个是重中之重，原因和第 2 章的七个约束直接相关：


| 属性 | 为什么在嵌入式上格外重要 | 关联约束 |
| --- | --- | --- |
| 性能效率 | 资源极度稀缺，性能余量小，容易触碰边界 | 约束五 |
| 兼容性 | 对端不受控且数量巨大，正确性是相对定义的 | 约束四 |
| 可靠性 | 要连续跑三到五年，且硬件不可回滚 | 约束二、三 |
| 安全性 | 合规是二值闸门，且设备位于家庭网络内部 | 约束七 |


## 5.2 从质量属性到测试类型

质量属性是抽象的要求，测试类型是可执行的活动。两者之间是一一映射的关系：


| 质量属性 | 对应测试类型 | 典型手段 |
| --- | --- | --- |
| 功能性 | 功能测试 | 等价类、边界值、状态迁移、场景法 |
| 性能效率 | 性能测试 | 负载模型、基准测试、分位数统计 |
| 兼容性 | 兼容性测试 | 矩阵设计、pairwise、市占加权削减 |
| 可靠性 | 稳定性与可靠性测试 | 长稳、老化、故障注入、加速试验 |
| 安全性 | 安全测试 | 攻击面分析、扫描、手工渗透、固件核查 |
| 易用性 | 易用性测试 | 场景走查、首次使用体验、无障碍核查 |
| 可维护性 | （贯穿在其他测试中） | 可测性评审、日志与状态导出核查 |
| 可移植性 | 移植性 / 平台兼容测试 | 跨平台回归、版本升级验证 |


| 【提示】为什么可维护性没有独立的测试类型可维护性衡量的是“出了问题好不好查、好不好改”。它没法通过一轮专门的测试来验证，而是体现在日常测试的过程中。判断方法很直接：你在定位缺陷时，有没有反复遇到“看不到内部状态”“日志没记录”“无法复现”这类障碍？如果有，那就是可维护性不足。所以可维护性的产出形式是可测性需求（DFT）——把这些障碍转化成对设计的要求，在评审阶段提出来。这一点第 2 章约束六里讲过。 |
| --- |


## 5.3 测试要能落地，还需要四个支撑

知道该测什么，不等于测得成。任何一项测试要真正执行，都需要四样东西：


| 支撑 | 缺了它会怎样 | 嵌入式产品的特殊挑战 |
| --- | --- | --- |
| 环境 | 没法把系统驱到目标状态 | 需要屏蔽房、恒温箱、程控电源、损伤仪 |
| 工具 | 没法观测或没法施加激励 | 仪器昂贵、需要专门培训、部分要自研 |
| 数据 | 没有合适的输入 | 码流库、语料库、异常报文集，都是重资产 |
| 判定 | 有结果但不知道算不算通过 | 大量感官量与概率量，判据难定义 |

这四样里，判定最容易被忽略，数据最容易被低估。


### 5.3.1 数据为什么是重资产

“数据”这一项在互联网测试里通常不难——造几条测试数据、准备几个账号就行。但在嵌入式产品上，输入数据本身就是一个庞大的工程：

- 机顶盒的码流库——需要按编码格式 × 档次 × 分辨率 × 帧率 × 位深 × 色度采样 × GOP 结构 × HDR 元数据等维度覆盖。缺哪个维度，那个维度就是测试盲区。
- 中屏音箱的语料库——需要覆盖年龄、性别、口音、语速、音量等人群维度。用工程师自己录的普通话语料测出来的唤醒率，没有外推价值。
- 接入产品的异常报文集——构造截断的、字段非法的、超规格的报文，用来验证协议栈的鲁棒性。
这些资产的建设周期以月计，而且需要持续维护（新编码格式出来了、新机型上市了、新口音要覆盖了）。它们定义了测试的输入空间，输入空间残缺，后面所有测试的结论都不完整。


## 5.4 同一个需求的多个视角

现在回答章首第二个问题。还是那条“路由器断网后自动恢复”，从六个视角看，会得到六个完全不同的问题：


| 视角 | 问题 | 为什么这个角度不能省 |
| --- | --- | --- |
| 功能 | 能不能恢复？ | 最基本的要求 |
| 性能 | 多久恢复？P95 是多少？ | 用户对时长敏感；均值会掩盖长尾 |
| 可靠 | 反复断网两百次，还都能恢复吗？ | 单次成功不代表可靠；重拨退避可能有缺陷 |
| 兼容 | 接不同厂商的光猫，表现一致吗？ | 上游设备实现有差异（约束四） |
| 易用 | 恢复的这两分钟，用户看到什么？ | 用户可能以为坏了，去按复位键，反而更糟 |
| 安全 | 恢复过程中配置会被重置吗？ | 如果重置成默认密码，就是安全事件 |

这六个视角地位平等，不分主次。而且它们中的每一个，都可能独立地导致产品不可用：

- 性能差——恢复要 5 分钟，用户早就重启了。
- 可靠性差——前 10 次都能恢复，第 11 次卡死。
- 兼容性差——接 A 厂商光猫正常，接 B 厂商永远恢复不了。
- 易用性差——恢复过程中指示灯一直红色，用户以为坏了直接退货。
- 安全性差——恢复后配置被重置，Wi-Fi 变成开放网络。

| 【案例】一个只测功能导致的真实后果场景：某型号路由器的“断网自动恢复”功能验收通过——测了 5 次，每次都在 40 秒内恢复。现场表现：批量出货后，客服接到大量投诉“网断了自己好不了”。真因：重拨采用固定间隔重试，且没有次数上限。当运营商侧出现短时故障、大量设备同时重拨时，认证服务器被打满，导致所有设备都拨不上——而且因为固定间隔重试，这个状态会一直持续，形成重拨风暴。为什么漏掉：功能视角只问“能不能恢复”，测的是单台设备、上游正常的场景。哪个视角能抓到：可靠性视角——反复断网并观察重拨行为，会发现没有指数退避；以及兼容性视角——模拟上游服务器异常（拒绝、超时、间歇故障），会发现设备的应对策略有问题。 |
| --- |


### 5.4.1 一个实用的自检方法

写完一组用例之后，用这张表自检，看有没有整个视角被漏掉：


| 自检问题 | 如果答不上来 |
| --- | --- |
| 这个功能慢的时候用户会怎样？ | 漏了性能视角 |
| 重复做一千次还成立吗？ | 漏了可靠性视角 |
| 换个对端设备 / 平台还成立吗？ | 漏了兼容性视角 |
| 用户看得懂当前发生了什么吗？ | 漏了易用性视角 |
| 这个过程中有没有暴露什么、丢失什么？ | 漏了安全性视角 |
| 出了问题我能查到原因吗？ | 漏了可维护性视角 |


## 5.5 视角与阶段的组合

把第 4 章的阶段和本章的视角放在一起，能得到一张更实用的表——同一个视角在不同阶段的重点是不同的：


| 视角 | EVT | DVT | PVT / MP |
| --- | --- | --- | --- |
| 性能 | 摸底能力上限与裕量 | 全量指标、边界、分位数 | 批次一致性、现网趋势 |
| 兼容 | 摸底主流对端（少量） | 按市占加权全量矩阵 | 新机型 / 新版本回归 |
| 可靠 | 关键应力摸底 | 长稳、老化、故障注入 | 现场失效数据回流 |
| 安全 | 安全等级可达性验证 | 攻击面全覆盖 | 量产固件复检 |
| 易用 | — | 场景走查、无障碍 | 现场反馈 |

注意 PVT 阶段的“量产固件复检”被特别标出——这是第 4 章讲过的高逃逸点，值得重复强调。


## 5.6 本章小结


| 【要点】要点清单1. 产品质量有八个属性：功能性、性能效率、兼容性、易用性、可靠性、安全性、可维护性、可移植性。功能全通过只代表第一个达标。2. 对嵌入式产品，性能效率、兼容性、可靠性、安全性是重中之重，原因直接对应七个约束。3. 质量属性 → 测试类型是一一映射。可维护性没有独立测试类型，它的产出形式是可测性需求（DFT）。4. 测试落地需要四个支撑：环境、工具、数据、判定。判定最容易被忽略，数据最容易被低估。5. 码流库、语料库、异常报文集是重资产，建设周期以月计。它们定义输入空间，缺口就是测试盲区。6. 同一个需求可以从六个视角提出六个完全不同的问题，且这六个视角地位平等。7. 每个视角都可能独立导致产品不可用。只测功能视角会漏掉重拨风暴这类问题。8. 用六个自检问题检查有没有整个视角被漏掉。9. 同一视角在不同阶段的重点不同。EVT 摸底、DVT 全量、PVT 一致性、MP 趋势。 |

## 6.1 性能测试的第一性原理


### 6.1.1 三个基本要素

性能测试的本质很简单：给系统施加负载，观察它的能力、资源和退化。


| 要素 | 是什么 | 路由器上的例子 |
| --- | --- | --- |
| 输入负载 | 你施加给系统的压力 | 帧长、速率、终端数、业务类型 |
| 输出指标 | 系统表现出来的能力 | 吞吐量、时延、抖动、丢包 |
| 系统资源 | 系统内部的消耗状态 | CPU、内存、温度、无线重传 |

很多人只关注中间那一项——输出指标。这是不够的，因为只看输出指标，你只能知道“现在行不行”，不能知道“为什么行/不行”以及“再加压会怎样”。


### 6.1.2 四个区间

现在回答章首第一个问题。大多数人画的曲线是“先线性上升，然后拉平”。实际的曲线是这样的：


| 区间 | 吞吐量表现 | 时延表现 | 系统状态 |
| --- | --- | --- | --- |
| 有余量 | 随负载线性上升 | 平稳且低 | 资源充裕，来多少处理多少 |
| 排队 | 上升变缓 | 开始上升 | 队列开始积压，但还能消化 |
| 饱和 | 达到平台，不再增加 | 急剧上升 | 处理能力已到上限 |
| 失效 | 开始下降 | 极高或超时 | 资源被重传、超时、排队消耗 |

关键在最后一段：进入失效区之后，吞吐量会往下掉，而不是维持在平台。

原因是：系统进入过载后，要花越来越多的资源去处理重传、超时重连、队列管理，真正用于有效转发的资源反而减少了。这在网络设备上叫“活锁”或“拥塞崩溃”，在其他系统上也有类似现象。


| 【要点】性能测试的目标不是测一个最大值如果目标只是“测出最大吞吐 1.8G”，那你只需要在饱和点测一次。但真正有价值的信息是：系统是怎么一步步走向边界的。· 余量区有多宽？（决定日常使用的舒适度）· 排队区的时延上升有多陡？（决定用户什么时候开始感觉“卡”）· 饱和点在哪？（决定容量规划）· 过载后会不会崩？能不能自动恢复？（决定异常情况下的表现）最后一条尤其重要，而且最少被测。 |
| --- |


### 6.1.3 资源曲线为什么必须同步采集

性能测试时必须同步采集资源数据（CPU、内存、温度、重传），原因有两个：

第一，资源是先行指标。性能开始下降之前，资源一定先有征兆。看到 CPU 已经打满、温度已经接近降频阈值，你就知道后面会发生什么。

第二，资源数据是定位的起点。吞吐上不去，可能是 CPU 瓶颈、可能是内存带宽瓶颈、可能是温度降频、可能是无线侧重传太多。这四种原因的解决方案完全不同，而区分它们只能靠资源数据。


| 【案例】一条被误判的性能结论现象：某路由器性能测试，前 10 分钟吞吐稳定在 1.6G，30 分钟后掉到 1.1G。测试人员判定“性能不稳定，存在性能衰减缺陷”，提给研发。研发查了两周软件，没发现问题。真因：设备放在密闭的测试机柜里，30 分钟后 SoC 结温达到阈值，触发降频保护。CPU 频率从 1.5GHz 降到 1.0GHz，转发能力随之下降。为什么会误判：测试只记录了吞吐量，没有同步采集温度和 CPU 频率。而降频这件事设备既不上报也不记日志（约束六：可观测性差）。教训有两条：一、性能测试必须同步采集资源数据，缺了它结论可能完全指错方向。二、“频率和温度可读”应该作为可测性需求在设计阶段提出——这正是第 2 章讲的 DFT。 |
| --- |


## 6.2 性能指标地图

性能不是一个数字，是一组指标。以路由器为例：


### 6.2.1 输出指标


| 指标 | 含义 | 为什么重要 |
| --- | --- | --- |
| 吞吐量 | 单位时间能转发多少数据 | 最基本的能力指标 |
| 时延 | 数据从进到出要多久 | 决定游戏、会议、SSH 的体验 |
| 抖动 | 时延的波动幅度 | 决定音视频是否流畅 |
| 丢包率 | 有多少数据丢失 | 直接影响所有业务 |
| 并发连接数 | 能同时维持多少条会话 | P2P、多设备场景的边界 |
| 无线覆盖 | 在多远/多少衰减下还能用 | 用户最直观的体验 |
| 漫游 | 在多个 AP 之间切换的表现 | 决定移动中的体验 |
| 长时间稳定性 | 跑很久之后指标会不会劣化 | 决定几周后用户的感受 |

最后两项最容易被忽略，因为它们需要额外的时间和场景才能测到。而恰恰是它们，对应着第 2 章讲的“时间累积”维度。


### 6.2.2 输入条件

现在回答章首第二个问题。听到“跑到 1.8G”，至少要追问六件事：


| 追问 | 为什么这一问是必要的 |
| --- | --- |
| 帧长多少？ | 64 字节和 1518 字节，结果可能差好几倍 |
| 几个终端？ | 单终端和 30 终端并发是两个世界 |
| 多远？有没有墙？ | 无线性能随距离和遮挡剧烈变化 |
| 开没开加密？ | 加解密有额外开销，尤其在弱 CPU 上 |
| 上行、下行还是双向？ | 双向吞吐通常远低于单向之和 |
| 跑了多久？ | 峰值 1.8G，稳态可能只有 1.2G |

性能结果必须与测试条件一起解释。脱离条件的数字，没有意义。

这句话是本章最重要的一条纪律。它有一个直接推论：任何性能报告，条件描述的篇幅应该不少于结果本身。


## 6.3 RFC 2544：有线转发的基准方法


### 6.3.1 它要解决什么问题

RFC 2544 是 IETF 发布的网络互连设备基准测试方法。它要解决的核心问题是：

如何让不同设备、不同时间、不同地点的转发性能测试结果，可以互相比较。

注意关键词是可比较，不是“测出最大值”。它的全部设计——固定拓扑、固定变量、固定流程——都是围绕可重复性展开的。


### 6.3.2 基本拓扑

测试仪发送端 → 被测设备（DUT） → 测试仪接收端 → （统计回送发送端）

为什么要形成闭环？因为接收端需要把统计结果（收到多少帧、丢了多少、时延多少）反馈给发送端，才能完成一轮判定并决定下一轮的参数。

在这个拓扑上，有四个可控变量：


| 变量 | 典型取值 | 作用 |
| --- | --- | --- |
| 帧长 | 64 / 128 / 256 / 512 / 1024 / 1280 / 1518 字节 | 考察不同负载特性下的能力 |
| 发送速率 | 从 0 到线速的百分比 | 施加不同强度的压力 |
| 流量方向 | 单向 / 双向 | 双向会显著增加处理压力 |
| 测试时长 | 建议单次不少于 60 秒 | 太短会受启动瞬态影响 |


### 6.3.3 五项核心测试


| 测试项 | 测什么 | 结论用于 |
| --- | --- | --- |
| 吞吐量
Throughput | 最大的无丢包转发速率 | 容量规划、规格标称 |
| 时延
Latency | 在吞吐量速率下的转发时延 | 实时业务的可行性判断 |
| 帧丢失率
Frame Loss Rate | 各速率档位下的丢包比例 | 过载行为的评估 |
| 背靠背帧
Back-to-back Frames | 最小帧间隔连续发送时能承受的突发长度 | 缓冲能力评估 |
| 系统与复位恢复
System / Reset Recovery | 过载或复位后恢复正常转发的时间 | 异常恢复能力 |

新人最常只做第一项（吞吐量）。但后三项其实更能反映设备的健壮性——尤其是帧丢失率和系统恢复，它们描述的是“过载时会怎样”，正好对应 6.1.2 里的失效区。


### 6.3.4 吞吐量的二分逼近算法

吞吐量的定义是“最大的无丢包转发速率”。怎么找到它？靠逐步逼近。

典型的工程实现是这样的：

- 选定一个帧长（每个帧长要独立测一遍）。
- 设置初始负载，通常从 100% 线速开始。
- 发送流量，持续规定时长（如 60 秒）。
- 检查是否丢包。
- 无丢包 → 说明还有余量，提高负载；有丢包 → 说明超了，降低负载。
- 每一轮把搜索区间减半，逐步收敛。
- 当区间宽度小于精度要求时停止，输出最大无丢包速率。
走一个具体的例子（精度要求 1%）：


| 轮次 | 负载 | 结果 | 搜索区间变化 |
| --- | --- | --- | --- |
| 第 1 轮 | 100% | 丢包 | [0%, 100%] → 取中点 |
| 第 2 轮 | 50% | 无丢包 | [50%, 100%] → 取中点 |
| 第 3 轮 | 75% | 丢包 | [50%, 75%] → 取中点 |
| 第 4 轮 | 63% | 无丢包 | [63%, 75%] → 取中点 |
| 第 5 轮 | 69% | 丢包 | [63%, 69%] |
| …… | …… | …… | 继续收敛至区间 < 1% |
| 结论 | 约 63% | 最大无丢包速率 | — |


| 【提示】关于这个算法的三点说明第一，这是典型实现，不是 RFC 唯一规定的算法。RFC 2544 定义的是测试方法和判定标准，具体的搜索策略各家仪器实现有差异。所以跨仪器比较结果时要注意这一点。第二，每个帧长都要独立跑一遍完整的逼近过程。7 个帧长 × 双向 × 每轮 60 秒 × 十几轮，时间成本很可观。这就是为什么完整的 RFC 2544 测试常常要跑几个小时。第三，精度不是越高越好。精度从 1% 提到 0.1%，迭代次数增加，总时长成倍上升。什么时候值得？认证送测、竞品对标、合同验收——这些场景数字要能站得住。日常回归不需要，你只是想知道“这版有没有掉”，1% 足够。 |
| --- |


### 6.3.5 帧长为什么这么重要

很多人的直觉是“大包更考验设备”，因为数据量大。这个直觉是反的。

关键在于：设备每收到一个包，都要做一系列固定开销的工作——查转发表、修改包头、做转发决策、更新统计。这些开销和包的大小基本无关。

算一笔账：在 1Gbps 线速下，


| 帧长 | 每秒包数（约） | 单包处理预算 |
| --- | --- | --- |
| 64 字节 | 1,488,000 pps | 约 672 纳秒 |
| 512 字节 | 234,962 pps | 约 4.3 微秒 |
| 1518 字节 | 81,274 pps | 约 12.3 微秒 |

小包的包数是大包的 18 倍，每个包的处理预算只有大包的 1/18。所以小包考验的是包处理能力（PPS），大包考验的才是带宽（bps）。

实际结果是：很多设备大包能跑满线速，小包只能跑到线速的百分之几十。这两个数字都是真的，但它们回答的是不同的问题。


| 【常见错误】只报一个数字是不负责任的性能报告里写“吞吐量 940Mbps”是不完整的。正确的写法是给出各帧长的完整结果：64B：420Mbps ｜ 128B：680Mbps ｜ 512B：930Mbps ｜ 1518B：941Mbps读的人才能判断这个设备适不适合自己的业务场景——大量小包的场景（如游戏、VoIP、DNS）看小包能力，大文件传输场景看大包能力。 |
| --- |


### 6.3.6 RFC 2544 答不了什么

这是最重要的一节。任何方法都有边界，说清边界比说清能力更重要。


| RFC 2544 能回答 | RFC 2544 答不了 |
| --- | --- |
| 有线转发的吞吐量基准 | 家庭环境的无线覆盖 |
| 转发时延与抖动 | 多终端并发时的体验 |
| 各速率下的帧丢失率 | 终端在房间之间移动时的漫游表现 |
| 突发流量的承受能力 | 有干扰环境下的实际表现 |
| 过载与复位后的恢复时间 | 真实业务（视频、游戏、会议）的质量 |

根本原因是：RFC 2544 测的是“设备作为转发单元”的能力，不是“设备在家庭环境中作为服务提供者”的能力。前者是后者的必要条件，但远不是充分条件。


## 6.4 TR-398：可控射频环境下的 Wi-Fi 性能


### 6.4.1 它要解决什么问题

无线性能测试有一个 RFC 2544 没有的麻烦：射频环境不可控。

在办公室测 Wi-Fi，今天测出 800Mbps，明天测出 600Mbps。是版本改坏了？还是隔壁开会人多了？还是有人打开了新的热点？你分不清。

TR-398（宽带论坛发布的 Wi-Fi 性能测试方法）要解决的就是这个问题：

通过控制射频路径，让不同设备的 Wi-Fi 性能可以被重复比较。


| 【要点】屏蔽房买的不是"干净"，是"可重复"很多人以为建屏蔽房是为了“没有干扰”。这只说对了一半。更重要的是可重复：射频路径通过可编程衰减器连接，衰减值设成 40dB 就是 40dB，今天和明天一样，深圳和西安一样。有了可重复，才能做三件事：判断改动是否有效（A/B 版本对比）、与竞品对标、跨团队交接测试结论。而且屏蔽房里可以主动注入受控的干扰——这比“碰运气遇到干扰”有价值得多。 |
| --- |


### 6.4.2 典型测试环境组成


| 组成 | 作用 |
| --- | --- |
| 屏蔽房 / 屏蔽箱 | 隔绝外部干扰，提供可控的射频空间 |
| 被测设备（DUT） | 待测的路由器或 AP |
| 参考终端（STA） | 标准化的客户端，避免终端差异引入变量 |
| 可编程衰减器 | 把“距离”变成可精确设置的数字 |
| 流量发生器 | 产生规定特性的业务流量 |
| 干扰源 | 注入受控的同频或邻频干扰 |
| Mesh 子节点 | 用于组网与漫游场景 |


### 6.4.3 六类重点场景


| 场景类别 | 测什么 | 对应的用户体验 |
| --- | --- | --- |
| 基础射频与能力 | 发射功率、接收灵敏度、支持的特性 | 产品的物理能力上限 |
| 吞吐与时延 | 各衰减档位下的速率与时延 | 不同距离下的快慢 |
| 覆盖与空间一致性 | 不同方向、不同衰减下的表现 | 家里各个房间的信号 |
| 多终端性能 | 多个终端并发时的总吞吐与公平性 | 人多时会不会卡 |
| 稳定性与共存 | 长时间运行、与其他协议共存 | 长期使用的可靠性 |
| Mesh 与漫游 | 组网拓扑、回程带宽、切换表现 | 大户型的组网体验 |


### 6.4.4 TR-398 的边界

TR-398 解决了可重复性，但它仍然是实验室方法：

- 它用参考终端，而用户家里是各种品牌、各种年代的终端混杂。
- 它的干扰是受控注入的，而真实环境的干扰是随机、时变的。
- 它测的是链路能力，不直接回答“视频会议卡不卡”。
- 它的场景是标准化的，不完全对应真实户型和摆位。

## 6.5 WAA：从链路能力到业务体验


### 6.5.1 它补的是哪一块

现在回答章首第三个问题：测速 500M，为什么视频会议还是卡？


|  | 测速软件测的 | 视频会议需要的 |
| --- | --- | --- |
| 方向 | 主要是下行 | 持续的上行（你的画面要传出去） |
| 时长 | 瞬时峰值（几秒） | 持续稳定（整场会议） |
| 关键指标 | 峰值带宽 | 低时延 + 低抖动 + 低丢包 |
| 并发 | 单流独占 | 与家里其他设备竞争 |

四个维度全都不同。所以“测速很快但会议卡”一点都不矛盾——它们测的根本不是同一件事。

速率不代表体验。

这就是 WAA（Wi-Fi 联盟的家庭 Wi-Fi 性能评估方法）要补的那一块：它把评估对象从“链路能力”拉到“家庭业务体验”。


### 6.5.2 关注点


| 关注点 | 具体内容 |
| --- | --- |
| 单设备与组网性能 | 单路由与 Mesh 组网两种拓扑下的表现 |
| 多频并发 | 2.4G / 5G / 6G 同时工作时的总体表现 |
| 多终端业务 | 多个终端同时跑不同业务时的公平性与体验 |
| 时变干扰 | 干扰强度随时间变化时的适应能力 |
| MLO 能力 | 多链路同时工作的收益与稳定性 |
| 漫游与组网 | 终端移动过程中的切换质量 |
| 家庭应用体验 | 视频、游戏、会议、下载等真实业务的质量 |

注意最后一行——它是前面所有指标的汇聚点。WAA 的逻辑是：所有的技术指标，最终都要落到“家里的业务能不能正常跑”上。


## 6.6 三类方法如何选择

三套方法不是替代关系，是递进关系：


| 方法 | 主要回答的问题 | 适用范围 | 典型场景 |
| --- | --- | --- | --- |
| RFC 2544 | 有线转发基准如何 | 最窄，最可比 | 规格标称、芯片能力评估、回归基线 |
| TR-398 | 可控射频条件下 Wi-Fi 能力如何 | 中等 | 版本对比、竞品对标、运营商测评 |
| WAA | 家庭场景中的业务体验如何 | 最宽，最贴近真实 | 产品竞争力评估、体验优化验证 |

选择的原则很简单：看你要回答什么问题。

- 要判断“这次改动有没有让转发能力变差” → RFC 2544（可比性最强）。
- 要判断“我们的 Wi-Fi 能力和竞品比如何” → TR-398（有标准化的对比基线）。
- 要判断“用户在家里会不会觉得卡” → WAA（最接近真实体验）。

| 【要点】一句需要背下来的话半年后你能独立干活了，项目经理问你：“我们的性能测过了吗？”“测过了”是不合格的回答——对方听完还是不知道该不该放心。合格的回答是三句话：一、用什么方法测的。RFC 2544 的有线基准？TR-398 的可控无线？还是 WAA 的业务体验？二、在什么条件下。帧长、终端数、距离、加密、时长。三、这个方法覆盖不到什么。比如做了 RFC 2544，那家庭覆盖、漫游、多终端体验都还没有结论。第三句最重要，也是最少人说的。它决定了对方能不能做出正确的决策。 |
| --- |


## 6.7 性能测试的六个常见陷阱

这一节把新人最容易踩的坑集中列出来。


| 陷阱 | 为什么错 | 正确做法 |
| --- | --- | --- |
| 只报均值 | 均值掩盖长尾。用户感知到的“卡”往往是 P99 的那一小部分 | 报告 P50 / P95 / P99，并给出抖动 |
| 只测峰值 | 峰值 1.8G，稳态可能只有 1.2G | 取稳态值（至少持续 2 小时后） |
| 只测规格内 | 不知道超限后会崩还是会降级 | 压到规格的 1.5 倍，观察过载行为与恢复 |
| 不采集资源 | 结论可能完全指错方向（见 6.1.3 案例） | 同步采集 CPU、内存、温度、重传 |
| 只测单终端 | 并发下的公平性问题完全暴露不出来 | 按真实场景构造多终端并发剖面 |
| 条件不记录 | 结果不可复现，也不可比较 | 条件描述的篇幅不少于结果本身 |


### 6.7.1 关于分位数，多说两句

“只报均值”是最普遍的陷阱，值得展开。

假设一次时延测试采集了 10000 个样本：


| 统计量 | 数值 | 含义 |
| --- | --- | --- |
| 均值 | 12 ms | 平均而言的时延 |
| P50（中位数） | 9 ms | 一半的请求快于 9ms |
| P95 | 28 ms | 5% 的请求慢于 28ms |
| P99 | 340 ms | 1% 的请求慢于 340ms |

均值 12ms 看起来非常好。但 P99 是 340ms——这意味着每 100 个请求就有 1 个会让用户明显感觉到卡顿。

在游戏、语音通话、实时会议这类场景下，用户感知到的不是平均值，而是最差的那一部分。1% 的严重卡顿，足以让用户觉得“这网络不行”。

所以性能验收的判据应该写成“P99 时延 ≤ X ms”，而不是“平均时延 ≤ X ms”。


## 6.8 本章小结


| 【要点】要点清单1. 性能测试三要素：输入负载、输出指标、系统资源。只看输出指标是不够的。2. 系统经历四个区间：有余量 → 排队 → 饱和 → 失效。失效区吞吐会下降而不是维持平台。3. 性能测试的目标不是测一个最大值，而是看清系统如何走向边界，尤其是过载后能不能恢复。4. 资源数据必须同步采集：它是先行指标，也是定位的起点。5. 脱离条件的性能数字没有意义。听到“跑到 1.8G”要追问帧长、终端数、距离、加密、方向、时长。6. RFC 2544 的价值来自可重复，不是数字大。五项测试：吞吐、时延、帧丢失率、背靠背帧、系统恢复。7. 吞吐量用二分逼近找“最大无丢包速率”。每个帧长独立跑一遍。精度提高，成本成倍上升。8. 小包考验包处理能力（PPS），大包考验带宽（bps）。只报一个吞吐数字是不负责任的。9. TR-398 通过可编程衰减器把“距离”变成可设置的数字，屏蔽房买的是“可重复”而非“干净”。10. WAA 关注家庭业务体验。速率不代表体验——测速看峰值下行，会议看持续上行与时延稳定性。11. 被问“性能测过了吗”，要回答三句：用什么方法、在什么条件下、这个方法覆盖不到什么。12. 六个常见陷阱：只报均值、只测峰值、只测规格内、不采集资源、只测单终端、条件不记录。 |

- A. 大包数据量大，更考验设备转发能力

- C. 12ms 这个数值太高

- C. “用 RFC 2544 测了有线转发基准，各帧长结果如下……；这个方法覆盖不到无线覆盖、多终端体验和漫游，那部分还没有结论。”
- D. “还没测完，下周给你结果。”
6-6 关于 TR-398 中可编程衰减器的作用，下列理解哪一项最准确？

- A. 用来削弱信号，模拟信号差的场景
- B. 把“距离”变成可精确设置、可重复的参数，使不同时间地点的测试结果可比

### 三、动手任务

6-10 用你手上能拿到的工具（哪怕只是手机测速软件 + 一台路由器），做一次简化的性能观察：

- 在同一位置连续测 20 次，记录每次的结果。
- 算出均值、最大值、最小值，并按从小到大排序找出第 19 个值（近似 P95）。
- 比较均值和 P95 的差距。
- 然后换一个位置（隔一堵墙），重复上述过程。
- 最后写一段“性能结论”，要求包含：用什么方法测的、在什么条件下、这个方法覆盖不到什么。
这个任务的重点不是数字本身，而是让你体会：同一台设备，条件一变结论就变；而只报一个均值，会丢掉多少信息。

## 7.1 兼容性测试


### 7.1.1 兼容对象有多大

第 2 章讲过约束四：正确性是相对于对端定义的。兼容性测试要做的，就是验证产品能不能进入真实的终端生态。

先看这个生态有多大：


| 产品线 | 主要兼容对象 | 数量级 |
| --- | --- | --- |
| 接入产品 | 手机、电脑、电视、游戏机、IoT 设备、浏览器、管理 App、上游光猫与 OLT | 终端上千款，OLT 数家 × 多版本 |
| 机顶盒 | 电视机、功放/回音壁、遥控器、运营商平台、内容源 | 电视数千款机型 |
| 中屏音箱 | 路由器、智能家居设备、第三方技能、云服务 | 路由器数百款，技能持续增加 |

而每一类对象内部还要再乘几个维度：

- 操作系统与版本——同一款手机，Android 12 和 Android 14 的行为可能不同。
- 芯片平台——不同 Wi-Fi 芯片对协议可选项的实现差异很大。
- 安全模式——WPA2、WPA3、过渡模式，老终端在过渡模式下经常连不上。
- 年代——三年前的机型和今年的新机，支持的特性完全不同。
乘起来是几千到几万种组合。穷举在数学上就不可能。


### 7.1.2 五条削减依据

现在回答章首第一个问题：只能选 10 台，怎么选？

大多数人的第一反应是“选销量最高的”。这个方向对，但只是五条依据中的一条：


| 依据 | 怎么用 | 为什么有效 |
| --- | --- | --- |
| 市场占有率 | 按目标市场的机型销量排序 | 覆盖最多的实际用户 |
| 芯片平台代表性 | 同一 Wi-Fi 芯片的机型只选一款代表 | 同芯片行为高度接近，能省下大量名额 |
| 历史缺陷 | 以前在哪些机型上出过问题，必须回归 | 已知的雷不能再踩 |
| 年代跨度 | 不能全选新机，要有老机型 | 老机型往往是兼容性重灾区 |
| 客户明确要求 | 运营商集采清单里点名的 | 没得商量，属于合同义务 |

第二条最容易被忽略，但性价比最高。举例说明：如果 A 品牌的某款手机和 B 品牌的某款手机用的是同一颗 Wi-Fi 芯片，它们在关联、协商、漫游上的行为会非常接近。选一款测，另一款抽查即可，省下的名额可以拿去覆盖别的芯片平台。

除了这五条，工程上还常用两种组合削减技术：

- pairwise（两两组合）——大量缺陷由两个因素的组合触发，很少由三个以上。pairwise 保证任意两个因素的所有取值组合都至少出现一次，用例数会从指数级降到多项式级。
- 正交表——统计学方法，用少量组合均匀覆盖参数空间。适合参数取值较多且相对独立的场景。

### 7.1.3 削减之后必须说明残余风险

这是本节最重要的一点，也是新人最容易漏的。

只交出“我们测了这 10 个组合”，是不完整的交付。

因为读报告的人真正要做的判断是“能不能发货”，而这个判断需要知道没测的那部分风险有多大。

完整的兼容性结论应该包含三段：


|  | 内容 | 示例 |
| --- | --- | --- |
| 覆盖了什么 | 测了哪些组合，依据是什么 | 按市占 + 芯片平台加权选取 10 款，覆盖目标市场约 68% 的存量终端 |
| 结果如何 | 各组合的通过情况与问题 | 9 款全通过；1 款在 WPA3 过渡模式下关联成功率 92%，已定位为终端侧实现差异 |
| 还剩什么风险 | 未覆盖部分的风险评估与缓解建议 | 未覆盖约 32%，其中高风险部分是 2019 年前的老机型；建议灰度发布时优先监控关联失败率 |


### 7.1.4 兼容性是移动靶

兼容性和其他测试有一个本质区别：它的对象在持续变化。

- 新手机每个月都在上市，新的芯片平台在出现。
- 手机系统会自动升级，同一台设备的行为可能在某次系统更新后改变。
- 第三方应用会自己更新，可能引入新的行为。
- 云端服务会发布新版本，一次发布影响全部存量设备。
所以兼容性测试不能是产品发布前做一次就完事的活动，它必须有常态化的回归机制：

- 终端库定期更新——按季度评估新上市机型，纳入测试清单。
- 现网监控——用现网数据（关联失败率、掉线率按机型分布）反过来发现兼容问题。
- 快速响应通道——某款热门机型出问题时，能不能在几天内定位并修复。

## 7.2 安全测试


### 7.2.1 从攻击面看安全

安全测试不是“用工具扫一遍”，而是系统性地识别产品生命周期中的风险入口。这些入口叫攻击面。


| 攻击面 | 典型风险 | 测试关注点 |
| --- | --- | --- |
| 物理调试接口 | 串口、JTAG 未关闭，可直接获得高权限 | 量产固件是否关闭；是否需要认证 |
| 网络端口与服务 | 开放了不必要的端口，或服务有漏洞 | 端口扫描；不必要服务是否关闭 |
| Web / App 管理面 | 越权访问、会话缺陷、注入 | 鉴权是否在后端；会话是否按策略失效 |
| 账号、认证与权限 | 默认密码、弱口令、权限提升 | 是否强制修改初始密码；权限边界 |
| 无线认证与加密 | 弱加密、降级攻击 | 是否支持并默认使用强加密 |
| 固件与 OTA 升级 | 未签名固件可刷入、可降级到有漏洞版本 | 签名校验；防降级（anti-rollback） |
| 云服务与用户数据 | 数据传输未加密、越权访问、隐私超范围 | 传输加密；数据最小化；权限校验 |


### 7.2.2 五条纪律

现在回答章首第二个问题：在工位上扫描自己的测试设备，有没有问题？

有问题。理由有三个，而且第三个最关键：

- 扫描流量会经过公司网络，可能触发安全监控告警，导致安全部门介入调查。
- 扫描工具的行为不一定完全受控，配置失误可能扫到不该扫的网段。
- 你没有书面授权。这一条与技术无关——即使前两条都不发生，未经授权的扫描行为本身就是违规。
所以安全测试有五条不可商量的纪律：


| 纪律 | 含义 |
| --- | --- |
| 明确授权 | 有书面的测试授权，明确范围、时间、可用手段 |
| 隔离网络 | 在物理或逻辑隔离的专用网络中进行，不接入办公网和生产网 |
| 专用账号 | 使用专门的测试账号和测试数据，不使用真实用户数据 |
| 设备可恢复 | 测试对象必须能被恢复到已知状态，不影响其他测试 |
| 完整证据 | 全过程留痕，包括做了什么、什么时候做的、结果是什么 |


| 【常见错误】这是纪律问题，不是技术问题新人容易把这五条理解成“麻烦的流程”。实际上它们保护的是你自己。安全测试的行为特征和真实攻击非常相似，一旦出了问题——比如影响了别人的工作、触发了客户告警——没有授权文件的话，你无法自证清白。还有一点：本手册和配套课件都不讲具体的攻击手法与工具。那需要专门的课程和明确的授权范围。这里讲的是“安全测试在看什么、按什么原则做”。 |
| --- |


### 7.2.3 量产固件复检：最典型的逃逸点

如果这一节只能记住一句话，就是这句：

用研发固件做的安全检查不算数，必须用量产固件复检。

原因很直接——研发固件和量产固件的安全配置完全不同：


| 配置项 | 研发固件 | 量产固件 |
| --- | --- | --- |
| 串口 / 调试接口 | 通常开着（不然没法调试） | 必须关闭或需认证 |
| 固件签名校验 | 通常关闭（不然每次改都要签名） | 必须开启 |
| 防降级 | 通常关闭 | 必须开启 |
| 调试账号 | 可能存在 | 必须清除 |
| 日志级别 | 详细（可能输出敏感信息） | 收敛 |
| 测试后门 | 可能保留 | 必须移除 |

所以在研发固件上做完安全测试就宣布“安全没问题”，等于什么都没验证。量产固件复检必须安排在 PVT 阶段，用真正要出货的那个固件，重新做一遍完整的核查。


### 7.2.4 隐私边界：中屏音箱的特殊议题

带麦克风和摄像头的设备常年放在私人空间里，隐私是第一性约束，不是合规文档上的一条。

这类产品有两个必须做到硬件级、不能停留在 UI 层的验证：


| 项目 | UI 层验证（不够） | 应该做到 |
| --- | --- | --- |
| 麦克风静音 | 点开关，指示灯变色，喊唤醒词没反应 | 电路级验证：静音时麦克风通路是否真的断开；尝试用软件绕过；数据面抓包确认无音频上传 |
| 摄像头遮挡 | 点开关，画面变黑 | 全路径验证：本地、远程、第三方应用、异常态、重启后，均不得取得画面；指示灯与采集硬件绑定 |

还有一个容易被忽略的点：误唤醒是隐私事件。第 3 章讲过，设备在没被呼叫时被触发，意味着它录了音并上传。所以误唤醒率不只是体验指标，它需要和数据上传边界一起评估。


## 7.3 自动化测试


### 7.3.1 什么该自动化

自动化的价值来自第 1 章的一条推论：反复执行同一条稳定用例，边际信息量趋近于零。把零信息量的活交给机器，人去做有信息量的事。

所以判断标准是“这件事的信息量是不是随重复次数快速衰减”：


| 适合自动化 | 原因 |
| --- | --- |
| 高频回归 | 同样的用例反复执行，人工执行边际价值极低 |
| 升级与恢复验证 | 步骤固定、次数要求高（防砖测试需要数百次断电） |
| 接口测试 | 输入输出明确，判定客观 |
| 长稳监控 | 需要连续数天数周采集数据，人做不了 |
| 性能基线 | 条件严格固定才有可比性，机器比人稳定 |
| 配置组合遍历 | 组合数量大，人工执行不现实 |

反过来，不适合自动化的是：探索式测试、首次验证新特性、需要主观判断且尚无客观判据的场景。这些恰恰是人的价值所在。


### 7.3.2 嵌入式自动化的特殊性：必须能程控物理世界

这是嵌入式自动化和互联网自动化最大的区别。

互联网的自动化控制的是软件：调接口、点页面、断言返回值。嵌入式的自动化如果只做到这一层，就碰不到第 2 章讲的那些真正的难缺陷——因为它们需要物理条件才能激励出来。


| 设备 | 能程控什么 | 解锁了什么测试 |
| --- | --- | --- |
| 可程控电源 | 精确控制断电时刻、注入欠压和跌落波形 | 写窗口随机断电、防砖测试、电源质量测试 |
| 可编程衰减器 | 把“距离”变成可设置的数字 | 覆盖测试、漫游触发、弱信号场景 |
| 网络损伤仪 | 注入指定的丢包率、时延、抖动、带宽限制 | 弱网测试、ABR 策略验证、容错验证 |
| 仪器控制 | 程控测试仪、频谱仪、光功率计 | 性能基线自动化、射频与光层批量测试 |
| 设备农场 | 多台设备并行执行、统一调度 | 兼容性矩阵、大样本概率型指标 |
| 红外/蓝牙注入 | 模拟遥控按键 | 机顶盒的高频操作测试 |

一句话概括：做不到程控物理世界，自动化就只能停在接口层。


### 7.3.3 自动化的有效性验证

现在回答章首第三个问题：自动化跑了三个月，通过率一直 100%，这是好事吗？

不一定。也可能是它根本抓不到问题。

有三种常见情况会让自动化“假绿”：


| 原因 | 具体表现 | 为什么难发现 |
| --- | --- | --- |
| 判据太松 | 断言只判“进程还活着”，设备卡死之前都算通过 | 看起来是有断言的 |
| 采集点错位 | 在错误的位置抓数据，问题发生在别处 | 数据能采到，只是采的不是地方 |
| 断言永远为真 | 脚本改过几轮之后，某个断言实际已失效 | 代码里还写着，但逻辑上不会失败 |

这就回到了第 1 章的元问题：我的测试有效吗？


| 【要点】故障注入：验证自动化的唯一可靠方法做法很简单：主动植入一个已知缺陷，看自动化报不报出来。· 接入产品：注入一定比例的丢包、人为限制某个表项容量、构造一次配置丢失。· 机顶盒：在码流里植入损坏帧、制造一段静音、注入固定的时延偏移。· 中屏音箱：播放一段弱唤醒样本、注入回声残留、延长云端响应时间。如果自动化报不出来，说明判据或采集点有问题，必须修。这件事应该周期性地做（比如每季度一次），因为脚本会随着版本演进而慢慢失效。自动化跑绿但抓不到问题，比不跑更危险——因为它给了虚假的安全感，会让人放弃人工检查。 |
| --- |


### 7.3.4 自动化的三个常见误区


| 误区 | 为什么错 | 正确做法 |
| --- | --- | --- |
| 追求自动化率 | 把不适合自动化的也硬做，维护成本高、稳定性差 | 按信息量衰减速度选，不追求数字 |
| 用例失败就重跑 | 掩盖了真实的偶发缺陷 | 先分析失败原因，区分真失败与环境抖动 |
| 只看通过率 | 假绿的自动化通过率也是 100% | 用故障注入验证检出能力 |

第二条尤其值得展开。自动化脚本失败时，新人的第一反应往往是“重跑一次看看”，跑过了就当没事。但偶发失败恰恰可能是最有价值的信号——它可能对应第 2 章讲的时间累积或竞态类缺陷。

正确的做法是：每次失败都要归因，明确区分是真失败（产品缺陷）、伪失败（环境抖动、脚本 bug）还是不确定。不确定的要保留现场，不能一重跑了之。


## 7.4 AI 赋能测试


### 7.4.1 一句话定位

自动化放大执行能力，AI 放大分析能力。

自动化解决的是“人做不过来”的执行问题；AI 解决的是“人看不过来”的分析问题。

嵌入式测试恰好会产生海量的原始数据：几万行日志、几个 G 的抓包、上千张截图、几小时的录音录像。人工逐一分析既慢又容易漏。


| AI 可以辅助的环节 | 具体做什么 |
| --- | --- |
| 需求解析 | 从需求文档中提取测试点初稿，标出歧义表述 |
| 用例建议 | 基于已有用例和需求，生成候选用例供人筛选 |
| 日志与抓包分析 | 在海量日志中定位异常时刻、聚类相似错误 |
| 异常分类 | 把大量缺陷按相似度聚类，识别重复问题 |
| 缺陷描述规范化 | 把口语化的描述整理成结构完整的缺陷单 |
| 报告生成 | 汇总数据、生成图表、起草报告初稿 |
| 知识检索 | 在历史缺陷、模式库、标准文档中快速检索 |


### 7.4.2 人必须负责什么

AI 能做的都是辅助性、可被验证的工作。下面这些必须由人负责：

- 测试策略与取舍——测什么、不测什么、为什么。这需要对业务风险的判断。
- 证据确认——AI 给出的结论，证据是否真的支撑它。
- 风险判断——残余风险有多大，能不能接受。
- 发布建议——能不能进入下一阶段。这是要签字的。

| 【要点】使用 AI 的一条底线你签字的每一个结论，都要能自己解释清楚。理由不是“AI 可能出错”——人也会出错。理由是：报告上署名的是你。三个月后有人拿着这份报告问“当时为什么判断是模块 X 的问题”，你要能答得出来。答不出来，这份报告就废了，你的专业信用也一起废了。所以正确的用法是：大胆用 AI 提高效率，但每一个进入正式测试资产的结论，都要经过你自己的确认。AI 的输出是初稿，不是结论。 |
| --- |

| 【要点】要点清单1. 兼容性组合是几千到几万种，穷举不可能。五条削减依据：市占率、芯片平台代表性、历史缺陷、年代跨度、客户要求。2. 芯片平台代表性最容易被忽略但性价比最高——同芯片机型行为接近，可以省下大量名额。3. 削减之后必须说明残余风险。只交出“测了这 10 个”是不完整的交付。4. 兼容性是移动靶：终端、系统、应用、云服务都在变，必须有常态化回归机制。5. 安全测试有七个攻击面和五条纪律。未经授权的扫描是违规行为，与技术无关。6. 用研发固件做的安全检查不算数。量产固件复检必须安排在 PVT 阶段。7. 麦克风静音和摄像头遮挡必须做到硬件级验证，UI 层验证不构成结论。8. 自动化的判断标准是“信息量是否随重复次数快速衰减”。探索式测试和新特性首次验证不适合自动化。9. 嵌入式自动化必须能程控物理世界：程控电源、可编程衰减器、损伤仪、仪器控制、设备农场。10. 自动化跑绿但抓不到问题比不跑更危险。用故障注入周期性验证检出能力。11. 自动化失败不要一重跑了之，每次失败都要归因：真失败、伪失败、还是不确定。12. 自动化放大执行，AI 放大分析，质量责任仍由测试工程师承担。你签字的结论要能自己解释清楚。 |

这一章讲的东西查不到。它不是知识，是思维习惯：面对一个陌生的问题时，你的大脑按什么路径去搜索。

## 8.1 六个核心思维习惯


### 8.1.1 抽象层次穿梭

定义：能在物理、协议、软件、体验四个层次之间自由上下移动，而不是被困在自己熟悉的那一层。

第 3 章讲过机顶盒的“花屏”：它可能来自六层中的任意一层。再扩展一下，同一个“花屏”的可能位置横跨了四个抽象层次：


| 抽象层次 | 可能的原因 | 验证手段 |
| --- | --- | --- |
| 体验层 | 用户的设置不对、片源本身质量差 | 换片源、检查设置 |
| 软件层 | 解码器 bug、缓冲策略缺陷、后处理算法 | 换固件版本、开关后处理 |
| 协议层 | 传输丢包、组播异常、上游 CDN 问题 | 抓包、换网络路径 |
| 物理层 | HDMI 链路裕量不足、电源纹波、温度降频 | 换线材、测眼图、监控温度 |

为什么这是第一位的能力：只能停在一层的人，遇到不在那一层的问题就束手无策，或者更糟——把问题硬塞进自己熟悉的那一层去解释。软件出身的会一直查代码，硬件出身的会一直怀疑硬件，两边都可能查了三周查不出来。


| 【提示】怎么训练方法一：每次定位问题时，强迫自己列出四层各自的可能原因，再逐层排除。哪怕你有把握是软件问题，也把物理层的可能性写下来。方法二：主动跨界学一点。软件出身的去看一次示波器怎么用、眼图怎么读；硬件出身的去看一次抓包怎么分析。不需要精通，但要知道“那一层能看到什么”。方法三：查了很久查不出来时，主动往下走一层。这是最实用的一条经验法则。 |
| --- |


### 8.1.2 失效想象力

定义：能想到还没发生过的失效方式。这直接对应第 1 章的第一个子问题。

很多人以为这是天赋——“有的人就是想得到，有的人就是想不到”。这个理解是错的，而且有害，因为它让人放弃了训练。

失效想象力的真相是：它是见识的函数。你见过一百个缺陷，自然就想得到第一百零一个。所以它可以靠三种方式系统性地补：


| 方法 | 怎么做 | 为什么有效 |
| --- | --- | --- |
| 缺陷模式库 | 读历史缺陷，按机理分类记忆 | 别人踩过的坑变成你的清单 |
| 结构化激发清单 | 对每个接口机械地问：断了/慢了/乱序/满了/重复了会怎样 | 不依赖灵感，靠遍历 |
| FMEA / FTA | 系统性地遍历失效模式与故障树 | 强迫覆盖，而不是凭印象 |

第二条最实用。举个例子，对路由器的 WAN 口应用这套清单：

- 断了——拔网线、断光纤、上游服务器宕机、认证服务器拒绝……
- 慢了——带宽被限、时延突增、DNS 解析慢……
- 乱序了——报文乱序到达、重传报文先于原报文……
- 满了——会话表满、缓冲区满、日志分区满……
- 重复了——重复的 DHCP 请求、重复的拨号、重复的配置下发……
五个词，二十几条失效路径，全程不需要灵感。这就是结构化的价值。


### 8.1.3 概率与统计思维

定义：把概率性现象当作分布来处理，而不是当作“偶然事件”。

这是嵌入式测试里最大的认知陷阱。有一句话，如果你在工作中听到或者自己说出来，就要警觉：

“偶现，不复现，关闭。”

这七个字连在一起，就是在埋雷。逐层拆解为什么：

- “偶现”意味着它有一个发生概率。假设是 1%，那么十万台设备在用户手里，每天就有上千次发生。
- “不复现”通常意味着复现条件没找到，而不是问题不存在。你试了 5 次没复现，如果真实概率是 1%，5 次不复现的可能性是 95%——这完全正常。
- “关闭”把一个已知存在的风险，变成了一个无人跟踪的风险。
正确的处理方式是提高复现率，而不是放弃：


| 手段 | 做法 | 效果 |
| --- | --- | --- |
| 加大样本 | 从 5 次提到 200 次 | 把 1% 的问题变成“大概率能看到” |
| 加压 | 在资源边界、高温、高负载下重试 | 很多概率型问题在压力下概率上升 |
| 自动化 | 让机器不停重复 | 人做不了的次数机器能做 |
| 分层隔离 | 换环境、换对端、换版本，看概率变化 | 概率变化本身就是定位线索 |


| 【要点】一个必须掌握的判断两个版本的成功率差异，什么时候才算真的有差异？版本 A：50 次成功 45 次（90%）。版本 B：50 次成功 47 次（94%）。看起来 B 提升了 4 个百分点。但在样本量只有 50 的情况下，这个差异完全落在统计波动范围内。换一批人、换一天再测，结果可能反过来。正确做法有两条路：要么加大样本量到足以分辨这个差异（通常需要数百次），要么在报告中明确写出“差异未达到统计显著性”。这不是学术上的吹毛求疵。如果基于这个假的“提升”做了发布决策，或者因此放弃了本该做的优化，代价是真金白银的。 |
| --- |


### 8.1.4 经济学思维

定义：把测试当作一项投资来做决策——资源有限，要投在回报最高的地方。

第 1 章已经证明了穷举不可能。所以测试的本质不是“覆盖”，而是风险加权采样。这意味着每一次“测什么”的决定，同时也是一次“不测什么”的决定。

知道不测什么，和知道测什么同样重要，而且更难。

为什么更难？因为“测了”是安全的，“没测”要担责任。人的本能是多测一点、保险一点。但资源有限，多测的那部分必然挤占了别的地方——而被挤掉的可能恰恰是高风险区域。

经济学思维的三个具体体现：

- 边际思维——再多测 100 条用例，能多换回多少信息？如果接近零，这 100 条就该省下来。
- 机会成本——花两周做一个完美的兼容性矩阵，代价是这两周没做长稳测试。哪个风险更高？
- 精度与成本的权衡——第 6 章讲过：吞吐测试精度从 1% 提到 0.1%，时间成倍上升。什么场景值得付这个代价？

### 8.1.5 边界思维

定义：面对任何系统，先找它的边界在哪。

一切资源都有边界。缺陷密度在边界处，比在中间高一个数量级。

为什么边界处缺陷多？因为边界是判断逻辑最集中、也最容易出错的地方：

- 边界值本身该算内还是算外（≤ 还是 <）
- 超出边界后的处理逻辑（拒绝？降级？覆盖最老的？）
- 边界附近的状态转换（快满了要不要提前告警？）
- 资源回收的时机（什么时候释放？释放不及时会怎样？）
而且这些逻辑通常执行频率极低——设备大部分时间都在中间区域运行，边界逻辑可能几个月才走一次。低频执行的代码，缺陷密度天然更高。

边界思维的实用做法：拿到任何一个功能，先问三个问题：

- 这里有哪些量是有上限的？（数量、大小、长度、时长、频率）
- 上限是多少？规格写了吗？（没写就是需求缺陷）
- 超过上限会怎样？（这一问最重要，也最少被测）

### 8.1.6 时间维度思维

定义：把“时间”当作一个显式的测试设计维度，而不是“跑个 72 小时老化”了事。

第 2 章讲过时间是一等公民。但“重视时间”不等于“跑得久”。把时间当维度来设计，意味着要考虑：


| 时间的不同面向 | 关注什么 | 典型缺陷 |
| --- | --- | --- |
| 顺序 | 事件发生的先后 | 上电顺序不同导致的初始化失败 |
| 时序 | 事件之间的精确间隔 | 竞态、握手超时 |
| 累积 | 量随时间单调变化 | 内存泄漏、同步漂移、闪存磨损 |
| 周期 | 按固定周期发生的事 | 定时任务冲突、心跳与老化不匹配 |
| 回绕 | 计数器达到最大值后归零 | 32 位计数器约 49 天回绕 |
| 跳变 | 时间本身发生突变 | NTP 同步后定时任务错乱、证书校验失败 |

注意后三项：周期、回绕、跳变。它们和“跑得久”没有直接关系——回绕可以用注入方式加速验证，跳变只需要改一下系统时间。很多团队做了很长的老化测试，却从来没测过时间跳变。


## 8.2 五个进阶思维

上面六条是入门阶段最该先建立的。下面五条属于进阶，你在工作一两年后会逐渐用到：


| 思维 | 核心 | 典型应用 |
| --- | --- | --- |
| 因果与证据 | 区分相关与因果；结论必须有证据链 | “换个路由器就好了”不是根因；“改了这行就不复现”也不是 |
| 场景还原 | 把用户投诉逆向翻译成可复现的实验室条件 | 从“晚上看电视卡”还原出“高并发 + 特定码率 + 特定时段” |
| 标准的意图 | 读标准要读懂条款背后的物理或商业意图 | 才能判断适用性、做符合性论证、在争议时与实验室对话 |
| 左移与可测性 | 最好的测试是让缺陷不可能发生，或必然暴露 | 在设计评审阶段提 DFT 需求，而不是事后抱怨没法测 |
| 元认知 | 测试有效性本身要被测试 | 逃逸分析、故障注入、DRE 度量 |

其中因果与证据最值得早点建立。新人最容易犯的错误是把“相关”当成“因果”：


| 【案例】一个把相关当因果的例子现象：某测试人员发现，只要打开设备的 IPv6 功能，网页加载就变慢。他提交了缺陷：“IPv6 功能导致网页加载变慢”。研发排查后发现：真实原因是测试环境的 IPv6 DNS 服务器响应很慢。启用 IPv6 后，系统优先尝试 IPv6 的 DNS 解析，等超时后才回落到 IPv4，于是每次都多等几秒。IPv6 功能本身没有问题，问题在 DNS 配置。这个缺陷单错在哪：它把“打开 IPv6”和“变慢”的相关性，直接写成了因果性。正确的写法：描述现象和复现条件，把“IPv6 导致”改成“启用 IPv6 后出现”，并附上抓包证据让研发自己判断因果。一条实用原则：缺陷单里描述你观察到的，不要描述你推测的。推测可以写在“初步分析”里，但要标明是推测。 |
| --- |


## 8.3 这些思维怎么练

思维不是读一遍就有的。下面是四种可操作的训练方式：


### 8.3.1 复盘每一个逃逸缺陷

现网出了问题，最没价值的复盘是“补一条用例”。最有价值的复盘是追问：为什么我们的测试方法没有抓到它？

逃逸原因通常能归到几类固定的方法缺陷：

- 样本量不足——概率型问题，测的次数不够。
- 时长不足——时间累积类问题，跑的时间不够。
- 维度不足——输入空间有缺口（码流库、语料库、机型库不全）。
- 环境过于理想——实验室条件与真实场景差距太大。
- 判据过松——现象发生了，但判据判成了通过。
每次逃逸都归到这五类之一，你会很快发现自己团队的系统性弱点在哪。


### 8.3.2 定位问题时强迫自己写假设

不要一上来就动手试。先写下三到五条假设，标明每条的验证方法，然后按“验证成本从低到高”排序去做。

这个习惯有两个好处：一是避免陷入“试错循环”，二是当所有假设都被否定时，你会被迫去想新的假设——那正是抽象层次穿梭发生的时刻。


### 8.3.3 每读一个标准，问它的意图

读到某条规定时，多问一句“为什么要这么规定”。比如 RFC 2544 为什么建议单次测试不少于 60 秒？因为要避开启动瞬态、让缓冲状态稳定、让统计有足够样本。

懂了意图，你才知道什么时候可以偏离（日常回归用 30 秒也行），什么时候绝对不能（正式送测必须按标准）。


### 8.3.4 主动去看自己不熟悉的那一层

每个季度给自己定一个跨层的小目标：这个季度学会读眼图，下个季度学会用频谱仪看干扰，再下个季度把某个协议的报文交互从头到尾读一遍。

不需要精通。目标只是知道那一层能看到什么、什么现象该怀疑到那一层。


## 8.4 本章小结


| 【要点】要点清单1. 知识可以查，思维不能。六个核心思维习惯决定了你三年后是执行者还是设计者。2. 抽象层次穿梭——能在物理、协议、软件、体验四层之间上下走。查很久查不出来时，主动往下走一层。3. 失效想象力——不是天赋，是见识的函数。靠缺陷模式库、结构化激发清单、FMEA 系统性地补。4. 概率与统计思维——“偶现、不复现、关闭”是在埋雷。正确做法是提高复现率，而不是放弃。5. 两个版本的成功率差异，样本量不足时可能只是统计波动。要么加大样本，要么写明未达显著性。6. 经济学思维——测试是风险加权采样。知道不测什么更难，因为“测了”安全、“没测”要担责。7. 边界思维——缺陷密度在边界处高一个数量级。三问：哪些量有上限？上限是多少？超过会怎样？8. 时间维度思维——时间有六个面向：顺序、时序、累积、周期、回绕、跳变。后三项与“跑得久”无关。9. 五个进阶思维：因果与证据、场景还原、标准的意图、左移与可测性、元认知。10. 缺陷单里描述你观察到的，不要描述你推测的。推测要标明是推测。11. 逃逸复盘要归到五类方法缺陷：样本量、时长、维度、环境、判据。补一条用例是最没价值的复盘。 |

- B. 换一个更有经验的开发继续查代码
- C. 主动往下走一层，排查链路、电源、温度等物理层因素

- A. 无法复现的问题确实无法修复，关闭是合理的
- B. 不复现通常意味着复现条件未找到；应通过加大样本、加压、自动化来提高复现率

- A. 版本 B 优于版本 A，提升 4 个百分点
- B. 版本 B 略优，但幅度不大
- C. 在此样本量下差异未达统计显著性，需加大样本量才能判断
- D. 两个版本没有差异
8-4 下列哪一项最能体现“边界思维”？

- B. 找出系统中所有有上限的量，测上限值、上限附近以及超过上限后的行为
- C. 优先测试用户最常用的功能
- D. 按需求文档的顺序依次测试

## 9.1 回到目标函数

第 1 章一开始，我们从三条公理推出了测试的目标函数：

在有限的时间、成本和观测手段下，最大化“关于交付风险的信息获取量”。

走过八章之后再看这句话，它的每一部分都有了具体内容：


| 目标函数的部分 | 对应前面哪些内容 |
| --- | --- |
| “有限的时间、成本” | 阶段策略（第 4 章）、组合削减（第 7 章）、经济学思维（第 8 章） |
| “有限的观测手段” | 约束六可观测性差（第 2 章）、可测性设计 DFT、分层定位（第 3 章） |
| “交付风险” | 质量模型八属性（第 5 章）、风险三维评估（第 4 章） |
| “信息获取量” | 判定准则五要素（第 1 章）、概率型指标的样本量（第 8 章） |
| “最大化” | 风险加权采样、故障注入验证有效性（第 7 章） |

换句话说，前面八章讲的所有方法，都是在解同一个优化问题的不同侧面。


## 9.2 什么是"刚刚好的测试"

既然不能穷尽，也不能敷衍，那什么算“刚刚好”？

“刚刚好”不是一个感觉，它是六类输入经过判断之后的输出：


| 输入 | 提供什么信息 |
| --- | --- |
| 客户与法规要求 | 哪些是不可谈判的硬约束（认证、入网规范、合同条款） |
| 核心用户任务 | 用户真正在用的是什么，哪些路径不能出问题 |
| 产品质量模型 | 要从哪几个视角去看（第 5 章的八属性） |
| 技术与变更风险 | 这一版改了什么，哪些模块历史上出过问题 |
| 当前研发阶段 | 这个阶段该问什么问题（第 4 章的 EVT/DVT/PVT/MP） |
| 可用资源 | 时间、人力、设备、测试资产的实际情况 |

六类输入汇进来，测试工程师做出判断，产出三样东西：


| 输出 | 内容 | 为什么必要 |
| --- | --- | --- |
| 本轮测试组合 | 测什么、不测什么、哪些组合可以代表覆盖 | 把有限资源分配到风险最高的地方 |
| 可信测试证据 | 数据、日志、抓包、判定记录 | 结论必须可被复现、可被质疑、可被复用 |
| 残余风险与建议 | 还剩什么风险、能不能进下一阶段 | 决策者需要知道自己在承担什么 |

“刚刚好”不是少测，而是让每一份工时都产生信息——而不是产生噪声。


## 9.3 测试工程师到底交付什么

现在回答章首第一个问题：向项目经理汇报，第一句话说什么？

大多数人的答案是“测试通过”或者“没什么问题”。


| 【常见错误】"没问题"是测试工程师最不该说的三个字第一，它不准确。你测的是有限的组合，不可能覆盖全部。“没问题”这个表述超出了你的证据能支撑的范围。第二，它不承担责任。出了事之后，“你不是说没问题吗”——这时候你既拿不出依据，也没法解释为什么当初漏了。第三，它剥夺了别人的决策权。项目经理需要判断“能不能发货”，这个判断需要知道风险在哪。你说“没问题”，等于替他做了决定，而你手上并没有他需要考虑的全部信息（市场窗口、客户压力、竞品动态）。 |
| --- |

合格的汇报是三句话：

- 我们测了什么。用什么方法、在什么条件下、覆盖了哪些范围。
- 结果是什么。关键指标的数值与判定，问题分布，证据在哪里。
- 还剩什么风险，我的建议是什么。哪些没覆盖、风险有多大、建议能进入下一阶段还是不能。
测试的结论不是“没问题”，而是“我们知道了什么，还有什么不知道”。


### 9.3.1 五个行动词

把这个岗位的日常工作压缩成五个动作：


| 动作 | 含义 | 做不到会怎样 |
| --- | --- | --- |
| 理解产品 | 知道它承诺了什么、由哪些部分构成、在什么环境里工作 | 测的是自己想象的产品，不是真实的产品 |
| 追溯需求 | 每一条用例都能追到一条需求或一个风险 | 测了很多，但说不清为什么测 |
| 识别风险 | 知道哪里最可能出问题，资源往那里投 | 平均用力，高风险区反而没测透 |
| 保留证据 | 结论可被复现、可被质疑、可被复用 | 结论没有说服力，也无法交接 |
| 支持决策 | 给出的不是“通过/不通过”，是决策所需的信息 | 变成盖章的人，而不是提供判断的人 |

最后回答章首第二个问题，也是这本手册的落点。

前言里说过，这个岗位入门门槛看起来低，天花板极高。走完九章，你应该能看清那个高度差在哪里了：


|  | 执行者 | 设计者 |
| --- | --- | --- |
| 面对陌生产品 | 等别人给用例 | 能自己推出该测什么 |
| 面对模糊需求 | 按字面理解就开始测 | 先拆成可测试需求，再谈设计 |
| 面对偶现问题 | 标记“不复现”关闭 | 设计实验提高复现率 |
| 面对资源不足 | 抱怨测不完 | 做风险加权，并说明残余风险 |
| 面对现象 | 停留在自己熟悉的那一层 | 在四个抽象层次之间穿梭 |
| 面对结论 | 说“测过了，没问题” | 说清测了什么、剩什么风险、建议是什么 |

右边那一列的每一条，都不是靠多干几年自然长出来的。它们对应的是第 8 章那六个思维习惯，而思维习惯需要刻意训练。


| 【要点】给你的三条起步建议第一，从今天起，每写一条用例都问一遍四个子问题。会怎么坏？怎么让它坏？怎么知道它坏了？这一次说明了什么？一开始会觉得慢，三个月后它会变成本能。第二，把每一个自己定位过的缺陷，写清机理。不是“改了这行就好了”，而是“为什么改了这行就好了”。写不出机理，说明根因分析没做完。第三，每个月找一次自己的认知边界。主动去看一层自己不熟悉的东西——一次抓包分析、一次眼图判读、一次声学测试。不需要精通，只要知道“那一层能看到什么”。 |
| --- |


## 9.5 本章小结


| 【要点】要点清单1. 前八章的所有方法，都是在解同一个优化问题——目标函数——的不同侧面。2. “刚刚好的测试”由六类输入决定：客户与法规、核心用户任务、质量模型、技术与变更风险、研发阶段、可用资源。3. 测试的三个输出：本轮测试组合、可信测试证据、残余风险与建议。4. “没问题”是测试工程师最不该说的三个字——不准确、不担责、剥夺了别人的决策权。5. 合格的汇报是三句话：测了什么、结果是什么、还剩什么风险与建议。6. 测试的结论不是“没问题”，而是“我们知道了什么，还有什么不知道”。7. 五个行动词：理解产品、追溯需求、识别风险、保留证据、支持决策。8. 执行者与设计者的差距在思维，不在年限。思维需要刻意训练。 |

## B.1 第 1 章


| 题号 | 答案 | 解析 |

| 1-1 | C | A、B 都是手段被误当成目的。D 是方向性错误——测试无法证明“没有问题”，只能提供关于风险的信息 |
| 1-2 | B | 必然通过的用例信息量趋近于零。注意不是 C（删除）——它仍有防回归价值，但应降频或自动化 |

1-6 要点：组合空间是天文数字，任何覆盖率的分母都是人为选定的，因此数字本身可以被“设计”得很好看，却不反映真实风险。覆盖率仍有意义的场景：作为同一分母下的趋势指标（本版比上版覆盖是否退化）、作为遗漏检查（哪些需求条目一条用例都没有）。

1-7 要点：多数经历会归到第一问（想不到）。归到第二问的例子：知道问题但构造不出条件；第三问：现象发生了但没有观测手段；第四问：测了少量样本就下了普遍结论。能说清理由比归对类别更重要。

1-8 参考改写：对象——路由器整机；条件——按典型家庭配置完成配网，接入 8 台终端持续跑混合业务；刺激——保持通电连续运行 14 天，期间每小时执行一次标准业务巡检；指标——内存占用、CPU 占用、连接数、业务成功率；标准——内存占用趋势斜率≈0（无单调上升），业务成功率≥99.9%，无非预期重启；证据——每小时采样数据表、趋势曲线、异常时刻日志。

1-9 提示：如果你列出的失效方式少于 8 条，说明只用了“断了”和“满了”两个词。试着把“乱序”和“重复”用足——它们最容易被忽略，也最容易挖出没人想过的路径。


## B.2 第 2 章


| 题号 | 答案 | 解析 |
| --- | --- | --- |
| 2-1 | B | A、C、D 互联网服务同样需要。硬件不可回滚是嵌入式独有 |
| 2-2 | B | 判据是趋势斜率而非绝对阈值。持续上升本身就是信号，不必等它超过 80% |
| 2-3 | C | 功能测试是必要不充分条件，是地基。正确做法是另外专门设计针对三交叉区的测试 |
| 2-4 | C | 这是产品的可测性缺陷，应转化为 DFT 需求推动设计改进，而不是接受现状 |
| 2-5 | D | 认证周期以月计且有依赖关系，必须在立项时锁定排期，是项目的关键路径 |

2-8 要点：主要落在时间累积（缓存堆积、碎片化、存储写满导致读写变慢）和资源边界（后台应用增多、内存不足触发频繁回收）。异常路径维度较弱。这个例子说明三个维度可以独立存在，也可以叠加。


## B.3 第 3 章


| 题号 | 答案 | 解析 |
| --- | --- | --- |
| 3-1 | C | 实验室给可比性（判断改动是否有效），现场给外推性（用户真实体验）。两者不可替代 |
| 3-2 | B | 加速路径可能绕过 QoS 策略。所有策略类问题都应先做双路径对比 |
| 3-3 | C | 这一问能一次切分掉一半的层次：只有个别频道花指向内容源或该格式解码，全部频道花指向链路或输出 |
| 3-4 | B | 误唤醒的定义是“无人呼叫时被触发”，必须用长时暴露统计，主动触发测的是唤醒率 |
| 3-5 | B | 同步误差会随时长单调累积，判据必须是趋势而非快照，且需要客观测量而非主观判断 |

3-6 要点：用户体验由整条链路决定，任何一环出问题现象都出现在输出端。例子：机顶盒“能播放”这个功能点测通过了，但用户仍然投诉卡顿——因为问题在传输环节的丢包，或在输出环节的 HDMI 链路。只测功能点会漏掉整个链路的耦合问题与非功能属性。

3-7 要点：漏唤醒是体验问题（多叫一次），误唤醒是隐私事件（未被呼叫时录音上云）。两者在同一条 ROC 曲线上此消彼长。面对“唤醒率提到 99%”的要求，应追问：①在什么声学条件下？②误唤醒率的约束是多少？③样本量多大？只优化一边会把误唤醒推高，反而制造更严重的问题。

3-8 要点：接入产品是多厂商 OLT 互通实验室；机顶盒是维度化码流库与电视机型库；中屏音箱是声学场景剖面与人群语料库。它们定义了测试的输入空间——码流库缺某个编码维度，那个维度的解码缺陷就必然逃逸；语料库缺儿童样本，儿童场景的唤醒率数据就没有外推价值。

| --- | --- | --- |
| 4-1 | B | 环境准备服务于第二个子问题（可控性），标准是能否把系统驱到目标状态 |
| 4-2 | B | “支持 64 台”这类表述最危险的是边界未定义。超限行为是最少被测、也最容易出事的部分 |
| 4-3 | C | 反了。可检出性越低（越难发现），风险优先级越高，因为它更可能逃逸到市场 |
| 4-4 | C | 判断依据：不达标要改什么？散热不足要改结构，属于硬件，必须在 EVT |
| 4-5 | B | 完整结论是三段式：测了什么、结果如何、还剩什么风险 |

4-6 参考六要素：对象——机顶盒整机；条件——已进入深度待机状态并保持不同时长（1 分钟 / 1 小时 / 24 小时 / 7 天）；刺激——通过遥控电源键唤醒；指标——从按键到首个可交互画面的时长、唤醒成功与否；标准——各待机时长下唤醒成功率 100%，唤醒时长 P95 ≤ 门限；证据——高速摄像或采集卡录制的时间戳记录、成功率统计表、失败时的日志。

4-7 要点：二维矩阵中的“概率”是用户侧发生概率，与“实验室能否发现”无关。若不引入可检出性，那些“实验室极难发现但现场必然发生”的问题（如 49 天计数器回绕、数周后的内存泄漏）会被排在后面，而它们恰恰是逃逸风险最高的。

4-8 要点：OTA 指标不达标可能需要改天线布局、结构或射频前端——都是硬件。等到 DVT 才发现，结构已冻结、模具已开，只能靠降低指标或软件补偿，代价是性能永久损失或推翻重来。这属于“一旦不成立就要改硬件”的验证，必须在 EVT。


## B.5 第 5 章


| 题号 | 答案 | 解析 |
| --- | --- | --- |
| 5-1 | B | 功能性只是八属性之一。其余七个尚无结论，尤其是性能、兼容、可靠、安全四项 |
| 5-2 | C | 可维护性无独立测试类型，体现在日常定位过程中，产出形式是可测性需求（DFT） |
| 5-3 | C | 四个支撑是环境、工具、数据、判定 |
| 5-4 | B | 码流库的维度缺口直接等于测试盲区，特定编码参数组合下的解码缺陷会逃逸 |
| 5-5 | C | 重拨风暴需要反复断网观察退避策略（可靠视角）+ 模拟上游异常（兼容视角）才能暴露 |

5-6 要点：性能效率↔约束五（资源稀缺，余量小易触边界）；兼容性↔约束四（对端不受控且数量巨大）；可靠性↔约束二、三（不可回滚 + 连续运行三到五年）；安全性↔约束七（合规二值闸门，且设备位于家庭网络内部）。

5-7 提示：多数人会发现最容易漏的是易用性和可维护性。这两个视角的共同点是它们不影响“功能能不能用”，因此在功能导向的测试中天然被忽略。

5-8 要点：因为输入空间需要人为构造且维度极多，建设周期以月计并需持续维护。缺口即盲区。举例应结合自己产品线的实际资产（码流库 / 语料库 / 终端库 / 互通设备）。


## B.6 第 6 章


| 题号 | 答案 | 解析 |
| --- | --- | --- |
| 6-1 | B | 过载后吞吐会下降，因为资源被重传、超时、排队消耗，有效转发反而减少 |
| 6-2 | C | 应优先排除物理因素。这也是“性能测试必须同步采集资源数据”的直接理由 |
| 6-3 | B | 小包数量多、单包处理预算小，考验的是包处理能力（PPS） |
| 6-4 | B | 均值掩盖长尾。用户感知到的卡顿往往来自 P99 那一小部分 |
| 6-5 | C | 合格回答的三句话：用什么方法、什么条件、覆盖不到什么。第三句最少人说但最重要 |
| 6-6 | B | 衰减器的核心价值是让“距离”成为可精确设置、可重复的参数，从而使结果可比 |

6-7 要点：资源是先行指标（性能下降前资源先有征兆），也是定位的起点（区分 CPU 瓶颈、内存带宽瓶颈、温度降频、无线重传）。不采集的后果见 6.1.3 案例：降频被误判为软件性能衰减，研发查了两周软件。

6-8 要点：三者是递进关系，适用范围由窄到宽。只有 RFC 2544 能回答的：“这次改动有没有让有线转发能力变差”（可比性最强）；只有 TR-398 能回答的：“在标准化可控射频条件下，我们和竞品的 Wi-Fi 能力差多少”；只有 WAA 能回答的：“用户在家里同时开会、看视频、下载时，体验会不会崩”。

6-9 要点：不足有三——①只测到规格值，未测超限行为（第 65 台会怎样？已连接的会不会受影响？）；②未说明测试条件（终端类型、业务负载、距离）；③未验证并发下的公平性（是否有终端被“饿死”）。应补充：压到规格的 1.5 倍观察降级行为与恢复、构造混合业务并发剖面、统计各终端的吞吐分布。


## B.7 第 7 章


| 题号 | 答案 | 解析 |
| --- | --- | --- |
| 7-1 | B | 同芯片平台机型行为高度接近，选一款代表可省下大量名额去覆盖别的平台 |
| 7-2 | B | 必须说明选取依据与残余风险，否则读者无法判断能否发货 |
| 7-3 | C | 三个理由：流量经过公司网络、工具行为不完全受控、缺少书面授权。第三条与技术无关 |
| 7-4 | B | 研发固件通常开调试口、关签名校验，与量产配置完全不同，必须用量产固件在 PVT 复检 |
| 7-5 | C | 长期 100% 通过可能是“假绿”。用故障注入验证检出能力是唯一可靠的检验方式 |
| 7-6 | B | AI 输出是初稿不是结论。底线是你签字的每个结论都要能自己解释清楚 |

7-7 要点：兼容对象持续变化——新机型上市、系统自动升级、第三方应用更新、云端发布。因此不能是发布前做一次的活动，必须有常态化机制：终端库定期更新、用现网数据反向发现问题、建立热门机型的快速响应通道。

7-8 要点：三种假绿——判据太松（断言只判进程存活）、采集点错位（数据采到了但不是问题发生的地方）、断言永远为真（脚本迭代后失效）。验证方法：周期性故障注入，主动植入已知缺陷看能否报出。

7-9 要点：UI 层验证只能证明“软件层面丢弃了音频”，无法排除软件绕过的可能，也无法证明麦克风通路真的断开。风险是：一旦存在绕过路径或实现缺陷，设备在用户以为静音的状态下仍在采集，这是隐私事件而非功能缺陷。应做电路级验证 + 软件绕过尝试 + 数据面抓包三重确认。


## B.8 第 8 章


| 题号 | 答案 | 解析 |
| --- | --- | --- |
| 8-1 | C | “查很久查不出来时主动往下走一层”是抽象层次穿梭最实用的经验法则 |
| 8-2 | B | 不复现通常是复现条件未找到。5 次不复现对 1% 概率的问题完全正常 |
| 8-3 | C | 样本量 50 时，90% 与 94% 的差异落在统计波动范围内，不足以支撑“提升”的结论 |
| 8-4 | B | 边界思维的三问：哪些量有上限？上限是多少？超过会怎样？第三问最重要 |

8-5 提示：如果列不到 10 条，检查是否把五个词都用足了。“乱序”和“重复”通常能各挖出 2–3 条别人想不到的路径。

8-6 要点：它是见识的函数而非天赋——见过一百个缺陷自然想得到第一百零一个。三种训练方法：缺陷模式库（把别人的坑变成自己的清单）、结构化激发清单（不依赖灵感，靠遍历）、FMEA/FTA（强迫系统性覆盖）。

8-7 要点：问题在于把相关性写成了因果性。参考改写：“启用 IPv6 后，网页首次加载耗时从约 0.3 秒增至约 5 秒；关闭 IPv6 后恢复。抓包见启用后先发起 IPv6 DNS 查询，等待约 4.5 秒超时后回落 IPv4。初步推测（待研发确认）与 IPv6 DNS 可达性有关。”——描述观察到的，推测部分明确标注。


## B.9 第 9 章


| 题号 | 答案 | 解析 |
| --- | --- | --- |
| 9-1 | C | 三句话：测了什么、结果如何、还剩什么风险与建议。A、D 都是“没问题”的变体；B 只有过程数据没有结论 |
| 9-2 | C | 测试不可能穷尽，残余风险必然存在。说明它不是示弱，而是完整交付的一部分 |
| 9-3 | C | 执行者与设计者的差距在能否自己推导出该测什么，与用例数、缺陷数、年限都不直接相关 |

9-4 要点：准确性——超出了证据能支撑的范围；责任——出事后无依据可循、无法自证；决策——剥夺了决策者的判断权，而你并不掌握他需要考虑的全部信息（市场窗口、客户压力、竞品动态）。

9-5 提示：一个可用的串法——产品是承诺 → 实现必然偏离 → 代价随阶段指数增长 → 所以要在有限资源下最大化风险信息 → 拆成四个子问题 → 嵌入式有七个约束使这四问都变难 → 所以有了流程、模型、专项方法 → 但方法都有边界 → 所以最终要靠思维判断 → 交付的是“知道了什么、还有什么不知道”。

- □ 三段式齐了吗？测了什么 / 结果如何 / 还剩什么风险

- □ 时延类指标给了分位数吗？还是只给了均值？

- □ 结论里有没有出现“没问题”这三个字？

- □ 这个月有没有一次主动往下走了一层？
- □ 有没有把某个缺陷抽象成模式，沉淀下来？
- □ 有没有对某个“看起来对”的结论提出过质疑？

# 附录 E　三条产品线的入门实操路径

手册正文讲的是通用方法。这个附录回答一个更具体的问题：分到某条产品线之后，第一个月该动手做什么？三条路径按“主攻线精读、其余两条泛读”的方式使用。


## E.1 共同的第一周

不管分到哪条线，第一周做的事是一样的：


| 动作 | 具体做什么 | 为什么先做这个 |
| --- | --- | --- |
| 看懂产品 | 拆一台样机（在导师指导下），对照本手册第 3 章的框图找到每个模块 | 看得见摸得着，比看图印象深十倍 |
| 跑通一条完整链路 | 从最基础的业务开始：接入产品跑通拨号上网，机顶盒跑通一个频道，音箱跑通一次唤醒 | 建立“正常长什么样”的基线 |
| 学会取证 | 串口怎么接、日志怎么导、抓包怎么抓、录像怎么录 | 没有取证能力，后面所有工作都是空谈 |
| 读安全与保密规范 | 实验室安全、设备操作规范、数据保密要求 | 这是红线，不能靠悟 |


| 【常见错误】第一周最容易走偏的地方很多新人第一周急着“开始测”，拿到用例就一条条执行。这样做的问题是：你还不知道“正常”是什么样，就开始判断“异常”。结果要么把正常现象当成缺陷提上去（有效率低），要么把真实缺陷当成正常放过去（漏测）。正确的顺序是：先建立基线认知，再开始判断。这一周慢一点，后面会快很多。 |
| --- |


## E.2 接入产品（路由器 / 光猫）


### E.2.1 第一个月的六个动手任务


| 任务 | 做什么 | 要能回答什么 |
| --- | --- | --- |
| ① 走通三种接入方式 | PPPoE 拨号、DHCP、静态 IP 各配一遍，抓包看完整交互 | 三者的报文交互有什么区别？失败时分别停在哪一步？ |
| ② 拉电 50 次 | 正常态、配置保存瞬间、升级过程中各拉若干次 | 有没有出现配置丢失？启动时长有没有变化？ |
| ③ 画一次转发路径 | 从 WAN 口进来的一个包，到 LAN 口出去，经过了哪些模块 | 数据流和控制流分别走哪里？ |
| ④ 开关硬件加速对比 | 同一条限速规则，开加速和关加速各测一次 | 行为一致吗？如果不一致，差在哪？ |
| ⑤ 做一次覆盖测试 | 固定几个点位测速率，再换一个位置重测 | 同一台设备，条件变了结论变了多少？ |
| ⑥ 跑一次 72 小时长稳 | 连续通电，每小时采一次内存、连接数、业务成功率 | 趋势曲线是平的还是上升的？ |

任务④ 是这条线最有价值的一课。它会让你亲眼看到第 3 章讲的“双路径不一致”——同一条策略，两条转发路径的行为可能完全不同。理解了这件事，你以后遇到“配置了但不生效”的问题，第一反应就会对。

### E.2.3 最先要读懂的三类缺陷

- 资源边界类——NAT 会话表、MAC 表、组播组数。找一个历史缺陷，看它是怎么被发现的。
- 拨号异常类——重拨退避、MTU 黑洞、上游异常。这一类现象最“像网络问题”，最考验定位能力。
- 双路径不一致类——见任务④。这一类现象最“像功能 bug”，但根因在架构。

## E.3 机顶盒


### E.3.1 第一个月的六个动手任务


| 任务 | 做什么 | 要能回答什么 |
| --- | --- | --- |
| ① 做一次分层隔离实验 | 同一个“花屏”现象，用换线、换电视、换片源、断网播本地文件四种方法逐层排除 | 每一步排除掉了哪一层？ |
| ② 抓一次 EDID | 接三台不同的电视，各抓一次 EDID 并对比 | 三台电视声明的能力有什么不同？盒子的输出跟着变了吗？ |
| ③ 测一次音画同步 | 用标准同步码流连续播放 4 小时，每半小时测一次偏差 | 偏差是随机波动还是单调漂移？ |
| ④ 跑一遍码流库 | 把手上能拿到的所有码流依次播放，记录异常 | 哪些参数组合会出问题？码流库覆盖了哪些维度、缺哪些？ |
| ⑤ 高频换台 | 连续换台 500 次以上（能自动化最好），观察组播组计数 | 组数会回落吗？还是持续累积？ |
| ⑥ 查一次 DRM 等级 | 用平台提供的工具查询设备实际达到的安全等级 | 是设计预期的等级吗？升级后会变吗？ |

任务① 是这条线的核心训练。做完之后你会形成一个本能：听到“花屏”不再直接去猜原因，而是先设计一组能切分层次的实验。


### E.3.2 第一个月要认识的工具


| 工具 | 用来干什么 | 入门标准 |
| --- | --- | --- |
| 采集卡 | 录制 HDMI 输出画面 | 能录制并逐帧回看，能定位到异常发生的那一帧 |
| 码流分析工具 | 看 TS 结构、PCR/PTS | 能读出码流的编码参数，能看时间戳是否连续 |
| EDID 读取工具 | 读取电视声明的能力 | 能抓取并解析，能对照实际输出核对 |
| 网络损伤仪 | 注入丢包、时延、抖动 | 能设置损伤参数并观察画面表现 |
| 声压计 / 音频分析 | 测响度与音频指标 | 能测量不同音源的响度差异 |


### E.3.3 最先要读懂的三类缺陷

- HDMI 链路类——EDID 解析、HDCP 鉴权、带宽裕量。这一类最常被误判为软件问题。
- 时间累积类——音画同步漂移、解码器实例泄漏。这一类在短测中完全不可见。
- 格式边界类——特定编码参数组合下的花屏或崩溃。这一类直接暴露码流库的维度缺口。

## E.4 智能中屏音箱


### E.4.1 第一个月的六个动手任务


| 任务 | 做什么 | 要能回答什么 |
| --- | --- | --- |
| ① 唤醒率的第一次统计 | 固定距离角度，唤醒 50 次，记录成功次数 | 成功率是多少？置信区间大概多宽？ |
| ② 加上播放再测一次 | 同样条件，但设备正在播放音乐（分档：低、中、最大音量） | 各档的唤醒率差多少？最大音量档还能用吗？ |
| ③ 换人再测一次 | 找不同性别、不同年龄、不同口音的同事各测 30 次 | 不同人之间的差异有多大？ |
| ④ 做一次误唤醒长时统计 | 让设备在播放电视剧或新闻的房间里跑 24 小时，统计自行响应次数 | 按“次/24 小时”计是多少？触发它的是哪些片段？ |
| ⑤ 测一次端到端时延 | 从说完到出声，测 50 次并统计分布 | 均值和 P95 差多少？慢的那几次卡在哪一步？ |
| ⑥ 断网走一遍高频指令 | 拔掉网络，把常用指令都说一遍 | 还剩哪些功能可用？提示语能让用户理解发生了什么吗？ |

任务①②③ 连起来做，是这条线最重要的一课。你会亲眼看到：同一台设备，条件一变（加上播放、换个人），唤醒率可能从 95% 掉到 60%。这会让你彻底理解为什么这个品类的所有结论都必须带条件和样本量。


### E.4.2 第一个月要认识的工具


| 工具 | 用来干什么 | 入门标准 |
| --- | --- | --- |
| 声级计 | 测环境噪声与播放音量 | 能测量并记录 dB 值，理解 A 计权的含义 |
| 多通道录音设备 | 采集麦克风原始音频 | 能采集并保存，能对照处理前后的差异 |
| 标准声源 / 人工嘴 | 稳定重复地发出测试语音 | 能按规定声压回放语料 |
| 抓包工具 | 核查端云交互与上传行为 | 能看出什么时候发生了音频上传 |
| 自动化脚本 | 重复触发唤醒并计数 | 能跑完 50 次以上的自动统计 |


### E.4.3 最先要读懂的三类缺陷

- 声学与 AEC 类——漏声、barge-in 失效、阵列一致性。这一类的根因常在结构和硬件。
- 统计判定类——样本量不足导致的错误结论、用主动触发去“测”误唤醒。这一类是方法错误，比缺陷本身更值得警惕。
- 隐私边界类——静音可绕过、非交互状态下的上传。这一类直接标致命。

## E.5 另外两条线：认知级要掌握什么

不是主攻线的那两条，不需要动手，但要能回答三个问题：


| 问题 | 接入产品 | 机顶盒 | 中屏音箱 |
| --- | --- | --- | --- |
| 它是什么？ | 转发 + 协议控制 + 安全管理三位一体的网络设备 | 把网络内容变成电视上音视频体验的媒体设备 | 把语音变成动作与反馈的交互设备 |
| 核心链路是什么？ | WAN 进 → 转发处理 → LAN/无线 出 | 传输→解密→解复用→解码→后处理→输出 | 采集→唤醒→识别→理解→执行→反馈 |
| 一个特有难点是什么？ | 资源边界与时间累积交叉处的高逃逸缺陷 | 同一现象可能来自六层中任意一层，分层定位难 | 输入是不可完全复现的物理声场，所有指标都是概率量 |

能把这张表用自己的话讲出来，认知级就达标了。
