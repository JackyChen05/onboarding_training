# 4.1 缺陷生命周期与提报规范

## 状态流转

```
新建 → 确认（开发接受） → 修复中 → 已修复 → 验证通过关闭
              ↓                            ↓
          拒绝/非缺陷 ←—— 说明理由      验证不过 → Reopen
```

要点：

- **有效缺陷 = 开发确认并修复**。被拒绝的缺陷要弄明白拒绝原因——是复现步骤不清、判据不对、还是确实非缺陷，记入《新人视角观察记录》。
- Reopen 必须附新的验证证据，不写「还不行」三个字。

## 提报必填字段（对照自查）

| 字段 | 要求 |
| --- | --- |
| 标题 | 模块 + 现象 + 条件，一句话可定位。反例：「Wi-Fi 有问题」；正例：「5G 频段 160MHz 下开启 WPA3 过渡模式，iPhone12 关联失败」 |
| 版本/构建 | 完整版本号，含日期 |
| 环境 | 拓扑、对端设备型号、关键配置 |
| 复现步骤 | 编号步骤，他人照做可复现；写明概率（如 3/10） |
| 预期/实际 | 预期结果要有判据出处（需求/标准/竞品行为） |
| 证据链 | 见 [4.3](/4-defects/evidence) |
| 严重度/优先级 | 按影响判定，不夸大不缩小 |

## 提交前自查（手册附录 C.3 提交缺陷前）

- [ ] 复现步骤别人照着能复现吗
- [ ] 概率写了吗（几次中几次）
- [ ] 证据链四件套齐了吗
- [ ] 预期结果的判据出处写了吗
