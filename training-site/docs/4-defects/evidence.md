# 4.3 缺陷证据链要求

## 为什么强调证据链

试用期目标原文：「缺陷提交时附完整证据链（日志/抓包/...）」。证据链的目的有两个：

1. **开发不用找你问第二遍**——复现环境、日志、报文都在附件里。
2. **互操作问题的归属靠证据谈判**——和对端厂商/运营商界定问题责任时，抓包 + 时序 + 标准条款，三样缺一不可（手册 2.5 要点 5）。

## 四件套标准

| 证据 | 要求 | 获取方式 |
| --- | --- | --- |
| 串口/系统日志 | 覆盖问题发生前后窗口，带时间戳，**先导日志再重启** | [3.2 串口与日志](/3-tools/serial) |
| 抓包文件 | pcap 原文件 + 关键报文标注 | [3.1 抓包分析](/3-tools/wireshark) |
| 环境信息 | 拓扑图、对端型号、关键配置、版本号 | 测试记录模板 |
| 复现概率 | 明确写 x/y，必现也要写「3/3 必现」 | 多次复现统计 |

## 不同类型缺陷的证据侧重

| 缺陷类型 | 关键证据 |
| --- | --- |
| 协议交互类 | 抓包（交互时序）+ 标准条款引用 |
| 性能类 | 打流报告（含五要素环境条件）+ 趋势数据 |
| 崩溃/复位类 | 串口日志（含 crash dump）+ 复现步骤 |
| 长稳/泄漏类 | 多天趋势曲线（内存/表项），不能只给快照 |
| 音画/显示类 | 视频录像 + 码流样本 + 分层隔离实验结论 |

## 反例（都是真实的新人被退回原因）

- 只有一张现象截图，没有日志 → 开发无法定位，退回。
- 日志是重启后抓的 → 现场已被轮转覆盖。
- 抓包只截了图没附 pcap → 开发无法自行分析。
- 「偶现」但没写概率和尝试次数 → 无法评估严重度。
