# 3.8 网络性能测试工具（iperf / IxChariot）

对应《新员工试用期能力建设与签核手册》第 5 项「吞吐性能测试」，以及 [3.3 码流/媒体分析](/3-tools/stream) 中 Iperf / IxChariot 两小节的原理展开。

**目标**：能用 iperf3 组织一次结果可复现的吞吐测试，能判读输出字段并区分「端点瓶颈」与「网络瓶颈」；知道 IxChariot 与 iperf 测的不是同一件事，知道什么场景该换工具。

## 一、先分清三个测量层次

「这条网络能跑多少」是一个缺主语的问题。下面三个答案可以相差数倍，混用就是指标互相矛盾的头号来源。

| 层次 | 谁在测 | 这个数字回答什么 |
| --- | --- | --- |
| 链路层 | PHY 协商速率 | 硬件/射频规格。Wi-Fi 随 MCS、空间流、信道宽度、RSSI 与干扰连续变化 |
| 传输层 | iperf / iperf3 | 一台主机的协议栈在这条路径上能跑出多少字节 |
| 业务层 | IxChariot / Hawkeye 等 | 应用事务跑起来是什么体验（响应时间、卡顿、MOS） |

iperf 系列工作在第 2 层、口径到第 4 层为止；IxChariot 的默认定位是第 4 到第 7 层。这不是精度差别，而是测量对象的差别。

### 口径提醒：iperf 报的数字不含协议头

iperf 系列报的字节数是 socket API 观察到的值，**不含 IP 头、TCP 头与以太网帧开销**。所以 1 Gbps 链路上 iperf3 显示 940 Mbps 属于正常，不是丢包。

IP 头 20 字节 + TCP 头 20 字节（共 40 字节）是一笔固定成本，只随报文尺寸摊薄，不随链路速率变化：

| MTU | 协议头占比 | 备注意义 |
| --- | --- | --- |
| 576（最小重组缓冲） | 6.94% | 小包场景开销急剧放大 |
| 1500（以太网标准） | 2.67% | 2.5 Gbps 链路理论上限 2.43 Gbps |
| 9000（巨型帧） | 0.44% | 同一链路上限提到 2.48 Gbps |

巨型帧要求整条路径（两端网卡、交换机、虚拟化层）一致支持，任一跳仍是 1500 会被分片，结果比统一用 1500 **更差**。

### 同一条 2.5 Gbps 链路上的四个数字（都正确）

| 数字 | 相对线速率 | 它回答的问题 |
| --- | --- | --- |
| 2.5 Gbps | 100% | 硬件规格 |
| 2.43 Gbps | 97.3% | MTU 1500 下能承载多少 |
| 2.48 Gbps | 99.1% | 换巨型帧后能承载多少 |
| 2.36 Gbps | 94.4% | **这台主机的协议栈**在这条链路上跑出了多少（iperf3 报的那一行） |

## 二、iperf 家族：先确认两端跑的是同一个程序

现在叫「iperf」的东西是三个不同的程序，两条活着的分支**没有共同协议、彼此不能互通**：

| 分支 | 起源 | 当前状态 | 默认端口 |
| --- | --- | --- | --- |
| 原始 iperf | NLANR/DAST，约 2003 | 已停止演进 | — |
| iperf2 | 从原始 iperf 派生，独立维护 | 活跃，最新 2.2.2（2026-08） | 5001 |
| iperf3 | ESnet / 劳伦斯伯克利国家实验室重写 | 活跃，最新 3.21（2026-04） | 5201 |

端口不同带来的一个幸运之处：一端跑另一个分支时表现为**连接失败**而不是错误数字。排查「iperf 测不通」时，先确认两端是同一个程序，再查防火墙。

### iperf3 关键版本能力变化（只列影响结论的）

| 版本 | 新增 | 对测量结论的影响 |
| --- | --- | --- |
| 3.0 | JSON 输出 `-J`、`-R` 反向、`-O` 跳过慢启动、`-A` 亲和性、TCP 也可 `-b` 限速 | 测量开始可自动化、结果可入库比较 |
| 3.1 | `--udp-counters-64bit`、`--cport` | 64 位计数器解决长时间高码率 UDP 计数溢出 |
| 3.7 | `--bidir` 双向同时测试 | 才能暴露「单向各自正常、同时跑就崩」的设备 |
| 3.16 | **每条测试流启动独立线程** | 最实质的一次变化：此前为单线程，官方帮助文本直接写着「CPU 受限时增加 `-P` 不会带来更高吞吐」 |
| 3.20 | JSON 毫秒时间戳、乱序计数 `reorder_seen`、`--server-max-duration` | 乱序从隐性变量变成可观测指标（Wi-Fi 7 多链路、多队列场景） |
| 3.21 | Linux 支持 GSO / GRO、`--set-mss` 上限提到 32K | 把分段/重组下放内核，提高软端点可测上限 |

### 选型判据（三条）

1. **默认用 iperf3**：JSON 输出、干净 API、活跃维护，自动化回归的默认选择。唯一要先确认的是平台支持状态——Windows 不在 iperf3 官方支持范围内。
2. **出现下面任一条时切 iperf2**：需要组播（IPTV/组播会议承载验证）、需要一台服务端同时服务多个客户端、需要 UDP 包级时延与直方图、需要逐流拥塞窗口报告、需要响应性测试（RPS）、需要把上千条流压满多核。
3. **需要业务体验指标时两者都不够**：它们都回答不了「VoIP 听起来如何」。

用 iperf2 补测时，**必须把版本号一起写进记录**，否则补测结果无法与主基线对照。

## 三、iperf3 参数与影响机制

### 单流 TCP 吞吐的四个天花板

一个 iperf3 数字是四个独立上限里**最小的那一个**。这是「参数调了一圈没变化」的根源。

| 天花板 | 判据 | 提高它的手段 |
| --- | --- | --- |
| ① 链路带宽 | 物理层/链路层协商速率 | 换介质、加宽信道、改善射频条件 |
| ② 窗口 ÷ RTT | 吞吐 ≤ 窗口字节数 × 8 ÷ RTT 秒 | `-w` 增大缓冲、确认窗口缩放生效、缩短 RTT |
| ③ 丢包 | 吞吐 ≈ (MSS ÷ RTT) × 1.22 ÷ √p | 修物理层与队列、换 BBR 这类算法 |
| ④ 主机处理能力 | 端点单核 CPU 占用率 | 多流（3.16 起）、`-Z`、`--skip-rx-copy`、`-A` 绑核、GSO/GRO |

两个必须记住的量级：

- **丢包是平方根关系**：150 ms RTT 路径上仅 0.1% 丢包就足以把单流压到约 3 Mbps——与链路是 100 Mbps 还是 100 Gbps 无关。反过来，丢包降 100 倍吞吐才升 10 倍，所以把窗口从 64 KB 提到 16 MB 也救不回 1% 的丢包。
- **窗口是一道与带宽无关的硬上限**：未启用窗口缩放的 64 KB 上限在 100 ms RTT 上给出 5.24 Mbps 硬顶。带宽时延积（BDP = 带宽 × RTT ÷ 8）是这条链满载所需的最小窗口：

| 场景 | 带宽 | RTT | BDP | 64 KB 窗口下的利用率 |
| --- | --- | --- | --- | --- |
| 局域网备份 / iSCSI | 1 Gbps | 1 ms | 125 KB | 52% |
| 城域存储复制 | 10 Gbps | 20 ms | 25 MB | 0.3% |
| 跨大西洋文件传输 | 1 Gbps | 80 ms | 10 MB | 0.65% |
| 云区间（跨太平洋） | 10 Gbps | 150 ms | 187.5 MB | 0.04% |
| 卫星回传 | 100 Mbps | 550 ms | 6.9 MB | 0.95% |

判断方法：一边跑测试一边看两端 CPU。**某个核心稳定 100% 而其余核心空闲，说明你测的是 CPU 而不是网络。**

### 参数速查（按作用分组）

| 参数 | 默认/取值 | 一句话影响 |
| --- | --- | --- |
| `-t / --time` | 10 秒 | 默认时长截断慢启动段，结果系统性偏低；建议 30–60 秒起步 |
| `-O / --omit` | — | 丢弃前 n 秒预测试统计以跳过慢启动；总墙钟时间会相应增加 |
| `-i / --interval` | 1 秒 | 周期报告间隔；关掉它就无法判断曲线是否平稳 |
| `-P / --parallel` | 1 | 3.16 起每流一线程；只解锁逐流窗口、逐流限速、单核 CPU 三类限制 |
| `-w / --window` | 系统自动调优 | 小于 BDP 按比例压低吞吐；远大于 BDP 会推高排队时延（缓冲区膨胀） |
| `-l / --length` | TCP 128 KB 缓冲 / UDP 约 1460 B | UDP 下直接决定每秒包数；`-l 64` 是最坏情形 |
| `-u / -b` | UDP 默认 **1 Mbit/s** | 报「UDP 只跑了 1 Mbps」先检查有没有显式给 `-b`；`-b 0` 解除限制 |
| `-R / --reverse` | — | 服务端发送、客户端接收；两个方向的路径并不对等 |
| `--bidir` | — | 同一窗口压双向（开 2×P 条连接），测出单向测试永远测不到的故障 |
| `-M / --set-mss` | MTU−40 | 隧道场景（IPsec/GRE/VXLAN/WireGuard）必须校正，否则「小包正常、大包丢」 |
| `-Z / --skip-rx-copy` | — | 零拷贝发送 / 跳过接收拷贝，把主机 CPU 瓶颈往后推 |
| `-A / -C` | — | CPU 绑核 / 指定拥塞控制算法（均仅 Linux、FreeBSD）；CUBIC 与 BBR 在同路径可差数倍 |
| `--repeating-payload` | 随机字节 | 改用重复载荷，暴露带硬件压缩的设备（含部分 Wi-Fi AP）的问题 |
| `-J / --logfile` | — | JSON 输出与落盘；让结果可入库、可回归对比 |

两点容易误解：

- **`-w` 设的值不等于实际窗口**。Linux 内核会把设置值翻倍以补偿开销，而拥塞窗口实测只爬到翻倍值的约 75%。官方明确说这不是 iperf3 的缺陷而是内核行为（`tcp(7)` / `socket(7)`），要看实测 Cwnd 或用 `--debug` 核对。
- **`-l` 的 TCP 默认值 128 KB 是 iperf3 的读写缓冲区，不是报文大小**。真正的分段由内核按 MSS 决定；只有 UDP 下 `-l` 才直接决定每个数据报大小。

### UDP 模式：丢包率是双义指标

UDP 没有拥塞控制，发送速率由客户端说了算，因此「丢了多少」可能是网络丢的，也可能是**接收端主机来不及处理丢的**。区分办法是反向验证：

1. 把 `-b` 调到明确低于链路能力——丢包消失说明此前是速率问题；
2. 看服务端 CPU 占用与绑核（ESnet 在 100G 测试床上遇到 UDP 超 10 Gbps 时接收端恒报约 20% 丢包，且与客户端 `-b` 无关，官方判断可能源于 CPU 绑定）；
3. 把 `-l` 调大减少每秒包数——丢包随包数而非字节数变化，说明瓶颈在包处理路径。

### 按问题选参数

| 要回答的问题 | 建议组合 | 为什么 |
| --- | --- | --- |
| 这条链路/设备的极限 | `-t 60 -P 4 -O 10 -i 1 -J`，两端同时看 CPU | 长时长跨过慢启动，多流解锁单核，JSON 便于归档 |
| 真实业务（单条流）能跑多少 | `-t 60`，`-R` 与不带 `-R` 各跑一次，不加 `-P` | 单流数字才对应单条备份/复制连接 |
| 瓶颈在逐流还是共享 | 同一时刻跑单流与 `-P 4` 比较汇总 | 多流明显更高 → 逐流限制；两者相同 → 共享限制 |
| 丢包对吞吐的实际影响 | `-u -b` 阶梯递增找丢包拐点，再对照 TCP 结果 | UDP 给拐点，TCP 给应用实际能拿到的量 |
| QoS 策略是否生效 | 两个方向各跑两组：带 `--dscp` 与不带 | 不设标记就测不出标记的效果 |
| 低时延应用在负载下的表现 | `-u -b` 低速小包 + 并行大流量背景 | 验证排队时延，即 TR-398 延迟-负载用例的思路 |
| 隧道/封装后的实际吞吐 | 先 `-M` 按隧道 MTU 校正再测，必要时 `--dont-fragment` | 避免把分片丢失误读成链路质量问题 |
| 回归测试 / CI 门禁 | `-J` + `--logfile`，固定全部参数并记版本号 | 可比较性来自参数冻结，不来自测试次数 |

### 三套可直接复制的模板

```bash
# 研发回归基线
iperf3 -c <host> -O 5 -t 30 -P 4 -i 1 -J > run.json

# 高带宽长肥路径（先按 BDP 核算窗口）
iperf3 -c <host> -O 5 -t 30 -P 8 -w 4M -i 1

# UDP 拐点扫描：从 -b 100M 起按 2 倍阶梯递增，固定 -l 1200，逐档记录丢包率
```

模板的价值在于它们被冻结下来，而不在于它们「最正确」。只有模板没有记录时，三个月后的历史数据依然无法解释。

## 四、结果判读

### 一次测试里有几个「结果」

- **两个视角**：同一段传输，`sender` 报一行、`receiver` 报一行，两者不等是正常的（差值是仍在途的数据与协议栈开销）。
- **多条连接**：`-P` 时每条流各报一行，外加 `[SUM]` 汇总行——汇总行是各流之和，**不是链路带宽**。
- **多个时间段**：每 `-i` 秒一行中间结果，末尾一行合计。
- **`--bidir` 的 `[TX-C] / [RX-C] / [TX-S] / [RX-S]`**：C 为客户端、S 为服务端，TX 为发出、RX 为收到，四个方向的数据同时出现。

### 字段逐项

| 字段 | 含义 | 读的时候要注意 |
| --- | --- | --- |
| Interval | 该行覆盖的时间区间 | 高丢包路径上间隔会偏离 `-i` 设定值（发送方阻塞到整块写完） |
| Transfer | 该区间传输字节数 | socket API 观察值，不含 IP/TCP 头与以太网帧开销 |
| Bitrate | 由 Transfer 与 Interval 算出 | `-f` 切换 Kbit/s 与 KB/s 时数值差 8 倍 |
| Retr | 发送端 TCP 重传次数 | **接收端看不到重传**，只看 receiver 行会得出「无丢包」的错误印象 |
| Cwnd | 发送端拥塞窗口 | Cwnd 顶在窗口上限不动 = 窗口受限的直接证据 |
| Jitter | UDP 到达间隔抖动 | 由接收端计算；用 `-R` 时要去接收端日志里读 |
| Lost/Total | UDP 丢包数与比例 | 分母是该方向发出的包数；手机丢包与网络丢包不可区分 |
| `[SUM]` | 所有并行流合计 | 聚合口径，不代表单条业务能拿到的速率 |

### 七种典型误读

| 形态 | 实际含义 | 纠正方式 |
| --- | --- | --- |
| 把服务端 `sender` 行当「客户端下载速度」 | 方向与视角双重错位，结论可能完全反了 | 先确认看的是哪个方向的哪一侧；`-R` 时尤其容易错 |
| 忽略 `-b` 的限速 | 报出接近某个整数档位的速率是你设的上限，不是网络极限 | 确认是否显式给了 `-b`；`-b 0` 才解除限制 |
| 混淆 bit 与 Byte | 同一结果两种格式相差 8 倍 | 固定一种格式写进测试条件；注意 `-f` 参数字母大小写 |
| 用默认 10 秒时长下结论 | 慢启动尚未结束，RTT 越大偏低越多 | 时长 30–60 秒起步，或加 `-O` 丢弃前段 |
| 把 UDP 丢包全部归给网络 | 可能是接收端主机丢的 | 降 `-b`、增大 `-l`、绑核，看丢包是否随之消失 |
| 以为 Retr 0 就等于无丢包 | 重传信息只在发送端可见 | 同时查看客户端与服务端输出（`--get-server-output`） |
| 把 `[SUM]` 当链路带宽 | 聚合口径被当成单流口径写进报告 | 单流与多流成对报告，注明各自对应什么业务形态 |

### 一次完整的归因示范

现象：标称 1 Gbps 的线路上，iperf3 单流只跑出约 90 Mbps，路径 RTT 约 100 ms。六步顺序比每一步的结论更重要：

| 步 | 动作 | 排除或确认了什么 |
| --- | --- | --- |
| 1 | 单流 30 秒，同时读发送端与接收端两行 | 两端一致、重传正常 → 排除「数据在途造成的口径差异」 |
| 2 | 同一时刻加 `-P 4` 对照 | 四流合计约 360 Mbps、接近线性 → 指向逐流限制 |
| 3 | 看两端 CPU 占用 | 均为个位数 → 排除主机 CPU 受限 |
| 4 | 检查拥塞窗口 | 稳定停在约 64 KB 不再增长 → 指向窗口上限 |
| 5 | 按 BDP 核算（1 Gbps × 100 ms ÷ 8 = 12.5 MB） | 64 KB 仅占 0.5% → 确认窗口就是硬约束 |
| 6 | 用 UDP 阶梯扫描复核 | 丢包到接近线速才升高 → 排除路径丢包 |

结论是「端侧窗口没有随带宽时延积放开」，而不是「链路有问题」。同一组数字如果停在第一步就下结论，会得到几乎相反的判断。

### 多次测量怎么汇总

- **不用单次最好值**：网络测量分布右偏，偶发的「跑得很好」不可复现，把它当能力上限会把后续正常结果都判成退化。
- **不用均值代表典型值**：一次异常慢测会把均值拉低，中位数不受影响；两者相差明显时说明分布有长尾。
- **用 P95 代表「最差的可接受情况」**：用户抱怨的从来不是中位数。
- **剔除规则必须事先写下**：「这次不算」在方法上等同于挑数据。
- **判据用区间**：单点门禁（「等于 940 Mbps」）会把测量自身的波动报成退化；工程口径建议基线至少 5 次并附 P95。

## 五、IxChariot：应用层性能测试系统

### 血统与定位

IxChariot 最初由 NetIQ 推出（当时叫 Chariot），后成为 Ixia 产品并改名，Ixia 被 Keysight 收购后归入其网络测试产品线。约 2020 年 IxChariot Pro 版本线更名为 **Hawkeye**，两者共用同一套 Endpoint。改名同时发生了一次定位分工：

| | 面向 | 定位 |
| --- | --- | --- |
| IxChariot | 部署前 | 设备验证、架构验证、上线前就绪度评估；跑「假设（what-if）」场景 |
| Hawkeye | 部署后 | 主动监控平台：合成流量做节点间与真实业务测试，判断终端用户体验 |

Keysight 官方产品页称其被 Wi-Fi Alliance 使用——含义是：某些认证测试里的「应用层性能」口径，可能本来就来自这套工具的定义方式。用裸 iperf3 去对齐认证结果时，差异可能来自工具而不是产品。

### 三层架构

| 角色 | 职责 |
| --- | --- |
| Console（控制端） | 定义拓扑、编辑脚本、下发任务、监控与出报告。有 Windows 桌面版，也有基于 Web 的 Linux Server Edition |
| Performance Endpoint（执行端） | 轻量代理，直接调用所在系统 TCP/IP 协议栈与网卡收发；支持 Windows / Linux / macOS / Solaris / FreeBSD / 嵌入式 Linux / Android / iOS / 虚拟机 / 公有云 |
| Registration Server（可选） | 让端点能被 Console 发现并维持心跳，端点可工作于 NAT 与防火墙之后 |
| IxProfile（辅助） | 从真实网络抓流量，据此生成自定义测试脚本 |

**被测业务路径的两端各必须有一个端点。** 把 Console 装在被测路径的一端、只用对端一个端点做测试，测到的是 Console 到设备的管理通道路由，不是真正的业务转发路径。

### 对象模型：场景即资产

iperf 把参数写在命令行里，IxChariot 把场景保存成工程文件。可重复性来自保存的场景，不来自记住的命令。

| 对象 | 含义 |
| --- | --- |
| Pair（业务对） | 最小测试单元：一条单向业务流，绑定源端点、目的端点与一个脚本。双向测试＝复制一对并交换源/目的 |
| Group（组） | 多个 Pair 编成一组，统一运行时长，可按组汇总报告 |
| AppMix（应用混合） | 按比例混合多种应用流量，可携带 QoS 模板（DSCP 标记） |
| Test Setup | 整场测试的容器，保存后即可重复执行的测试资产 |

脚本是原子单元，覆盖 TCP / UDP / RTP / SPX / IPX / SNA / IPv6。最基础的 `Throughput.scr` 就是一次循环，四个关键参数：

| 参数 | 作用 |
| --- | --- |
| Initial_delay | 多业务混合时错开各流起始时刻，避免同时冲击同一队列 |
| Number_of_timing_records | 决定测量窗口划分粒度 |
| Transactions_per_record | 决定单条记录的样本量 |
| file_size | 决定吞吐结果被固定开销主导的程度。**默认值通常偏小**，高速链路上会「瞬间传完」被判该次测量无效 |

```
吞吐 ≈ Transactions_per_record × file_size × 记录数 ÷ 总运行时长
```

要点是：**要测的量必须比固定开销大得多，否则你测的是开销。** 把默认文件大小提高十倍是常见起步调整。

做 RFC 2544 帧长序列测试时必须换算一次——`file_size` 是有效载荷，RFC 2544 规定的是以太网帧长，两者相差 58 字节头（14B 链路层 + 20B IP + 20B TCP + 4B FCS）：

| RFC 2544 帧长 | 对应 file_size | 备注 |
| --- | --- | --- |
| 64 | 6 | 包速率最高，对交换结构压力最大 |
| 128 / 256 / 512 | 70 / 198 / 454 | — |
| 1024 / 1280 | 966 / 1222 | — |
| 1518 | 1460 | 标准最大帧，恰好等于常见 MSS，不再分片 |
| 1600（超帧） | 1542 | 会被分片成 1460 + 82 |

启用 TCP 时间戳、VXLAN 封装或 IPsec 隧道都会改变这 58 字节，换算会整体偏移——对齐标准前先抓一次包量出真实头部长度。

### 度量口径

| 指标族 | 具体指标 | iperf 系列是否提供 |
| --- | --- | --- |
| 吞吐 | 吞吐量、事务速率（Transaction Rate） | 提供吞吐，无事务速率 |
| 时延 | 响应时间、单向时延、往返时延 | 仅 UDP 抖动 |
| 质量 | 丢包、抖动、丢失数据量 | 提供丢包与抖动（UDP） |
| 语音质量 | 6 种 VoIP 编解码器的 MOS 评分 | 不提供 |
| 视频与应用 | OTT 视频体验、HTTP 流、Citrix 等业务响应 | 不提供 |
| 无线相关 | Wi-Fi 统计（SSID/BSSID 等） | 不提供 |

口径提醒：MOS 是由客观参数映射出来的主观质量分，其可比性依赖同一套编解码器参数。**把 MOS 当作「网络客观质量」使用，会得到看起来精确、实际只是模型输出的数字。** 单向时延则需要两端时钟同步，误差来源是时钟偏移。

报告呈现与 iperf3 的差别是结构性的：IxChariot 把平均值/最小值/最大值与 95% 置信区间、相对精度做进了产品本身，支持 HTML/文本/CSV 导出与跨运行对比；iperf3 要得到分布必须自己跑多次并写脚本汇总。在需要「证明某产品稳定达标」的场合（认证、验收、SLA），这个差别往往比吞吐数字本身更能决定工具选择。

### 同一链路上两个工具给出不同结论：四种解释

| 假说 | 机制 | 验证方式 |
| --- | --- | --- |
| P1 测量层不同 | iperf 报 socket 观察到的字节速率；IxChariot 报事务级吞吐与响应时间 | 同一测试里同时看「字节数 ÷ 时间」与「事务数 × 事务大小 ÷ 时间」，差值是应用层开销 |
| P2 并发模型不同 | 单流 vs pair 在并发度、线程模型、进程调度上都不一样 | 把 iperf 的 `-P` 调到与 pair 数一致再比较 |
| P3 载荷特征不同 | iperf3 默认随机字节，业务脚本按真实应用特征构造载荷 | 用 `--repeating-payload` 把 iperf3 的载荷换成重复模式再测一次 |
| P4 部署位置与端点实力不同 | 端点主机的 CPU、网卡、驱动直接决定可测上限 | 测试期间看两端 CPU；把 iperf 换到与商业端点同级的机器上复测 |

四种解释都能在没有工具缺陷的前提下产生数倍差异。**工具之间的一致性只能通过条件对齐获得，不能通过换工具获得。**

### 端点安全基线（必须纳入资产盘点）

| 时间 | 事件 | 版本 |
| --- | --- | --- |
| 2017-08-11 | 两个当时被归为功能缺陷的问题，2026 年被追认为高危 CVE | Endpoint 9.5.102 |
| 约 2020 | IxChariot Pro 线更名为 Hawkeye（共用同一套 Endpoint） | — |
| 2026-04-30 | 修复 CVE-2026-49435（CVSS 9.3，栈溢出，**未认证、单包即可管理员权限执行代码**） | Endpoint 10.0.254 |
| 2026-06-26 | 同一漏洞在监控与探针产品线上的修复 | Hawkeye 6.0.7；IxProbe / IxTap / IxByPass 3.13.0 |

测试端点的三个特征使它系统性避开常规软件清单：以硬件名登记（「那台测试机」）、被当作临时资产（装过一次再没动过）、常连在被测设备的管理网段上（横向移动价值高于普通终端）。可执行动作三条：确认每个端点的实际版本号；把旧版本列入整改；**检查虚拟机模板、镜像与备份介质里的旧版本**——否则一次恢复就把旧版本带回来。

开源侧同类风险是另一种形式：iperf3 服务端没有认证机制，任何能连到 5201 端口的主机都能让它跑起一段流量，占用被测链路带宽与端点 CPU。官方提供两个缓解选项：`-1 / --one-off`（处理完一个客户端即退出，不留常驻进程）、`--server-max-duration`（限制计时测试最长时长）。要做的事与商业端点侧相同：确认哪些机器跑着什么版本、哪些端口对外可达、有没有孤儿服务端进程。

## 六、标准脉络：2544 / 6349 / Y.1564 / TR-398

四个标准回答四个不同的问题。把工具挂到标准上，选型就不再靠偏好。

| 标准 | 测量对象与层次 | 并发模型 | 判据特征 |
| --- | --- | --- | --- |
| RFC 2544 | 单个互联设备的帧转发，L2/L3 | 单流，四类测试顺序执行 | 零丢包 + 二分搜索找最高速率，结果呈通过/不通过 |
| RFC 6349 | 端到端路径的 TCP 吞吐，L4 | 单条与多条 TCP 连接分步测量 | 引入 TCP 效率与缓冲区时延占比两个连续指标 |
| ITU-T Y.1564 | 以太网业务开通验证，L2/L3 | 多业务并发，单次测全部 SLA | 按带宽轮廓（承诺/超额速率）逐业务判定 |
| BBF TR-398 | 接入点在室内场景的整体性能，含射频层 | 32 站并发、多频并发 | PASS/FAIL 阈值表，覆盖吞吐、时延、公平性、稳定性 |

一个必须先说清的事实：**RFC 2544 的整套判据建立在「测试仪本身不引入偏差」这一未言明的前提上。** 硬件仪表接近这个前提，软件端点不接近——它的 CPU 频率、内核缓冲、网卡 offload、驱动队列分配乃至载荷随机性都会进入结果。这个维度在主流的 RFC 2544 / RFC 6349 框架里没有位置。TR-398 部分绕过了它（规定使用特定测试台与流量生成方式），代价是结论只对那套测试台成立。

### RFC 2544 的四类测试与被指出的判据缺陷

四类测试：吞吐（从 100% 帧速率递减，二分搜索步长 50 / 25 / 12.5 / 6.25 / 3.125%，直到分辨率落在 1%–10%）、时延（以已确定吞吐速率发不少于 120 秒帧流，第 60 秒后打标，至少重复 20 次取平均；按规范跑完七档帧长约 280 分钟）、帧丢失率、背靠背帧。

2020 年一项实证研究指出三点可用实验复现的问题：

1. **对延迟过度宽容**：只要帧最终被转发，吞吐项就算通过——一台引入大量排队时延的设备可以在吞吐项上拿满分。
2. **零帧丢失判据过于绝对**：设备若有非零但很低的丢包率，RFC 2544 意义上的吞吐会测得接近零，而真实通信仍能以可观速率进行——指标在临界点附近跳变。
3. **未要求统计显著的多轮测试**：单次试验结果差异可能很大，数值可靠性不足。

### RFC 6349 与那个 100 Mbps 案例

RFC 6349 给的是可执行顺序：先做 L2/L3 开通测试 → 路径 MTU 探测（RFC 4821）→ 确定基线 RTT 与带宽 → 单条与多条 TCP 连接吞吐测试。两个新指标：

- **TCP 效率**：传输字节中非重传字节的比例——回答「多少带宽被重传浪费了」。同一段吞吐，99% 与 92% 对应的链路状况完全不同。
- **缓冲区时延占比**：测试期间平均 RTT 相对空载 RTT 的增幅——回答「缓冲区被填到了什么程度」。**必须先在没有测试流量时测一次基线，否则这个指标没有意义。**

这两个指标把「吞吐不够」拆成两种可区分的病因：重传多说明路径在丢包（查物理层与干扰），时延增幅大说明缓冲区在排队（查整形与队列配置）。处置方向相反，只报一个吞吐数字时两者长得一模一样。

标准里还有一条常被忽略的警告：网络本身处于异常状态时不可能做出准确的 TCP 吞吐测量，5% 丢包和/或 150 ms 抖动已可能超出可准确测量范围——此时应先修链路，而不是继续测。

典型案例：客户购买 100 Mbps 透明 LAN 服务，服务商用 RFC 2544 测得达标，客户 FTP 实测只有 25 Mbps。根因是端侧未启用 TCP 窗口缩放、最大窗口卡在 64 KB（RFC 6349 对该路径推荐 250 kB）。这类问题只有第 4 层测量才看得见。

### TR-398：Wi-Fi 场景的补位

2019 年作为首个室内 Wi-Fi 性能标准推出，现称 BBF.398，用于评定 802.11n/ac/ax 家用路由器与接入点。Issue 3（2024-02 获批）把用例归入 7 大类共 24 项，焦点从「覆盖与单频吞吐」转向「多频并发与体验」；Issue 4 面向 Wi-Fi 7，加入多链路聚合吞吐、新旧世代混合设备的空中时间公平性、最坏情境延迟与抖动。

**延迟-负载测试（6.2.6）是所有标准里最接近「体验」的一项**：在低负载、高负载与超载（125%）三种条件下测单向时延，平均值与最大值分别达标。社区候选阈值：

| 负载 | 平均单向时延 | 最大单向时延 |
| --- | --- | --- |
| 1% | < 10 ms | < 20 ms |
| 70% | < 20 ms | < 40 ms |
| 125% | < 50 ms | < 100 ms |

但实测反差很大：提交该用例的团队用 32 台真实网卡做站点，在 32 站高负载下观测到 1 秒以上的单向时延，部分接入点达到数秒级，因此建议把阈值放宽到「几百毫秒」。**在实验室里跑出来的吞吐曲线漂亮，和用户在多设备家庭里的实际体验，是两件相差三个数量级的事。**

32 站并发的判据本身：2.4 GHz 每站 2 Mbps UDP、5 GHz 每站 8 Mbps UDP，各持续 2 分钟，要求每站丢包低于 1%，总吞吐不低于 64 Mbps × 99%（2.4 GHz）与 256 Mbps × 99%（5 GHz）。这些数字本身不高（第三方复现测试中当时三款产品全部通过，区分度有限），价值在于**可复现**。

三条口径提醒：延迟-负载阈值来自社区提案、尚未确认为最终核准值；TR-398 用例项数在不同文档中记为 20 至 24 项（差异来自 Mesh 与条件必测项的计入口径）；Issue 4 部分规格仍在推进中。

### 按标准组织测试计划

| 阶段 | 依据 | 判据形式 | 产物 |
| --- | --- | --- | --- |
| 研发回归 | 自定基线 | 区间判据（≥ 基线中位数的 95%） | 基线与本次的对照表 |
| 设备功能验证 | RFC 2544 | 零丢包 + 二分搜索，PASS/FAIL | 按帧长分档的测试记录 |
| 以太网业务开通 | ITU-T Y.1564 | 按带宽轮廓逐业务判定 | SLA 验证报告 |
| 端到端路径验证 | RFC 6349 | 连续指标，需与空载基线对照 | 路径测试报告 |
| 产品性能与认证 | BBF TR-398 | 阈值表 PASS/FAIL | 认证测试报告 |
| 上线后监控 | 自定（监控类工具） | 趋势与告警阈值 | 监控看板与告警记录 |

被问到「这次该按哪个标准测」时，先看测试处在哪个阶段，而不是先看手上有哪套工具。

## 七、场景与选型

| 场景 | 要回答的问题 | 首选组合 | 关键约束 |
| --- | --- | --- | --- |
| 设备研发与固件回归 | 这次改动有没有让吞吐或时延退化 | iperf3 + `-J` + CI 门禁；需组播或包级时延时补 iperf2 | 参数冻结并纳入版本管理 |
| Wi-Fi 产品与认证 | 多站/多频并发、负载下时延是否达标 | 按 TR-398 口径的自动化测试台 | 射频条件必须可控且可复现；**只看峰值吞吐会漏掉体验问题** |
| 网络验收与 SLA | 这条业务线路能否承载承诺等级 | RFC 6349 的 TCP 层测量 + 多业务并发验证 | 必须走真实端到端路径，不能拿隔离环境结果替代 |
| 日常运维排障 | 用户抱怨慢，瓶颈在哪一段 | iperf3 单流与多流对照 + CPU 观测 | 要在业务可用窗口内做，测试流量本身占带宽 |
| 测试资产与安全 | 有多少端点、版本多少、暴露面多大 | 资产盘点 + 版本核对 | 端点最易停留在旧版本 |

三类任务**不值得**上商业工具：只需要一条链路的吞吐上限；要嵌进产品固件或产线测试（iperf3 有 libiperf 库形态可编译进目标系统）；被测对象本身就是端点能力（此时商业工具更适合作为基准尺，而不是被测对象）。

### 生态位：它们不在同一个竞争维度上

按「部署与持有成本」与「业务仿真保真度」两个维度摆开，iperf3 / iperf2 / netperf / TamoSoft / Ostinato 在左下（低成本·基础工具），TRex / LANforge 在中间地带（需要自定义流量但不需要业务模型），IxChariot / Hawkeye 偏右上（业务仿真），IxLoad / Spirent 在右上极端。这张图的用法是排除法：需求落在左下象限，右上象限的工具都是浪费；需求明确涉及 MOS、组播、多业务并发，左下象限的工具无论怎么调参数都到不了。

### 三条推荐组合

1. **研发回归线**：iperf3 为主（JSON + CI 门禁 + 参数冻结），iperf2 在需要组播、包级时延或每流拥塞窗口时补位。成本接近于零，瓶颈在人而不在工具。
2. **产品性能线（Wi-Fi / 路由器 / 网关）**：按 TR-398 口径组织自动化测试，把延迟-负载与公平性作为必备项而非可选项。自建测试台用定制 iperf3 做流量生成是经过验证的可行路径。
3. **对外承诺线（验收、认证、SLA）**：用带业务仿真的工具产出可对外的结论，并按 RFC 6349 报告 TCP 效率与缓冲区时延占比。结果一旦对外，就必须附带完整测试条件记录。

### 自建 Wi-Fi 测试台的三个决定

| 决定 | 结论 |
| --- | --- |
| 射频条件用衰减器还是人工摆位 | 人工摆位不可复现（同一个人两次摆放结果也可能不同）；可编程衰减器 + 固定工位是唯一能把「位置」变成参数的做法 |
| 站点用真实终端还是仿真射频 | 真实终端贴近现实但数量受限、状态难控；仿真射频可拉高站数，但站点行为更规整，公平性与重传行为的测法与实际有差异。判据与用哪种站点无关 |
| 时延在哪里测 | **最容易做错的一项**。观测点与流量生成端同侧时，测到的时延里含有测试台自身的排队与主机开销。观测点应放在被测设备的上行侧，或用第三台独立主机做旁路观测 |

## 八、变量控制与最小记录集

### 会改变结果的变量（固定取值或记录取值，没有第三条路）

| 层面 | 变量 | 它如何改变结果 | 固定/记录方式 |
| --- | --- | --- | --- |
| 端点主机 | CPU 型号与核绑定 | 高 UDP 速率下接收端出现与 `-b` 无关的固定丢包；25 GbE 以上单流 TCP 常先撞 CPU | `-A` 指定亲和性；测试时两端同时看各核占用 |
| 端点主机 | 工具版本 | 3.16 起每流独立线程、3.20 加乱序计数、3.21 加 GSO/GRO——同一命令在不同版本上是不同的工具 | 两端都跑 `--version` 并写入记录；**升级视为变更，必须重跑基线** |
| 端点主机 | 内核缓冲区行为 | Linux 把 `-w` 值翻倍计算，而实测 Cwnd 只爬到翻倍值的约 75% | 记录 `-w` 与内核版本；用 `ss -i` 核对实际 cwnd |
| 端点主机 | offload 与零拷贝选项 | `-Z` / `--skip-rx-copy` / GSO-GRO 改变包处理成本 | 同组对比必须一致；记录是否启用 |
| 链路与介质 | 帧长与 MTU | 40 字节头在 9000 字节帧上只占 0.44%，在 1500 上占 2.67% | 记录 MTU 与 `-M`；跨链路比较前先对齐帧长 |
| 链路与介质 | 无线位置与衰减 | 无线实际吞吐约为理论 PHY 速率的 50%–60% 以下，每跳 mesh 再减约一半 | 用可编程衰减器与固定工位替代人工摆位 |
| 工具参数 | 时长与预热 | 默认 10 秒截断慢启动段，低估结果 | `-O` 跳过慢启动、`-t` 30–60、`-i 1` |
| 工具参数 | 并发流数 | 3.16 之前服务端单线程，CPU 受限时增加 `-P` 无增益 | 冻结 `-P` 取值；诊断时先单流再多流对照 |
| 工具参数 | TCP 窗口 | 64 KB 上限在 100 ms RTT 上给出 5.24 Mbps 硬顶 | 记录 `-w`；对照实验必须走同一条路径 |
| 工具参数 | 载荷熵 | 默认随机字节 vs 循环载荷，带硬件压缩的设备上结果不同 | 固定载荷模式；跨工具比较时必须一致 |
| 工具参数 | UDP 包长与目标速率 | `-l 64` 是最坏情形（一次对照中 8 条并行流出现 81% 丢包，去掉该选项后 8 流合计 810 Mbps 且 0% 丢包） | 记录 `-l` 与 `-b`；小包测试单独成组，不与常规包长混算 |
| 测量与统计 | 重复次数与统计量 | 单次最好值不是证据 | 基线至少 5 次，同时给出中位数与 P95 |
| 测量与统计 | 判据形式 | 单点门禁会把测量波动报成退化 | 用区间判据，例如「不低于基线中位数的 95%」 |
| 环境与资产 | 端点与软件版本清单 | 端点常以硬件名登记而脱离软件清单，最易停留在旧版本 | 把工具与端点版本纳入资产清单；检查镜像、模板与备份介质 |
| 环境与资产 | 业务共载与测试窗口 | 测试流量本身占用带宽，业务侧整形会互相影响 | 选择窗口并记录共载情况；不在业务高峰做基线 |

### 一次测试的最小记录集（七项）

1. 两端主机标识（主机名或资产编号）、CPU 型号、内存、操作系统与内核版本；
2. 两端工具版本（`iperf3 --version` 的完整输出行）；
3. 链路与介质（有线速率与帧长 / 无线频段、信道宽度、工位与衰减设定）；
4. **完整命令行，含全部选项，直接复制粘贴而非事后回忆**；
5. 测试窗口（日期时间、持续时长、共载情况）；
6. 重复次数与统计量（次数、中位数、P95，以及是否剔除任何一次及其理由）；
7. 判定判据（这一次的通过线是多少，事先写下）。

低成本的实现方式：固定一条命令模板，把端点信息与条件写成同目录的说明文件。

```text
日期     2026-09-15 14:20–14:35（窗口内无其他测试任务）
端点 A   lab-pc-07 / i5-12400 / 16 GB / Windows 11 23H2 / 网卡驱动 2.1.3.15
端点 B   lab-dut-01（被测设备管理侧）/ iperf3 3.21，A 端同版本
链路     有线 2.5GBASE-T 直连，MTU 1500，路径无中间设备
命令     iperf3 -c lab-dut-01 -O 5 -t 30 -P 4 -i 1 -J > run.json
重复     5 次；发布中位数与 P95
判据     通过线 = 上季度基线中位数的 95%
```

检验标准只有一句：**换一个人拿着它，能在同样两台机器上复现出量级相同的数字。** 不能的话，这个数字就不该出现在结论里——因为它无法被反驳，也无法被采用。

## 验收 checklist（导师签核项）

- [ ] 能说明「链路层能跑多少」「传输层能跑多少」「业务能跑多少」三种问法的区别，并用一次测试把它们区分开
- [ ] 能独立完成一次 iperf3 测试：服务端启动、客户端发起、TCP 与 UDP 各一轮，并说明每个参数为什么这样设
- [ ] 能判读一次输出的 `sender` / `receiver` / `[SUM]` / `Retr` / `Cwnd` 字段，指出哪个数字对应的业务形态
- [ ] 遇到「吞吐远低于预期」时，能按「单流 vs 多流 → CPU → Cwnd → BDP → UDP 阶梯」的顺序给出归因，而不是先改参数
- [ ] 能按最小记录集七项留档，让另一个人凭记录复现出量级相同的数字
- [ ] 能用 IxChariot 配置一对业务流并出报告，指出它的结果与 iperf3 数字为什么不相等
- [ ] 能说出 RFC 2544 / 6349 / Y.1564 / TR-398 各自测什么，以及在验收阶段该按哪一个组织测试
- [ ] 知道测试端点需要纳入资产盘点，能说出 Endpoint 与 iperf3 服务端各自的安全注意事项
